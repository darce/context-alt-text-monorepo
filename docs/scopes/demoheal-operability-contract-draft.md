# DEMOHEAL operability contracts — implementation draft

Date: 2026-09-21. Owner: DEMOHEAL-1. This is a proposed contract, not a claim about shipped APIs. Implementation promotes it into `docs/workbay/contracts/proxy-route-manifest.md`, `security.md` and `gpu-lifecycle.md` in the owning slices. Existing fields were checked at `11fe4dea7` using codebase graph snippets. New symbols below are explicitly proposed.

## Route inventory and unavailable state (slices 1–2)

`ProxyRoutes` (new PHP constant class) owns the nine retention call sites first. Each entry has method, API path template and an explicit `route_level_not_found` flag. Do not claim all proxy families are covered until their callers are migrated and tested. The deterministic FastAPI exporter emits sorted method/path pairs without opening network connections or starting lifespan services. Normalize path parameters consistently (PHP placeholder name is irrelevant); ignore query strings and documented implicit HEAD/OPTIONS routes. A stale-fixture test compares the exporter output byte-for-byte. PHP parity tests must exercise all retention controller handlers and compare the **actual emitted method and complete path** to the map and manifest; a subset-only test on an unused map is insufficient.

A static retention policy/status endpoint returning an untyped router 404/405 can be `contract_mismatch`. A typed domain/resource-not-found response remains a domain 404 even when its route is declared. Never rewrite 401/403, 429, or a parameterized entity 404 as a route mismatch. Tests cover each distinction; no transport failure is invented from an application error.

Keep the existing `{reason,service,http_status,retry_after_seconds,checked_at}` contract and add optional `request_id`. `http_status` remains null when no upstream HTTP response exists. `checked_at` is when this availability observation happened, not proof an API call happened. Retry seconds is null when unknown or when manual configuration is needed. Do not manufacture a countdown for missing configuration. Missing localized endpoint produces a typed local `not_configured` result with no upstream status/request id; failed WP REST calls are rendered from the error path as well as the data path. Keep unknown/unparseable failures distinct from known reasons.

One PHP class-constant vocabulary and one TS `as const` vocabulary per domain, linked by a shared fixture, preserve the declared PHP >=8.0 floor. Do not add native PHP backed enums without a separately scoped runtime-floor change. Reuse `serviceUnavailable.ts:parseUnavailable/readUnavailable`; the shared notice renders service, reason, checked time, optional retry and optional request id. It must handle both WP_Error-shaped and available:false data envelopes. Capture of the demo's generic panel is evidence for the historical cause, not a prerequisite for fixing the independently reproduced missing-endpoint and thrown-error paths.

## Diagnostics, breaker and correlation (slice 3)

Proposed admin routes, all `manage_options` plus normal REST nonce/auth checks:

**Amended 2026-09-21 after planning review DEMOHEAL-1-PR-01/05/06/07: there is exactly ONE connection-truth surface.** The existing authenticated `POST acx/v1/settings/test` remains that surface and is extended in place; no second probe contract is introduced and the existing `TestConnectionResponse` outcome taxonomy (including `invalid_key`) is preserved, with new probe results added as additive optional fields. `SettingsPage` keeps calling the localized `settingsTest` endpoint; localization, producer, consumer and `security.md` move in the same slice. The existing ban on anonymous `/health` probes stands: the probe set is the authenticated `/recognition/health/pool`, `/scene/gpu/status` and `/recognition/retention/policy`. A public `/health` response is never sufficient for a green card.

- `GET acx/v1/recognition/connection`: cached diagnostics only; does not probe or reset. Each stored result carries the effective-target fingerprint (API base URL + key id + tenant) and its observation time. A result whose fingerprint differs from the current configuration, or which is older than a 300-second TTL, is returned as `stale`; a site with no stored result is `never_checked`. Green is allowed only for a fresh result matching the current fingerprint. Reconfiguration invalidates immediately. First-read and reconfiguration tests are required.
- `POST acx/v1/settings/test` (extended): bounded read-only probes as above. No user-supplied URL, no redirects to another origin, no GPU intent or work creation. Concurrent checks are coalesced by a short-lived database single-flight lease keyed by site+fingerprint; a caller that loses the race returns the in-flight result rather than launching its own probes. A bounded probe pool caps concurrent outbound diagnostics per site; on saturation the response is a local `not_sent` outcome, never a timeout attributed to the API. Contention is tested alongside a normal proxy request.
- `POST acx/v1/recognition/connection/reset-breaker`: explicit allowlisted family; no wildcard reset. Record actor, family, prior state and new state. Separate manual trip is deferred; RES-15's full operator-control pattern is not claimed implemented by reset alone.

Set a total probe budget of 10 seconds with at most one attempt per route and at most 3 seconds each. These are initial UI policy limits, not measured SLOs. Reuse proxy timeout controls; disable automatic retries for these probes, coalesce simultaneous checks per site, and return partial/timeout outcomes when the total deadline expires. A probe respects the family's open breaker; reset is a separate explicit operation. Health success never proves authenticated route success.

Breaker semantics: closed -> open at the existing threshold; open makes no upstream attempt until cooldown. At cooldown atomically admit exactly one half-open trial per family, deny other callers until its result; success closes, failure/timeout reopens. A stale probe completion must not overwrite a newer reset/open transition: compare state version/owner on update. Include expiry, simultaneous requests and reset-during-probe tests. A transient get-then-set is not atomic admission; the implementation must use the site's shared database with conditional ownership updates. Reuse the existing abstract proxy named-lock acquisition/release for breaker updates, clamping its acquisition timeout; add explicit owner/version state for half-open trials. Do not rely on a process-local lock or optional object cache. Transition history is a fixed 100-entry ring; per-family attempt rings hold 20 entries. Updates to observability rings may be best-effort under contention, but must not fail requests or silently promise a complete audit log.

The request id is minted in an early REST ingress hook (`rest_pre_dispatch`, before permission and route resolution) and echoed from a post-dispatch filter, so nonce failures, `manage_options` denials and unknown-route 404s carry the same id as a proxied request; tests cover 401/403/404 preflight responses and malformed ids, not only the proxied path. WP mints one UUIDv4 request id at ingress unless a bounded valid UUIDv4 was provided; invalid/oversized/newline values are replaced. It returns the id in the WP response header and envelopes, forwards it to the API, and makes it available before preflight returns. Each downstream attempt also has a bounded numeric attempt index. Diagnostic fields are allowlisted: route template (not query/body), method, configured host (no userinfo), time, outcome, status, duration, request id, attempt index, `sent`. Missing config/key and breaker rejection use `sent:false`/`not_sent`; network connect failures may be attempted but never received. Neither case promises an API record. Do not log tokens, headers, payloads, arbitrary URLs or raw upstream exception strings.

Extend existing `recognition/interface_adapters/http/middleware/correlation.py:CorrelationIdMiddleware`, its `CORRELATION_ID_HEADER/generate_correlation_id/CorrelationIdFilter`, and `api/logging_config.py:configure_logging`. `api/main.py` already registers this middleware. Adopt `X-ACX-Request-Id` as that single canonical external header and UUIDv4 as its wire format; update existing correlation fixtures rather than introduce an independent contextvar or dual-header shim. The existing internal log field remains `correlation_id`. Preserve exception-handler access to the id in request scope: the current middleware intentionally relies on request-task context isolation because an early finally-reset loses the id before outer 500 handling. Verify isolation and exception logging before changing lifetime behavior. Validate or replace incoming values and echo the id on success and error responses. Test concurrent requests, malformed IDs, exception paths and **actual access records**, not only one application logger. Use one request-scoped access record if the server's default access logger cannot carry the context; avoid duplicate access logs. Background/startup logs have no fabricated request id. Proxy client IP trust in DEMOHEAL-4 is allowlisted to actual reverse proxies, never `*`.

## Finite warming observation (slice 4)

Current producer: `scene/interface_adapters/http/routers/gpu.py:GpuStatusResponse/GpuStateResponse/GpuIntentStatus`. Existing fields include `snapshot_fresh`, `snapshot_age_seconds`, `server_time`, `gpu_state.state`, `.since`, `.intent`, `.intent_status`, `.intent_expires_at`, `.lease_expires_at`. Intent statuses are `none|pending|honoured|blocked_work_in_flight|stopped_with_work|expired`; there is no `active` value. Neither an intent TTL nor a lease expiry is a warm-up completion estimate. State values on the wire are lowercase.

Add a shared frontend policy helper (new `warmingDeadline.ts:deriveWarmingObservation`) used by both `useActivityStatus` and `useDescribeRunProgress`. Input is the current run and the existing GPU status query result; do not add a second polling loop. A live run's `phase=warming` can provisionally display warming while fetching evidence. Fresh `starting|warming` corroborates lifecycle work. START is demand-driven; operator intent is only an override. A fresh `stopped` state can precede reaper consumption of new demand and does not alone prove a stall. An absent/expired intent never contradicts warming. An explicit fresh start/demand failure may show stalled; otherwise retain provisional waiting with the finite observation deadline. An unexpired start/auto override can support waiting but is not required. A stop intent is not proof of successful shutdown. An absent/stale/failed snapshot is **unknown**, not stopped or healthy; show unknown with retry and retain a finite local observation deadline.

Initial proposed UI budget: 600 seconds + 30 seconds grace from the first warming observation for `(run_id,startup_id)`, shortened by trustworthy older phase-start evidence when available. This is a conservative product-policy fallback, not a backend SLO or proof the job failed. Export `WARMING_OBSERVATION_LIMIT_MS` and `WARMING_OBSERVATION_GRACE_MS` in one module; document them in `gpu-lifecycle.md`. Persist the first-observed timestamp in session storage under that key so poll, rerender, navigation and reload do not renew it; reconcile against server time/known elapsed age and expire records when the run becomes terminal. Storage failure remains a tested degraded case with the in-memory deadline; it cannot silently disable the watchdog. A new run/startup legitimately starts a new bound. Retry refetches the existing run and status; it never creates duplicate work or resets the deadline. Actual resumed progress/terminal state takes precedence over a stale stalled display. No backend lifecycle semantics change.

Fake-timer tests: fresh stopped/no intent remains bounded provisional waiting, demand-triggered start without an intent, explicit fresh start failure; valid pending start; stale/missing status; malformed or expired intent; within/exactly at/after deadline; repeated polls; component remount; terminal transition; new startup; refetch without renewal. Test lowercase wire fixtures and the no-evidence path. A UI deadline only says confirmation is overdue, not that execution failed.

## Reclaimer liveness and bounded recovery (slice 5)

Reuse `OutboxMaintenanceService::purge_terminal_rows` and `OutboxDrain::purge_terminal_rows_for_tenants`; centralize completion instrumentation so scheduled, drain and inline paths agree. Record per authenticated tenant last attempt, last successful batch, outcome, count and backlog indicator. Do not stamp success on scheduling, entry, `false`, exception or rollback. No history is `never_run`, not healthy. Expose scheduler mode/period: Action Scheduler one-hour single action, WP-cron daily fallback. Overdue = one effective period; freshness breach = two. Record the selected mode; do not assume a global daily period.

Run a bounded local purge attempt before the upstream sync attempt when overdue, so an unavailable API cannot prevent local reclamation. Acquisition is tenant-scoped atomic database ownership/CAS, with a finite expiry and owner-checked release. Reuse existing transactional/row-CAS protections. A get/set transient is not a correctness lock. Test two concurrent claimants, expired owner, former owner releasing late, transaction failure and separate tenants. Failure does not advance last-success and does not prevent a later retry; the scheduler path reschedules in a finally/recovery path even if the purge fails.

Initial inline bound: at most one 100-row batch per existing purge/reclaim category per sync invocation (no loop-until-empty), with no network I/O. Retain existing eligibility rules and test them; do not widen deletion merely to make old rows vanish. Report remaining eligible backlog and oldest age separately from successful-run liveness. If the batch cap is reached, the next sync is eligible to continue without waiting a whole period; avoid claiming a large backlog disappears in one sync. Database statement/lock timeout must be bounded by the existing connection configuration and included in verification. Scheduled work retains its separate batch policy. All operations use autoload-disabled bounded state and uninstall cleanup owned at integration.

### Frozen `reclaimer` wire object (DEMOHEAL-1-PR-02): S5A produces, S5B consumes

`SyncStatusResponse.reclaimer` is a required object once shipped. The SPA treats an absent object as `unknown`, never as healthy.

| field | type | semantics |
| --- | --- | --- |
| `state` | `never_run` \| `healthy` \| `overdue` \| `breach` | `overdue` = strictly more than one effective period since the last committed success; `breach` = strictly more than two. At exactly one or exactly two periods the lower state still holds. |
| `scheduler_mode` | `action_scheduler` \| `wp_cron` | recorded, never assumed |
| `effective_period_seconds` | int | 3600 for `action_scheduler`, 86400 for `wp_cron` |
| `last_attempt_at` | ISO-8601 UTC string \| null | |
| `last_success_at` | ISO-8601 UTC string \| null | advances ONLY on a committed batch |
| `last_outcome` | `success` \| `failed` \| `lock_contended` \| null | |
| `last_purged_count` | int \| null | rows |
| `backlog_remaining` | int \| null | eligible rows still present after the capped batch; null = not measured |
| `backlog_oldest_age_seconds` | int \| null | seconds |
| `batch_cap_reached` | bool | |

All values are per authenticated tenant. PHP uses class constants (the PHP >= 8.0 floor forbids native backed enums here); TS uses one `as const` object. The shared fixture is `apps/prototype-wp-alt-context/tests/fixtures/sync-status/reclaimer.json`, with one example object per `state`. Producer and consumer tests reject shape drift; no field is left silently optional.

**Presentation precedence.** The sync indicator renders the worse of upstream `sync_health` and the reclaimer state, never the better: `breach` forces an error presentation, `overdue` forces a warning, `never_run` and an absent/unparseable object force an `unknown` warning, and only `healthy` leaves upstream `sync_health` unchanged. A successful upstream sync therefore cannot mask a stale reclaimer. Every state pairs colour with an icon and text ([sr-004]).

A stopped host cannot display an alert. This scope exposes a freshness breach on the next status read; unattended external alert delivery remains deferred.
