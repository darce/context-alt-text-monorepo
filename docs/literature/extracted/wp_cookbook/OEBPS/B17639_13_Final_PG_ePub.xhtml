Chapter 13: Distributing Your Plugin on WordPress.org

Once you have a version of your new plugin that is ready to be distributed to the masses, you need to decide whether you will join the official WordPress repository or self-publish it.

In most cases, the preferred option is to add your new extension to the official WordPress plugin repository. The official repository includes free hosting, built-in notification of new updates, and a powerful search engine that users can access on WordPress.org or from the Plugins section of their website's administration pages. Other benefits of hosting on the official repository include download statistics and the creation of a free forum to facilitate user support.

To qualify for this hosting, your work must be free and open source. It must also comply with the GNU General Public License, Version 2 (also known as GPL v2), a common open source software license that WordPress itself uses. This includes any code you wrote, along with any third-party PHP or JavaScript libraries that you have included in your plugin. To learn more about the GPL v2 license, visit https://www.gnu.org/licenses/gpl-2.0.html. It is also possible to publish a plugin with premium features that require a one-time payment or recurring subscription on the official repository. However, the plugin must offer a reasonable amount of free features and you cannot transform these features into paid functions over time.

In comparison, self-hosting gives you full control over pricing, distribution license, and the general presentation of your work. That being said, it also makes it harder for people to find your plugin and requires you to implement a custom update notification mechanism. Alternatively, users can manually download updates to your work as they become available. There are several popular plugin digital marketplaces, such as CodeCanyon (https://codecanyon.net/), that can help alleviate some of these drawbacks. However, your work will still have less visibility than it would on the official repository.

Before making your plugin publicly available, you should also be sure that you are ready to deal with user feedback and questions. Once your creation is available for download, WordPress website administrators will quickly find it and install it. As they use it, they may find that your work covers most, but not all, of their needs. When this happens, you will start getting requests to add functionality. This interaction with users is usually a great experience that can bring new ideas to enhance your work. However, you must also be ready to accept criticism and invest time in fixing issues and implementing new features. You also need to consider the time that will be involved in testing your plugin against new versions of WordPress, which typically come out two to three times a year.

This chapter explains how to prepare your work to be uploaded to the official plugin repository. It covers applying for an account, the actual code submission using Subversion, and how to customize your plugin page to give it a unique look.

More specifically, we will discuss how to distribute your creations through the following topics:

  • Creating a README file for your plugin
  • Applying for your plugin to be hosted on WordPress.org
  • Uploading your plugin using Subversion
  • Providing plugin banner and thumbnail images

Creating a README file for your plugin

If you look at any plugins on the official WordPress repository, you will see that their page contains a lot of information. This includes a description of the extension, a list of frequently asked questions, and installation notes. As you may have noticed from the work that we have done so far, this data does not reside in the main plugin's code file. Instead, the official WordPress repository looks for this information in a specially formatted readme.txt file that needs to be included with the plugin.

Getting ready

You should have already followed the Updating page title to include custom post data using plugin filters recipe in Chapter 4, The Power of Custom Post Types, to have a starting point for this recipe. Alternatively, you can get the resulting code (ch4/ch4-book-reviews/ch4-book-reviews-v12.php) for that recipe from the book's GitHub page.

How to do it...

Follow these steps to create a readme.txt file for the Book Reviews plugin that we created in Chapter 4, The Power of Custom Post Types:

  1. Navigate to the ch4-book-reviews folder of your WordPress plugins directory.
  2. Create a new text file named readme.txt and open it in a code editor.
  3. Insert the following text in the file:

    === Book Reviews ===

    Contributors: ylefebvre

    Donate link: http://ylefebvre.ca/wordpress-plugins/book-reviews

    Tags: book, reviews

    Requires at least: 5.0

    Tested up to: 6.0

    Stable tag: 1.0

    License: GPLv2 or later

    License URI: https://www.gnu.org/licenses/gpl-2.0.html

    Create your own book review web site!

    == Description ==

    This plugin lets you add a book review system to your WordPress site. Using custom post types, administrators will be able to create and edit book reviews to be published on your site.

    == Installation ==

    1. Download the plugin.

    1. Upload the book-reviews folder to your site's wp-content/plugins directory.

    1. Activate the plugin in the WordPress Admin Panel.

    1. Start creating new book reviews!

    1. Use the [book-review-list] shortcode to list reviews on a page.

    == Changelog ==

    = 1.0 =

    * First version of the plugin.

    == Frequently Asked Questions ==

    There are currently no FAQs at this time.

    == Screenshots ==

    1. The review edition page

  4. Save and close the text file.
  5. Navigate to the Book Reviews section of the WordPress administration section of your development site and edit one of your entries.
  6. Take a screenshot of the interface using a third-party screen capture tool or your operating system's built-in function.
  7. Save the resulting image as screenshot-1.jpg in the plugin directory.

How it works...

The readme.txt file uses a wiki-like syntax, with the number of equal signs (=) indicating the level of each section header. The first and most important section is the header, which contains important information. This data includes the plugin's name, the author's WordPress.org username, donation link, search tags, supported versions, and stable Subversion code tag, along with a one-line description of its functionality. This last item will always be visible as users navigate through your plugin's pages.

The initial header is followed by multiple sections, which correspond to the various sections that appear within a plugin's display pages. More specifically, these sections contain a complete description of the extension's capability and a step-by-step guide to installing and using your work. They also contain a change log containing a list of all the versions with a summary of changes for each of them, frequently asked questions, and screenshots. It is also possible for plugin authors to create their own arbitrary sections using the same syntax.

As with the standard wiki syntax, the repeating 1. in front of each installation step will be converted to incrementing values when they are displayed on the plugin's page. If screenshots are listed in the readme.txt file, the WordPress.org website will search for files whose names start with the keyword screenshot-, followed by a number. These images will be displayed in the screenshot section using their associated text as a legend. When taking screenshots of your plugin in action, make sure that they are clear and meaningful, as visitors will often decide whether or not they will download your creations based on these images.

You can find more details about the readme.txt file format in the WordPress.org plugin handbook (https://developer.wordpress.org/plugins/plugin-basics/header-requirements/).

There's more...

Let's take a closer look at the Subversion Stable tag property that is specified as part of the header information.

Releasing plugin versions using tags

Tags are a Subversion concept that allows developers to identify a group of file revisions at a specific point in time and label them with a name. This tag is used to specify the version of your plugin that WordPress.org visitors will be able to download. We specified 1.0 in this recipe, for the first version of our plugin. As you release new versions of your plugin, you will always be creating new tags for your code and updating the value of the Stable tag field to match the new tag name.

In addition to keeping your work organized, working with tags allows you to commit partially implemented new plugin features to your repository without users getting access to them. When your new features are ready, create a new tag and update the Stable tag to release your new work. It's also interesting to know that every version identified with a tag can be downloaded from the Advanced View section of your plugin page on the official repository. This makes it easy for users to roll back to a previous version if issues come up after an update. It also allows them to download an unreleased version of the plugin so they can test updates before you make them available publicly.

Applying for your plugin to be hosted on WordPress.org

After creating proper documentation for your creation, the next step toward its publication on the official plugin repository is to apply for hosting. This is simply done by submitting a request form in the Developer Center section on WordPress.org.

How to do it...

Follow these steps to apply for plugin hosting on the official WordPress plugin repository:

  1. Create a zip archive containing your entire plugin directory, including the readme.txt file created in the previous recipe.
  2. Visit the https://wordpress.org/plugins/developers/add/ website and log in using the link in the top-right corner of the page or create a new account if you don't have one yet.
  3. Select your ZIP file and upload it to the site.

How it works...

Plugin submission is a fairly simple process, giving developers access to a Subversion repository that they can use to upload their work and share it with the community.

Before submitting your plugin, you should search through existing plugins to be sure that you have not selected a name that already exists in the repository. If your selected name is already taken, your request will be turned down immediately. You can search using the plugin repository's search engine, as well as trying to access addresses based on your plugin name. For example, following our Book Reviews plugin example, you could check to see if the address https://wordpress.org/plugins/book-reviews exists.

It should be noted that your plugin needs to be functional when you apply to be listed on the repository. Once your plugin has been approved, you will get access to a hosted Subversion version control repository. This tool will allow you to easily keep backups of all the versions of your work during development and easily publish it. If you work on a plugin with one or more people, this infrastructure will make it very easy to exchange code between all contributors.

Uploading your plugin using Subversion

Using Subversion in the recipes of Chapter 1, Preparing a Local Development Environment might have seemed like overkill when you were working on a plugin locally. However, you will see that this knowledge will be very handy once your hosting request has been approved by the WordPress plugins team, as the system's backend relies on that version control system.

Getting ready

You should have already followed the Applying for your plugin to be hosted on WordPress.org recipe to have an approved repository on the official website. You should have also installed a Subversion client as shown in the Creating a local Subversion repository recipe in Chapter 1, Preparing a Local Development Environment. Finally, you should have plugin files ready for upload.

How to do it...

Follow these steps to submit your creation to the WordPress.org website once a repository has been created for you:

  1. Open Command Prompt or Terminal and navigate to a work directory on your computer.
  2. Check out your plugin's repository with the following command. You should use the address of your new repository, as indicated in your hosting approval email, for example:

    svn checkout http://plugins.svn.wordpress.org/book-reviews

    Note

    Calling the checkout command creates a directory whose name matches the last section of the repository URL (book-reviews in this case). This new directory contains three new empty folders: branches, tags, and trunk, reflecting your new plugin repository structure.

Figure 13.1 – Newly checked out empty plugin repository

  1. Copy your plugin's files to the trunk folder of the resulting directory structure if it is empty. If the directory contains the initial files you submitted with your plugin application, update them if you made any changes since you applied.
  2. If you added new files, add them using the svn add command.
  3. If you added new files or updated them, commit your plugin files with the svn commit command:

    svn commit -m "1.0 - First public version"

  4. When prompted for authentication, use your WordPress.org username and password.

    Note

    After committing your files, you will receive an email from the WordPress repository confirming that they have been uploaded. The email also contains information on all changes that were made to each file.

  5. Back in Command Prompt or Terminal, use the following command to tag the files that are currently in your trunk directory. The 1.0 number should match the stable tag number specified in the readme.txt file, for example:

    svn copy https://plugins.svn.wordpress.org/book-reviews/trunk/ https://plugins.svn.wordpress.org/book-reviews/tags/1.0 -m "1.0 Release"

Figure 13.2 – Plugin repository page after commit

Once the commit and tag creation process are completed, you will be able to visit your plugin's page and download it. For our example, the Book Reviews plugin, the address of the page would be https://wordpress.org/plugins/book-reviews.

How it works...

The official WordPress plugin repository uses Subversion to manage all code files, provide version control services to developers, and find information to populate the extension's page. When your new repository is created, it contains three main directories: trunk, tags, and branches.

The trunk directory is usually the main location where you place the latest version of your plugin files. Following the steps in the recipe, we copy our files to this location and commit them to the server. Once uploaded, the WordPress.org servers take care of creating a zipped copy of your work for users to install on their site.

The tags directory is designed to hold pointers to various versions of your creation over time, as discussed in the Creating a README file for your plugin recipe. Used in conjunction with the Stable tag field of your plugin's readme.txt file, tags allow you to offer users a working plugin version while you commit and test new work to the trunk. New tags are created using the svn copy command. The branches directory has a similar function to tags but is more focused on the creation of alternate versions of plugins or in-development revisions that include specific functionality.

There's more...

If you want to execute your plugin's code in a local WordPress development installation as you are writing it, the following section shows you how to manage your code.

Checking out plugins to your development installation

When checking out the complete plugin repository folder, you end up with a structure that cannot be executed directly in WordPress for testing and development purposes. Instead of checking out the entire directory structure, you can limit your selection to the trunk directory. This will only copy the contents of that specific folder to your development environment.

Providing plugin banner and thumbnail images

While the plugin listing that we put in place by creating a readme.txt file is perfectly functional, it does not really stand out among the sea of extensions that are available on the website. Thankfully, WordPress.org introduced a mechanism allowing plugin developers to add a banner image to their listing. This image can be anything from a simple picture to a complex graphic to advertise your creation.

Getting ready

You should have already followed the Applying for your plugin to be hosted on wordpress.org and Uploading your plugin using Subversion recipes. You should have an approved repository on the official repository and plugin files uploaded to the server.

How to do it...

Follow these steps to prepare images for your plugin and learn how to upload them to your repository:

  1. Navigate to the plugin repository folder created in the previous recipe.
  2. Create a new directory called assets, next to the branches, tags, and trunk folders.
  3. Create a new image that is exactly 772 x 250 pixels.
  4. Save the image as a PNG file with the name banner-772x250.png and save it to the newly created assets directory.
  5. Create smaller images that are exactly 256 x 256 pixels and 128 x 128 pixels in size and name the files icon-256x256.png and icon-128x128.png, respectively. The larger icon should be a higher-resolution version of the exact content of the smaller one. It will be used to replace the smaller one on high DPI displays.
  6. Open Command Prompt or Terminal and navigate to the work directory created in the previous recipe.
  7. Use the svn add command to identify the new assets folder and all of the files it contains to be added to the repository:

    svn add assets

  8. Commit your new files to your repository with the svn commit command:

    svn commit -m "Graphical assets for plugin page"

  9. Visit your plugin's page on WordPress.org to see the images in place:

Figure 13.3 – Graphically-improved plugin repository page

  1. Search for your plugin through the https://wordpress.org/plugins page or the Add New section of the Plugins management interface of WordPress.

Figure 13.4 – Book review plugin appearing in search results

As seen in Figure 13.4, the icon and short plugin description that we provided appear in these results.

How it works...

When files are uploaded to the plugin repositories, the WordPress.org website checks for the presence of specific image files with specific names in a specific directory for the plugin banner and icon. If these files are present, it changes the layout of the plugin page to incorporate the images. It is important to respect the image format and specified dimensions when creating a plugin banner and icons to make sure that they are displayed properly on the website.
