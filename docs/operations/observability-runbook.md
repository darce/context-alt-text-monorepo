# Observability Runbook

Operator-facing runbook for the prototype description service. It names the
probes, the log fields, and the metric queries an on-call engineer needs to
diagnose a failed sync or a degraded deploy without reading source code.

The service exposes three categories of observability surface, all reachable
on the running container:

| Surface | Path | Auth | Purpose |
| --- | --- | --- | --- |
| Liveness | `GET /health` | none | Caddy active probe at 10s. Process is up. No dependencies. |
| Readiness | `GET /ready` | none | DB reachable, breaker closed, InsightFace model bundle on disk. |
| Operator diagnostic | `GET /health/detailed` | API key | Full pool stats, breaker state, model-cache inventory. |
| Metrics | `GET /metrics` | API key | Prometheus exposition for the host-local scraper. |
| Logs | stdout | n/a | Structured JSON, one object per record, correlation-id stamped. |

Default local port is `8000`. The `Authorization: Bearer <key>` header (or
`X-Api-Key`) must be set for the auth-gated surfaces — even the host-local
Prometheus scraper is not exempt.

## Health and Readiness

Use the probes during a deploy or when a pod looks wedged.

```bash
# Liveness — cheap, no I/O. If this fails the process is wedged or crashed.
curl -sS http://localhost:8000/health

# Readiness — runs DB + breaker + model-cache checks. A 503 here means
# traffic should be pulled from the pod; the body names the failing probe.
curl -sS -o /tmp/ready.json -w '%{http_code}\n' http://localhost:8000/ready
jq '.checks[] | select(.status != "ok")' /tmp/ready.json

# Operator diagnostic — pool stats (business + observability), breaker
# state, on-disk model inventory. Requires an API key.
curl -sS -H "Authorization: Bearer $API_KEY" \
  http://localhost:8000/health/detailed | jq .
```

`aggregate_status` rolls the three readiness probes up: any `unhealthy`
flips the endpoint to 503; `degraded` stays 200 so degraded-but-serving
pods keep carrying traffic.

## Structured Logs

Every log record is a single-line JSON object. Grep by `correlation_id` to
follow one request through the stack; grep by `logger` to narrow to a
subsystem.

Key fields:

- `correlation_id` — `req-<uuid7>` from the `X-Request-ID` header, or a
  fresh id generated by `CorrelationIdMiddleware`. The same id is echoed
  back on the response header so clients can correlate their own logs.
- `level`, `timestamp`, `message`, `logger` — standard.
- `correlation_source` — `api` for HTTP-origin requests, `worker` for
  background jobs.

Example: pull every record for one failing request.

```bash
kubectl logs deploy/description-service --since=30m \
  | jq -c 'select(.correlation_id == "req-01HXYZ...")'
```

## Request Metrics

The `/metrics` route exposes Prometheus exposition. Percentiles are not
pre-computed — `/metrics` emits histogram buckets and PromQL derives
quantiles downstream via `histogram_quantile()`. Pre-computed percentiles
would require summary metrics, which lose aggregability across replicas.

### Exposed series

- `http_request_duration_seconds` — Histogram. Labels: `method`, `path`,
  `status`. Buckets: `0.25, 0.5, 1, 2, 5, 10, 30, 60, +Inf`.
- `http_requests_total` — Counter. Labels: `method`, `status_class`
  (`2xx`, `4xx`, `5xx`, …).
- `http_requests_in_flight` — Gauge. Untagged.

The `path` label resolves to the FastAPI route template
(`/clusters/{cluster_id}`), not the raw URL, so two requests to different
cluster ids collapse to the same label. This keeps histogram cardinality
bounded at the number of registered routes.

### PromQL: quantiles from the histogram

```promql
# P50, P95, P99 request latency over the last 5 minutes, per route.
histogram_quantile(
  0.50,
  sum by (le, path) (rate(http_request_duration_seconds_bucket[5m]))
)

histogram_quantile(
  0.95,
  sum by (le, path) (rate(http_request_duration_seconds_bucket[5m]))
)

histogram_quantile(
  0.99,
  sum by (le, path) (rate(http_request_duration_seconds_bucket[5m]))
)
```

### PromQL: error rate and saturation

```promql
# 5xx rate per second, last 5 minutes.
sum(rate(http_requests_total{status_class="5xx"}[5m]))

# Fraction of requests that are 5xx.
sum(rate(http_requests_total{status_class="5xx"}[5m]))
  /
sum(rate(http_requests_total[5m]))

# In-flight saturation — sustained high values mean the event loop is
# saturated or downstream deps are slow.
max_over_time(http_requests_in_flight[5m])
```

### Known limits

- Histogram buckets are tuned for the description-service's observed
  1–30s distribution. Revisit after one day of staging data.
- Recording on response-complete introduces coordinated-omission bias —
  tail numbers are lower bounds, not worst-case.
- API and VLM-worker pools share one process today. When a VLM worker
  lands on the OCI A1 host, split the DB pools so a pathological batch
  cannot exhaust the pool serving `/v1/describe` (PA-11, bulkhead).

## Probe Integration

### Caddy `reverse_proxy` health check

Caddy's active upstream health check points at `/ready` so an unhealthy pod is
pulled from the load-balancer pool without waiting for a 5xx on real traffic.
Use `/ready` — not `/health` — because `/ready` rolls up the dependency
probes; `/health` is liveness-only and would keep a DB-less pod in rotation.

```caddyfile
reverse_proxy description-service:8000 {
    health_uri       /ready
    health_interval  10s
    health_timeout   2s
    health_status    2xx
}
```

### Prometheus Blackbox Exporter

Blackbox hits `/health` for the cheap liveness probe — no auth, no I/O — and
alerts on failure independently of the scrape-based metrics path.

```yaml
# blackbox.yml
modules:
  http_2xx_health:
    prober: http
    timeout: 5s
    http:
      valid_status_codes: [200]
      method: GET
      preferred_ip_protocol: ip4

# prometheus.yml
scrape_configs:
  - job_name: blackbox-description-service
    metrics_path: /probe
    params:
      module: [http_2xx_health]
      target: [http://description-service:8000/health]
    static_configs:
      - targets: [blackbox-exporter:9115]
```

## Tracing a Request by Correlation ID

Every request is stamped with a correlation id from `X-Request-ID`; if the
client omits the header, `CorrelationIdMiddleware` synthesises a new
`req-<uuid7>` and echoes it back on the response. That id is the thread to
pull through the stack.

1. Client (or the browser devtools network tab) reports the
   `X-Request-ID` response header for the failing call.
2. Grep stdout logs for that id — every log record emitted on behalf of
   that request carries it:
   ```bash
   jq -c 'select(.correlation_id == "req-01HXYZ...")' < logs.ndjson
   ```
3. If the request talked to the DB, the worker log line for the matching
   scan-queue row carries `correlation_source=api` and the same id.
4. Cross-check the `/metrics` series: the request should have contributed
   one observation to `http_request_duration_seconds_bucket` under the
   resolved route template and one counter increment on
   `http_requests_total` with the matching `status_class`.

## Common Failures

### `/ready` is 503 with `database: connection_unavailable`

The observability session dep yielded `None` — the pool checkout failed
or was blocked by the circuit breaker. Check `/health/detailed` for the
live pool stats; if the breaker is `open`, that's the primary signal and
the DB probe being red is a consequence.

### `/ready` is 503 with `breaker: open`

The session-dependency circuit breaker tripped after repeated pool
checkout failures. It will flip to `half_open` after the configured
cool-off; watch `breaker_state` on `/health/detailed`. If the breaker
stays open, the DB is genuinely unreachable — check the managed Postgres
instance.

### `/ready` is 503 with `model_cache: bundle_missing`

The InsightFace `buffalo_l` bundle is not on disk at the configured
`cache_dir`. Either the cache volume didn't mount or the first-run model
download was blocked. `health_detailed.model_cache.bundle_files` names
the exact on-disk count.

### `http_requests_in_flight` climbs without draining

Saturation. Usually one of: a downstream dep (DB, VLM worker) is slow,
the event loop is blocked on sync work inside a handler, or the pool is
exhausted. Cross-reference `http_request_duration_seconds` tail buckets
per route — the offender will show a spike under its own `path` label.

### `/metrics` returns 401

The scraper is missing an API key. Local Prometheus must carry the same
`Authorization` / `X-Api-Key` header the operators use. Mounting
`/metrics` as an ASGI sub-app would bypass `require_auth` — don't; the
route is registered as a FastAPI route specifically so auth runs.
