# DEMOHEAL-1 independent planning review

Frozen snapshot reviewed: `2026-09-21` planning set at the lane baseline. Review lenses applied: `GRPH-01`, `GRPH-09`, `GRPH-31`, `GRPH-32`, Release It! §5.1–5.5, DDIA chapters 8/11/12, `OBS-08`, `SEC-01`, and verification/`rg-006`.

## Findings

**DEMOHEAL-1-PR-01 — HIGH — `docs/workbay/contracts/security.md:350-378` (also `docs/tasks/v0.5.0/DEMOHEAL-1-truthful-service-state-and-reclaimer-liveness-task-plan.md:104,122`) — Canon: `SEC-01`, `GRPH-32`.** The proposed `ConnectionController` creates a second probe contract without reconciling the existing authoritative `POST /acx/v1/settings/test`: `SettingsPage` still calls the localized `settingsTest` endpoint, whose closed `TestConnectionResponse` probes authenticated `/recognition/health/pool`, while the new draft probes `/health`, GPU status, and retention policy and says nothing about migrating or retiring the old route. With an invalid API key, the existing endpoint returns `invalid_key`, but an implementation following the new draft can treat public `/health` as success or return a different partial envelope, so the Settings UI publishes conflicting connection truth; it also violates the existing explicit ban on anonymous `/health` probes. The smallest fix is to choose one surface, update producer, consumer, localization, and `security.md` in the same slice, preserve the existing authenticated outcome taxonomy (or specify a versioned replacement/deprecation), and add an invalid-key/no-anonymous-health parity test.

**DEMOHEAL-1-PR-02 — HIGH — `docs/scopes/demoheal-operability-contract-draft.md:43-47` (also `docs/tasks/v0.5.0/DEMOHEAL-1-truthful-service-state-and-reclaimer-liveness-task-plan.md:127,180-181`) — Canon: `GRPH-32`, `OBS-08`, `DDIA-11/12`.** The reclaimer status is described only as “last attempt, last successful batch, outcome, count and backlog indicator”; no exact JSON shape, field names, nullability, timestamp/count units, version/unknown semantics, or rule for folding a freshness breach into the existing `sync_health` is frozen, while the current `SyncStatusResponse` fields are optional and `fetchSyncStatus` is a generic cast. If the PHP producer emits a flat `last_successful_at: null` and the TS lane expects a nested `reclaimer.last_successful_batch`, or if upstream sync is successful while reclaimer history is `never_run`, the renderer can omit the alert and the existing `SyncStatusIndicator` can remain green. Freeze one fixture/schema with explicit `never_run|healthy|stale|failed` semantics and `sync_health` presentation precedence, then make producer/consumer tests reject shape drift rather than leaving fields optional.

**DEMOHEAL-1-PR-03 — MEDIUM — `docs/scopes/demoheal-operability-contract-draft.md:47` (current loop/tenant discovery in `apps/prototype-wp-alt-context/src/sovereign/sync/class-outbox-maintenance-service.php:345-470` and `apps/prototype-wp-alt-context/src/sovereign/sync/class-outbox-drain.php:368-380`) — Canon: Release It! §5.5.** The “one 100-row batch per category” inline promise does not define a bounded execution entry point, yet the shared service currently loops up to `MAX_PURGE_BATCH_ITERATIONS` for each category and the scheduled drain loads every distinct tenant into one array before iterating it. With 21 full batches for one tenant, or 100,000 tenants each holding one terminal row, an overdue sync can hold database locks and exhaust the request/scheduler budget despite the stated cap. Add an explicit inline mode/limit propagated to every batch helper, and page/cursor the scheduled tenant set with a bounded continuation action; prove both modes with 21-batch and large-tenant tests.

**DEMOHEAL-1-PR-04 — MEDIUM — `docs/scopes/demoheal-operability-contract-draft.md:45` (also `docs/tasks/v0.5.0/DEMOHEAL-1-truthful-service-state-and-reclaimer-liveness-task-plan.md:180,224,247`) — Canon: `DDIA-08`.** “Atomic ownership/CAS, finite expiry and owner-checked release” is not fencing: worker A can acquire a tenant lease, pause past expiry, worker B can acquire and commit a newer purge/status stamp, and A can resume and write its older outcome/backlog because the plan does not require a lease epoch on every mutation. The visible result can therefore regress to an old backlog or false success even though the newer owner completed, and a wall-clock comparison can be wrong under host skew. Use database-authoritative time plus a monotonically increasing fencing token returned by acquisition; require that token in purge/status writes and release, and test pause-after-expiry, clock skew, and late completion against a new owner.

**DEMOHEAL-1-PR-05 — MEDIUM — `docs/scopes/demoheal-operability-contract-draft.md:19-23` — Canon: `OBS-08`.** `GET /connection` is specified as cached diagnostics, but the planning set never defines a cache TTL, target/configuration fingerprint, invalidation on URL/key/tenant changes, or a `never_checked`/stale state. If a site has a cached successful check for API A and its URL changes to API B (or a fresh site has no check), the GET can return the old healthy result and the Settings card can read green for a target that never ran. Store the effective-target/config epoch with each result, invalidate or mark stale on changes, and allow green only for a fresh result matching the current target; cover first read and reconfiguration tests.

**DEMOHEAL-1-PR-06 — MEDIUM — `docs/scopes/demoheal-operability-contract-draft.md:23` — Canon: Release It! §5.3.** “Coalesce simultaneous checks per site” has no atomic single-flight mechanism, global/per-site concurrency cap, or fail-fast bulkhead. If 50 admin tabs POST checks concurrently, each can launch the three probes, producing up to 150 outbound requests and consuming WP/API workers needed by retention and sync; the diagnostics surface then reports timeouts while starving the normal product traffic it is meant to diagnose. Specify a short-lived database/cache single-flight lease plus a bounded per-site/global probe pool, return local `not_sent` on saturation, and test contention alongside a normal proxy request.

**DEMOHEAL-1-PR-07 — MEDIUM — `docs/scopes/demoheal-operability-contract-draft.md:27-29` (plan surface list at `docs/tasks/v0.5.0/DEMOHEAL-1-truthful-service-state-and-reclaimer-liveness-task-plan.md:122`) — Canon: `OBS-03`, `SEC-01`.** The contract requires a request id “before preflight returns”, but the planned WP changes name only the controller/proxy and provide no early REST ingress hook or preflight proof. A bad nonce, permission denial, or unknown REST route is rejected before `ConnectionController`/`proxy_request` runs, so that response has no generated/validated ID and cannot be joined to WP logs, contrary to the stated response-header guarantee. Specify the early request hook and post-dispatch echo path (including 401/403/404), then test malformed IDs and permission/route preflight responses rather than only proxied requests.

**DEMOHEAL-1-PR-08 — MEDIUM — `docs/scopes/next-wave-gpu-ui-fir512-dag.json:112-114,250-336` — Canon: `GRPH-31`, `GRPH-32`.** The machine graph includes the FIR nodes `F1a` through `F6` and `Q`, but `GATE` consumes only `I`; there is no edge from `F6`/`Q` (or a FIR gate) into the integration gate, and the recorded critical path is UI-only. If F1e or the F6 rollback rehearsal fails while S1–S5 and `I` pass, the declared `GATE` can still receive “integrated behavior and receipts” and return a green next-wave review with the FIR work unconsumed. Add `F6`/`Q` to an explicit FIR acceptance gate and join it to `GATE`, or document a separate FIR gate and remove the misleading shared gate/path analysis.

**DEMOHEAL-1-PR-09 — MEDIUM — `docs/tasks/v0.5.0/DEMOHEAL-1-truthful-service-state-and-reclaimer-liveness-task-plan.md:100,140,157` — Canon: `rg-006`, `GRPH-32`.** The route freshness proof says to compare a stale fixture, while the export target is described as running the exporter with the tracked PHP fixture as its explicit output; if CI runs that target before the pytest proof, a newly added API route overwrites the stale fixture and the comparison passes. The smallest fix is a non-mutating `--check`/temporary-output path used by the test and a separate explicit fixture-update command, with a test that edits a copy of the fixture and observes failure.

**DEMOHEAL-1-PR-10 — LOW — `docs/tasks/v0.5.0/DEMOHEAL-1-truthful-service-state-and-reclaimer-liveness-task-plan.md:147` — Canon: `rg-006`.** The Integration proof lists “service ruff” without an executable command, working directory, or changed-path scope, unlike the concrete Composer and npm commands. An integrator can run the two concrete commands, omit Python lint entirely, and mark a new syntax/import or ruff regression in `api/main.py` as integrated. State the exact command (for example, `make lint` from `apps/prototype-description-service`, or the repository’s resolved ratchet invocation) and the files/receipt it must cover.

## Checked and found sound

- The DEMOHEAL task DAG’s declared implementation dependencies are acyclic by inspection of `docs/scopes/demoheal-dependency-dag.json:58-170`; its stated UI critical path matches the listed S1A→S1B→S2A→S2B→S3C→INTEGRATE→GATE chain. Resource conflicts and their integration resolutions are explicitly listed at `:227-258`.
- The named existing PHP, TypeScript, Python, GPU-router, sync, and test anchors were confirmed with `test -f` and targeted `rg -n`; the new exporter, manifest test, connection controller/card, and warming-deadline test paths are absent as the plan labels them new. The PHP and Vitest test runners are configured (`phpunit.xml.dist:6-10`, `vite.config.ts:25-36`), and the service’s explicit pytest paths collect the named files when passed directly (`pyproject.toml:320-340`).
- The correlation plan points at the real shared middleware: `correlation.py` defines the current middleware/filter/generator, `api/main.py:569-584` registers it, and the request-id work is correctly scoped to extending that context rather than adding a second system.
- The existing transport safety boundary is present: `RecognitionEndpointResolver` rejects non-loopback HTTP and `RecognitionTransport` forces `redirection=0` and uses the safe remote transport for non-loopback hosts (`class-recognition-endpoint-resolver.php:229-267`, `class-recognition-transport.php:31-61`). The existing settings routes also use `manage_options` permission callbacks (`class-settings-controller.php:94-121`); these areas were not independently reported as defects.
- Existing purge completion is transactional and returns `false` on transaction/error results (`class-outbox-maintenance-service.php:108-188`), and current scheduler behavior is visibly Action Scheduler first with daily WP-Cron fallback (`:191-220`); the findings above concern the missing new bounds/state contract around those anchors.
