# Plan: v0.2 -- Sovereign Outbox and Operation Tracking

## Problem Statement
The current sovereign architecture projects clusters but lacks a reliable way to track pending local mutations (e.g., renames, merges) that need to be synced back to the backend. This can lead to lost curation data if the browser session is closed before proxy calls complete.

## Workflow Principles
- **Local-First Writes**: Every curation action must be recorded in the outbox before attempting a network call.
- **Idempotent Retries**: Outbox operations must be safe to replay against the backend.

## Terminology
- **Outbox**: A database table in WordPress that queues pending state synchronization tasks.
- **Operation ID**: A unique identifier for a specific curation event used to prevent duplicate processing.

## Current State Analysis
- Curation mutations currently attempt a direct dual-write (local + proxy fallback).
- There is no background retry mechanism.
- Drift is possible if the backend write fails and the client session ends.

## Proposed Solution
Introduce an outbox table (`wp_acx_cluster_operations`) to queue local mutations and track their synchronization status with the remote service, enabling background retries and audit logging.

## Patterns to Follow

### [Outbox Ingestion Pattern]

```php
// Example insertion using wpdb
$wpdb->insert(
    $wpdb->prefix . 'acx_cluster_operations',
    [
        'operation_type' => 'rename',
        'payload_json'   => json_encode($payload),
        'status'         => 'pending',
    ]
);
```
