# OCIRV-1 adversarial operability review

**OCIRV1-RB-01 — high.** The rotation's first OCIR proof invokes `docker login` directly rather than through the watchdog (`scripts/deploy/ocir-token-rotate.sh:239-243`), even though `run_bounded` exists at lines 132-160. With a valid username/token and a registry connection that completes TCP setup but stops responding, `scripts/deploy/ocir-token-rotate.sh` can wait for Docker's transport timeout instead of `ACX_VAULT_FETCH_TIMEOUT`; the operator is stuck before the new token is stored and receives no bounded failure classification.

**OCIRV1-RB-02 — high.** Both push modes are unbounded: `_push_ref` runs a bare remote `ssh ... docker push` or local `docker push` with no wall-clock deadline, SSH keepalive, or stall detector (`scripts/deploy/recognition-service.sh:794-804`). If OCIR stops acknowledging a layer after the connection is established, a manual deploy can hang indefinitely (the Actions job's 45-minute ceiling only bounds CI), monopolizing the serialized environment deploy lane and leaving the operator unable to tell whether the registry accepted the tag.

**OCIRV1-RB-03 — medium.** The advertised `--readable-timeout` bounds only the post-write Secrets data-plane read; KMS/Vault discovery and the mutating `create_secret`/`update_secret` calls use SDK defaults and sit outside that deadline (`scripts/deploy/_vault_put_secret.py:243-247`, `scripts/deploy/_vault_put_secret.py:254-271`, versus the explicitly bounded client at lines 280-310). With `--readable-timeout 5`, slow `get_vault`, paginated list, and update calls can each consume their own SDK timeout before the five-second budget even starts; if `update_secret` is accepted and its response is lost, killing/re-running can submit another version without knowing which write won.

**OCIRV1-RB-04 — medium.** Post-write VM verification gives SSH only `ConnectTimeout=5` and no `ServerAliveInterval`/`ServerAliveCountMax` or outer deadline (`scripts/deploy/ocir-token-rotate.sh:293-301`). A route drop after SSH establishes but before the remote program finishes can therefore hang after the new token is already durable and the laptop leg has run, leaving the operator without a terminal success/failure result for the production consumer.

**OCIRV1-RB-05 — low.** Vault read-back retries use the same deterministic 1.0×1.5 sequence capped at five seconds for every caller and add no jitter (`scripts/deploy/_vault_put_secret.py:117-151`). During a Vault 503/propagation incident, simultaneous operator or automation retries align their requests and can amplify the unhealthy dependency instead of spreading load, contrary to the bounded-backoff-with-jitter recovery rule.

**OCIRV1-RB-06 — medium.** A rerun with byte-identical input is not idempotent: after locating an existing secret the helper always calls `update_secret` and creates a new version, without comparing the active value or attaching an idempotency/conditional-update token (`scripts/deploy/_vault_put_secret.py:254-272`). Re-running after a crash or lost response therefore accumulates indistinguishable duplicate versions; repeated recovery attempts consume version history and make it harder to identify the version that actually became active.

**OCIRV1-RB-07 — medium.** Bootstrap rotation writes the token and username as two independent commits, token first, with no compensating rollback (`scripts/deploy/ocir-token-rotate.sh:251-258`). If `--set-username new-user` stores the new token and the second helper call times out or fails, Vault serves `old-user` plus `new-token`, so every fresh laptop/VM login fails while currently running services continue; the runbook acknowledges the mismatch and says to retry (`infra/oci/vault-instance-principal-runbook.md:191-197`), but recovery still requires retaining the once-shown token or minting another and repeating a non-atomic operation.

**OCIRV1-RB-08 — high.** In the default remote-build path, `docker build` overwrites the VM's environment tag with the candidate (`scripts/deploy/recognition-service.sh:781-790`) before `promote_gate` calls `preserve_rollback_tag` (`scripts/deploy/recognition-service.sh:833-840`), and `do_deploy` orders those operations exactly that way (`scripts/deploy/recognition-service.sh:1476-1486`). For prod currently serving image A, building B as `:latest` means the alleged `rollback-<id>` points to B; if B then fails boot smoke, prod keeps serving A but the recovery tag created for this attempt has already lost A.

**OCIRV1-RB-09 — medium.** Rollback preservation is both host-local and explicitly best-effort: it runs `docker tag` on the VM, never pushes the rollback reference to OCIR, and continues on inspect/tag failure (`scripts/deploy/recognition-service.sh:1223-1240`). If the VM is replaced, its Docker cache is pruned, or the tag operation fails immediately before a bad prod restart, the advertised `rollback-<id>` is unavailable from the registry and the operator must reconstruct a prior SHA by hand during the outage.

**OCIRV1-RB-10 — high.** After the mutable env tag is pushed, `do_restart` pulls it before running the blob repair (`scripts/deploy/recognition-service.sh:1425-1439`), while its caller handles any failure only by restoring `ACX_IMAGE_REPO`, not the registry or VM tag (`scripts/deploy/recognition-service.sh:1487-1495`). If the pull of B succeeds and the repair then fails, A remains serving but the VM's `:latest` now names B; a later systemd restart or host reboot activates B outside the smoke/verification transaction, turning a contained deploy failure into a latent production rollout.

**OCIRV1-RB-11 — high.** Cutover is an in-place `systemctl restart` of the only environment unit (`scripts/deploy/recognition-service.sh:1440-1444`), and a failed post-restart health check merely exits without restoring or restarting the prior image (`scripts/deploy/recognition-service.sh:1498-1507`). An image that passes the isolated smoke but fails against live Vault, database, mounts, or environment configuration stops the currently serving process, fails to become healthy, and remains deployed until manual intervention; this is stop-then-start with no automatic rollback, not additive-then-flip containment.

**OCIRV1-RB-13 — low.** Verification adds a fixed five-second delay before its first request and also sleeps after terminal failures on the final attempt (`scripts/deploy/recognition-service.sh:1498-1502`, `scripts/deploy/recognition-service.sh:1713-1719`, `scripts/deploy/recognition-service.sh:1725-1728`, `scripts/deploy/recognition-service.sh:1776-1779`). With `ACX_VERIFY_ATTEMPTS=1`, an immediately observable 401/connection refusal or SHA mismatch still costs ten avoidable seconds before failure is returned, and repeated attempts use fixed, non-jittered spacing.

**OCIRV1-RB-14 — medium.** The emergency prod rollback examples do not run as written: both place `CONFIRM=PROMOTE` only in trailing comments rather than the command environment (`docs/runbooks/deploy-recognition-cicd.md:125-134`), while the implementation requires the variable for prod (`scripts/deploy/recognition-service.sh:1529-1535`). Copying either command during an outage therefore performs an SSH preflight and then refuses the rollback, wasting recovery time; the examples must prefix the command with `CONFIRM=PROMOTE`.

**OCIRV1-RB-15 — medium.** The OCI README says `make deploy-dev` is a local build and that remote build requires `REMOTE_BUILD=1` (`infra/oci/README.md:502-518`), but the Make target resolves an unset selector to `REMOTE_BUILD=1` (`mk/deploy.mk:111-118`), as confirmed by `make -n deploy-dev`. An operator following the documented local iteration path instead rsyncs, prunes, and builds on the multi-environment production VM, creating unexpected latency and blast radius on the serving host.

**OCIRV1-RB-16 — medium.** The same README still instructs operators to seed a persistent `~ubuntu/.docker/config.json` with interactive `docker login` as a remote-build prerequisite (`infra/oci/README.md:539-546`), but the deployed path ignores that cache and creates a private ephemeral Docker config populated from Vault (`scripts/deploy/recognition-service.sh:172-208`, `scripts/deploy/recognition-service.sh:514-527`). The documented command can succeed while the next deploy still fails because Vault/IAM is broken, sending a 3 a.m. operator down a remediation path that cannot affect the actual consumer.

**OCIRV1-RB-17 — medium.** `--readable-timeout 0` commits the Vault mutation and explicitly skips the matching-value read-back (`scripts/deploy/_vault_put_secret.py:274-279`), but the wrapper immediately performs a Vault-backed laptop login (`scripts/deploy/ocir-token-rotate.sh:280-287`). On a first create or slow version propagation, that login sees 404 or the old token and reports failure after the write was accepted—the exact race the readiness gate was added to prevent—so the documented zero-wait option produces an ambiguous partial-success state rather than a reliable fast mode.

**OCIRV1-RB-18 — medium.** All Make deploys default to building on the same VM that serves every environment (`mk/deploy.mk:111-141`); each run first prunes BuildKit state and then performs an unrestricted Docker build there (`scripts/deploy/recognition-service.sh:740-790`). A routine dev deploy with a large context can saturate CPU, disk I/O, or free space used by prod before any candidate gate runs—the README itself warns of the serving-traffic CPU spike (`infra/oci/README.md:548-555`)—so the blast radius of build failure/load is cross-environment rather than isolated to dev.
