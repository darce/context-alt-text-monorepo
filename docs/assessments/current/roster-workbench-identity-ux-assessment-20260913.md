# Roster + Workbench Identity Chip UX Assessment

> **Metadata**
>
> - **Date**: 2026-09-13
> - **Author**: Claude (Sonnet 5)
> - **Scope**: Workbench media-row identity chips (same-person dedup, avatar source) and six open roster UX questions
> - **Status**: Draft

## Summary

- Workbench media rows render one chip per distinct `cluster_id` (`groupIdentitiesByClusters`, `apps/prototype-wp-alt-context/js/admin/pages/workbench/identity-clusters/utils.ts:48-75`), so one person split across N unmerged/null-cluster identities on the same media item shows as N chips. This is a data-quality symptom (unmerged clusters or missing `cluster_id`) surfaced as a UI defect, not a grouping bug in the chip code itself.
- Each chip's avatar crops `cluster.members[0]` — the first identity **of this media item's own group**, not the cluster's designated representative (`IdentityClusterItem.tsx:79-105`, `ClusterPreview.tsx:25-52`). The payload (`DetectedIdentity`, `identity.ts:66-85`) carries no representative crop fields at all, so the frontend has nothing else to draw from.
- Roster already solves the "which face represents this person" problem correctly one screen over: `RosterEntriesTable.tsx:35-53` (`selectRepresentativeIdentity`) picks the cluster with the highest `identity_count` and uses its server-supplied `representative_identity`. The workbench chip should reuse that pattern, but the workbench payload shape doesn't carry the field.
- Merge is cluster-level only (`ClusterMergeService::merge_cluster`, `class-cluster-merge-service.php:62-207`); there is no person-level (`acx_persons`) merge, and `RosterEntryProjectionRepository::group_rows_by_normalized_name` (`class-roster-entry-projection-repository.php:115-161`) groups roster rows by normalized name string equality only — two same-named-but-differently-spelled persons stay separate rows with no merge affordance.
- Roster tags round-trip through `acx_persons`/`ClusterProjectionWriter`/`PersonResolutionService` and the roster UI's own client-side search filter (`RosterEntriesSection.tsx:107`), but no downstream consumer (export, caption generation, media search) was found — tags currently only filter the roster table itself.
- The needs-assignment rail cited in the brief is already retired (UXW2-4, `RosterZeroStateReachability.test.tsx`); Roster's zero state routes to the workbench queue instead. That part of the brief's premise is stale — flagged below, not re-litigated as a defect.

## Defect A: Workbench media row shows the same person as multiple identity chips

**Root cause.** `MediaSelectionRow` → `IdentityClusterList` → `groupIdentitiesByClusters` groups an item's identities by `identity.cluster_id ?? identity-<identity_id>` (`utils.ts:48-75`, confirmed via codemap `search_graph`). One chip renders per distinct key. The grouping logic is correct given its inputs — the defect is upstream: the same person is legitimately represented by two or more distinct `cluster_id` values (unmerged sibling clusters that share a label) or by a `null` `cluster_id` (each becomes its own `identity-<id>` singleton group).

**Server-side confirmation.** `MemberResponseMapper::map_cluster_identity` (`class-member-response-mapper.php:72-107`) emits `cluster_id` per-member straight from the row (`normalize_cluster_id`); it does not deduplicate or collapse clusters sharing a label. `IdentityMembersReadRepository::list_for_media_ids` (`class-identity-members-read-repository.php:184-239`) joins `wp_acx_clusters c` on `m.cluster_uuid = c.cluster_uuid` per member row — there is no cross-cluster collapse by label or by `person_id` in this query path, so if two clusters share a human label (a state the merge service is meant to prevent going forward, but which pre-existing/legacy rows can still hold), both survive as separate chips.

**Evidence this is a known, recurring class of defect**, not a one-off: the prior `recognition-roster-suggestion-workflow-assessment-2026-05-05.md` F5 finding ("the cluster tab exposes raw cluster rows instead of a person-consolidated view") and F9 both describe the same underlying gap — cluster identity is exposed to the user as backend topology instead of collapsed to a person. UXW2-4's Slice 2/3 (`docs/tasks/uxw2/UXW2-4-roster-library-parity-task-plan.md:32-34`) already targeted a version of this for the Library/media-identities read path ("label writes always bind a person"; "media identities read no longer falls back to raw human labels"), which narrows but does not close the workbench-chip symptom: a chip groups by `cluster_id`, not by `person_id`/roster label, so two clusters both correctly bound to the *same* `person_id` still render as two chips.

**Impact.** Reported on demo.altcontext.com workbench page 2, every row: a user labels one identity as "Jane", clusters exist as `cluster-a` and `cluster-b` both eventually bound to Jane's `person_id`, and the media row still shows two "Jane" chips with no visual signal they're the same reviewed person.

**Recommendation.** Group workbench chips by an effective person key (`person_id` when bound, else `cluster_id`, else singleton), not raw `cluster_id`. This needs a payload field carrying `person_id` per identity (currently `DetectedIdentity` has none — only `cluster_id`/`cluster_label`), sourced from `c.person_id` which `list_for_media_ids` already joins against `p.name`/`p.id` but does not currently select into the response. Pair the collapsed chip with an "N face groups" badge (see Proposal) rather than silently hiding the cluster count, per HAI-01 (evidence before label — collapsing must not hide that multiple clusters remain unmerged).

## Defect B: Chip avatar shows the current image's face, not the cluster representative

**Root cause.** `IdentityClusterItem` sets `const representative = cluster.members[0]` (`IdentityClusterItem.tsx:105`) — the first identity in *this media item's* local group, built from `cluster.members`, which only ever contains identities detected on the current media item (see `groupIdentitiesByClusters`, which iterates `identities: DetectedIdentity[]` scoped to one item's response). `ClusterPreview` (`ClusterPreview.tsx:25-52`) crops `representative.media_url` + `representative.bbox` directly — there is no fallback to a cluster-level canonical face.

**Data-shape evidence.** `DetectedIdentity` (`identity.ts:66-85`) carries `representative_id?: string | null` — a bare UUID, no crop fields (`media_url`/`bbox`/`attachment_url` are all present on the identity itself, describing *that* identity's own detection, not the cluster's representative). Server-side, `MemberResponseMapper::map_cluster_identity` (`class-member-response-mapper.php:88-105`) does select `c.representative_id` from the joined cluster row and emits it as `representative_id`, but never resolves that id to a member row and folds its `media_url`/`bbox` into the response. So even when the payload correctly names *which* identity is canonical, the frontend has no image to render for it and falls back to whatever face happened to appear on the current item.

**Consequence.** The same person's chip shows a different face on every media row — whichever face was detected on that specific image — defeating the purpose of a stable per-person visual anchor and making it harder to visually confirm "is this the same Jane" across rows (this is the direct trigger for Defect A's downstream symptom: users can't eyeball-merge duplicate chips because the avatars don't match each other even when correct).

**Options considered:**
1. **(Recommended) Server joins the representative member's crop into the payload as a `representative_face` object** (`{media_id, media_url, attachment_url, bbox}`), resolved once per cluster in `IdentityMembersReadRepository::list_for_media_ids` (or a lightweight follow-up query keyed on the distinct `representative_id`s in the result set) and threaded through `MemberResponseMapper::map_cluster_identity`. Rationale: the mapper already resolves face-source fields per row via `resolve_face_source_fields` (called at `class-member-response-mapper.php:83`) — extending that same resolution to the representative id is a bounded, single-layer change, and it keeps the "representative" concept authoritative at the data layer (matching `RosterEntriesTable.tsx`'s `selectRepresentativeIdentity`, which already treats "most-confirmed cluster's representative" as canonical). It also avoids a second round-trip from the frontend.
2. **Frontend resolves via the existing `clusters.all` react-query cache.** Rejected as primary: it requires the workbench to already have every relevant cluster's full detail cached (it doesn't, by design — clusters load lazily per selected item), forces a second network fetch keyed by `representative_id` with no existing endpoint that accepts a bare identity id, and duplicates representative-resolution logic that already exists server-side for roster.

**Recommendation:** implement option (i); it is a strict superset of what the mapper already does and matches HAI-01 (evidence before label) and HAI-17 (a review screen must render the store's actual reference image, not a substitute capture) from the heuristics canon.

## Roster Questions

### 1. Thumbnail size — 32px directory thumb

Current: `DIRECTORY_THUMB_SIZE = 32` (`RosterEntriesTable.tsx:26`), explicitly commented "Dense table-row size — not the drawer default (96/128)." Canon: no canon rule sets an absolute pixel floor for identification thumbnails; the closest is HAI-01 ("the reviewer can inspect that evidence in one action") and HAI-17 ("the true entity is rejected when the lone reference is old or unlike it") — both concern *access to* and *representativeness of* the reference, not raw pixel size. 32px at a dense table density is an intentional, documented trade-off (scanability of a directory list) with a larger 96/128px reference available one click away in the drawer (`PersonWorkspacePanel`). **Recommendation:** no change; the size trade-off is already justified in-code and the escape hatch (drawer) exists.

### 2. Value of the face-group count

Current: the roster table's "Face groups" column (`RosterEntriesTable.tsx:314`) shows `cluster_count`, i.e., how many distinct clusters are bound to this person. Per `recognition-roster-suggestion-workflow-assessment-2026-05-05.md` F6, the roster entries contract historically exposed only counts, not the underlying clusters/instances for review — that gap has since been filled by `PersonWorkspacePanel` (`entry.clusters[].instances[]`, `PersonWorkspacePanel.tsx:323-350`), so the count is no longer a dead end. **Recommendation:** keep the column, but make it a link/affordance into the workspace panel filtered to that person's clusters (it currently is not directly clickable per row — the row's clickable elements are Edit/Delete/Save/Cancel only, `RosterEntriesTable.tsx:237-279`), and treat a `Face groups > 1` count as the trigger surface for the person-level merge affordance proposed below.

### 3. Tags — what consumes them downstream

Current: tags are stored on `acx_persons` (`class-roster-entry-projection-repository.php:63-95` decodes the JSON `tags` column), editable in `RosterEntriesTable.tsx:140-173` and displayed in `PersonWorkspacePanel.tsx:263-267`. Grep across `apps/prototype-wp-alt-context/src` and `apps/prototype-description-service` for tag consumers outside the roster projection/mapper/label-service/merge-service/person-resolution layer turned up no export, caption-generation, or media-search consumer — the only *use* found is the roster table's own client-side search filter (`RosterEntriesSection.tsx:107`, `entry.tags.some((tag) => ...)`). **Recommendation:** either document tags as a roster-local search/organization aid only (update in-app copy so users don't expect it to affect captions/exports), or, if downstream consumption was intended, that's a real product gap worth its own follow-up — this assessment did not find evidence of a broken downstream integration, only an apparently-never-built one.

### 4. Merge UX for the same person on separate rows (person-level merge missing)

Current: `ClusterMergeService::merge_cluster` (`class-cluster-merge-service.php:62-207`) merges cluster A into cluster B and (when a label is supplied) binds a person to the target — this is a cluster-to-cluster operation. There is no `merge_person`/`merge_roster_entry` endpoint. `RosterEntryProjectionRepository::group_rows_by_normalized_name` (`class-roster-entry-projection-repository.php:115-161`) only groups DB rows sharing an *exact normalized name string* — it is a display aggregation over `acx_persons` rows that already share a name, not a merge tool for two persons with different underlying `person_id`s (e.g., "Jane Doe" vs "jane doe " with trailing whitespace normalizes together automatically per the method, but "Jane Doe" vs "J. Doe" never will, and only an operator visually recognizing the duplication has any UI path to converge them — none exists today). Canon: INT-07 (preview before commit) and INT-09 (reversible command stack) are both already honored for the cluster-merge path — `IdentityClusterItem.tsx` renders `MergeUndoBanner` after `mutations.merge` succeeds (`handleUndoMerge`, `IdentityClusterItem.tsx:230-243`) — so a person-level merge should be built to the same standard: preview the resulting merged person (name conflict resolution, tag union) before commit, and keep an undo path. **Recommendation:** add a person-merge endpoint (merge cluster bindings + tag union + preserve one canonical `person_id`) surfaced from the roster table when two rows' `Face groups` counts suggest overlap, gated by the same preview/undo pattern already proven at the cluster level.

### 5. Click-name → media items behaviour vs canon

Current: clicking a roster entry's name toggles inline edit mode (`RosterEntriesTable.tsx:271`, `onClick={() => setIsEditing(true)}`) — it does not navigate to that person's media. The actual "review this person's images" surface is `PersonWorkspacePanel`, opened separately (via `RosterPage.tsx:212`, `onOpenQueue`) and showing `cluster.instances` with a lightbox (`PersonWorkspacePanel.tsx:289-350`). This satisfies COG-02 (recognition over recall — no typed query needed to find a person's media) once the panel is open, but the *entry point* is not the name itself, which is arguably the least-discoverable element for "show me this person's photos" (a user's first instinct on a directory row is usually to click the name/photo, not to locate a separate button). **Recommendation:** either make the name (or the avatar) the primary trigger for opening the workspace panel and move inline-rename to a dedicated edit icon (already present, `Pencil` icon at `RosterEntriesTable.tsx` per the lucide-react imports), or keep both but visually signal that the avatar/name is clickable for review — current markup gives no such affordance.

### 6. Low-confidence suggestions in the Unnamed-faces CTA

Current: the standalone `NeedsAssignmentSection` rail described in the task brief and in `UXW2-4-roster-library-parity-task-plan.md` has already been retired per that plan's Slice 4 ("retire needs-assignment rail, link to workbench queue") — confirmed by its absence from the current roster page file listing and by the presence of `RosterZeroStateReachability.test.tsx` in its place. Roster's zero state now routes to the workbench review queue rather than rendering its own unlabeled-cluster rail. Similarity banding for suggestions lives in `band_for` (`apps/prototype-description-service/recognition/application/suggestions/roster_candidates.py:75-81`): `strong` at/above `suggestion_ceiling`, `possible` in `[floor, ceiling)`, else `none` (only two live bands plus a floor-gated absence — not the three-tier strong/likely/possible scheme named in the task brief, which does not match current code and should not be re-asserted). **Recommendation:** none needed for the CTA itself (already addressed by UXW2-4); if "low-confidence suggestions" specifically means the `possible` band, confirm with `apps/prototype-wp-alt-context/js/admin/pages/roster/similarityCopy.ts:36-53` (`bandLabel`) that the UI copy correctly labels `possible`-band suggestions as tentative rather than implying confirmed identity — out of scope to verify further here without a live suggestions payload.

### 7. Roster completeness vs corpus manifest

The corpus manifest (`benchmarks/manifests/corpus-manifest-v3r-20260814.json`) lists 130 top-level `identities` entries and 130 distinct named identities across all 646 `entries[].named_identities`/`primary_identity` fields (verified by direct count, not sampling) — the two counts agree, so the manifest itself is internally consistent. This assessment did not have access to a live roster/database to compare against; verifying roster completeness requires querying `acx_persons` count on a running site against this 130 baseline (see Verification below), not a static-file comparison.

## Proposal

1. **Per-media dedupe by roster person, not raw cluster_id.** Extend the media-identities payload with a `person_id` (and derived `person_label`) per identity, sourced from the `p.id`/`p.name` join `list_for_media_ids` already performs but does not currently expose on the identity object. Change `groupIdentitiesByClusters` (or a new `groupIdentitiesByPerson`) to key on `person_id ?? cluster_id ?? identity-<id>`, and render an "N face groups" badge on the collapsed chip when `> 1` distinct `cluster_id` collapsed into one person, with the badge itself opening a small inline list of the underlying clusters (satisfying HAI-01 — collapsing chips must not hide that unresolved cluster fragmentation still exists).
2. **Representative crop as primary avatar, current-image face secondary.** Implement Defect B option (i): resolve the cluster's `representative_id` to its member row's crop fields server-side and add a `representative_face` object to the cluster-level portion of the payload (not per-identity, since it's the same value for every member of a cluster) — mirroring `RosterEntriesTable.selectRepresentativeIdentity`. `ClusterPreview` should prefer `representative_face` when present, and can still show a secondary, smaller "current image" thumbnail if operators need to confirm the specific detection they're reviewing (this preserves evidence-before-label without regressing the ability to inspect the actual detection driving the review).
3. **Person-level merge with preview + undo.** Add a merge-persons operation (merge cluster bindings across two `person_id`s, union tags, pick a canonical name) gated behind a preview (INT-07) with the same undo pattern already implemented for cluster merges (INT-09, `MergeUndoBanner`). Surface it from the roster table when `Face groups` counts and/or normalized-name grouping suggest the same person is split across rows.

This proposal deliberately stops at what the evidence in this assessment supports; it does not extend into suggestion-refresh orchestration, which the prior 2026-05-05 assessment already covers in more depth (F1-F4, F10) and remains the correct home for that work.

## Open Questions and Verification

- **Unverified claim:** the exact three-tier "strong/likely/possible" similarity-band scheme named in the task brief does not match current code (`band_for` implements two live bands: `STRONG`/`POSSIBLE`, gated by a floor). If a three-tier scheme exists elsewhere (e.g., a UI-only presentational layer), it was not found in `roster_candidates.py` or `similarityCopy.ts` in this pass — flag for the requester to confirm which surface they observed it on.
- **Unverified claim:** roster completeness against the corpus manifest requires a live `acx_persons` row count, which this assessment could not obtain (no running local site was inspected). The 130-identity manifest baseline is confirmed; the "roster has fewer/more people than the manifest" comparison is not.
- **Reproduction (local site):** scan a corpus batch with ≥2 unmerged clusters sharing a label, view the resulting media item on the workbench Review Queue — expect N chips for the same person (Defect A) with mismatched avatars per chip (Defect B).
- **Test coverage to check before implementing:** `apps/prototype-wp-alt-context/js/admin/pages/workbench/identity-clusters/__tests__/ClusterPreview.test.tsx` (avatar/representative rendering), `IdentityClusterItem.twinChip.test.tsx` (merge-twin chip, adjacent to but distinct from Defect A), `apps/prototype-wp-alt-context/tests/Unit/IdentityMembersRepositoryTest.php` (`list_for_media_ids` query shape), `RosterEntriesTable.reservedLabel.test.tsx` and `RosterZeroStateReachability.test.tsx` (roster-side regressions to watch when touching the table), and any PHPUnit coverage on `MemberResponseMapper::map_cluster_identity` for the proposed `representative_face` field addition.
