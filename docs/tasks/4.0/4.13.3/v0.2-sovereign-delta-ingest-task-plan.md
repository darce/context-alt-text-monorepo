# Plan: v0.2 -- Delta Ingest and Idempotent Ingest

## Problem Statement
Full snapshot synchronization is inefficient for large tenants with frequent updates. A delta-based ingest model is required to reduce bandwidth usage and improve synchronization frequency.

## Workflow Principles
- **Idempotency**: Applying the same delta payload multiple times must always result in the same database state.
- **Monotonic Sequence**: Ingest must only process versions greater than the locally persisted `snapshot_version`.

## Terminology
- **Delta**: A partial update containing only the changes since a specific version.
- **Idempotent Ingest**: A processing pattern where updates are guarded by version checks.

## Current State Analysis
- The system only supports full snapshot pulls via `GET /snapshot`.
- Every sync cycle replaces the entire local projection content.
- Bandwidth usage grows linearly with the number of identities.

## Proposed Solution
Implement a delta endpoint on the backend and an idempotent ingest handler in the plugin to process incremental updates (events) while preserving curation integrity.

## Patterns to Follow

### [Idempotent Ingest Pattern]

```php
if ( $incoming_version <= $local_version ) {
    return; // Already processed
}
// Apply update...
```
