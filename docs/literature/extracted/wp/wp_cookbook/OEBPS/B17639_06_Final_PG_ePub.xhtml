Chapter 6: Extending the Block Editor

As mentioned a few times thus far, a large evolution in WordPress functionality came in version 5.0 with the introduction of the Block Editor, also well known by its development codename, Gutenberg. While the original page editor was quite functional and had been supporting content creators for many years, it did not provide full What You See Is What You Get (WYSIWYG) functionality. More specifically, users building a complex website were often required to use shortcodes that are only seen once a page is saved and viewed on the site, or even had to type in HTML code. Of course, many third-party plugins (Visual Composer, WPBakery, Elementor, Divi, and so on) saw this as an opportunity to provide more advanced page building interfaces, eventually leading to the WordPress development team creating their own solution with the block editor.

The block editor introduced a new content creation paradigm with an array of building blocks that can be added and immediately seen on the page and post editors. The block editor also introduced a new programming paradigm for plugin developers, with the majority of its code being written in JavaScript instead of PHP. Furthermore, new blocks can either be written in traditional JavaScript or using ESNext, a new version of JavaScript that is not yet supported by browsers, along with JSX, a JavaScript module created by the React project.

While the same results can be achieved with both techniques, creating new blocks using ESNext and JSX is much easier, since developers can write simple code that will be converted to browser-compatible JavaScript through a build process. The resulting code is also better optimized to support all browsers with no additional work on the developer's part, and all compiled code is automatically combined and minimized in a single script file, allowing browsers to load it rapidly.

We'll develop three new blocks in this chapter using ESNext and JSX in the following recipes:

  • Setting up a block development environment and creating a simple block
  • Creating an editable blockquote block
  • Creating a new WordPress REST endpoint
  • Creating a server-side rendering block that leverages an existing shortcode

Curious readers can take a look at a set of sample block codes provided by the WordPress development team on GitHub (https://github.com/wordpress/gutenberg-examples/) to see how code differs between standard JavaScript and ESNext/JSX samples.

When developing plugins, supporting the Block Editor can help widen your audience, since many users have started using the new editor and are always on the lookout for plugins that support blocks. That being said, only supporting blocks to display your plugin's content or functionality can be very limiting, since users running the Classic Editor plugin, a different page builder, or the ClassicPress (https://www.classicpress.net/) WordPress fork won't be able to use your creations.

Technical requirements

You can find complete code examples on GitHub in the following repository: https://github.com/PacktPublishing/WordPress-Plugin-Development-Cookbook-Third-Edition.

You should also make sure that you are not running the Classic Editor WordPress plugin on your development site, since that plugin's only purpose is to suppress the new block editor, which we'll be extending.

Setting up a block development environment and creating a simple block

As mentioned in the introduction, code to create custom blocks written using ESNext and JSX must be compiled before being able to run in standard browsers. This recipe shows how to download a copy of Node.js, the tool that will allow us to build our code, along with a set of necessary support modules to create a reusable block development environment.

Getting ready

You should have access to a WordPress development environment, either on your local computer or a remote server, where you will be able to load your new plugin files.

How it works...

Node.js is a powerful tool that allows developers to run JavaScript code outside the browser from Command Prompt and is the cornerstone behind the creation of ESNext/JSX WordPress blocks. Once installed, we're able to run the necessary commands to download all scripts and modules required to compile our code and perform the actual compilation.

The npm init command's purpose is to create a file called package.json, defining our project's configuration. While many lines in this file are purely informational, the important lines are the ones that define where the compiled code should be saved (build/index.js) and the command to run to compile the code (wp-scripts build).

Our subsequent call to npm install --save-dev --save-exact @wordpress/scripts fetches all components that make up the @wordpress/scripts Node.js bundle, along with the wp-scripts executable that we referenced in our build command. While Node.js only needs to be installed once on your computer, steps 5 to 8 will need to be repeated for any new plugin you create that creates custom blocks. Alternatively, you can copy and modify the package.json file, along with a straight copy of the node-modules directory, to a new folder to save yourself time when starting a new project.

Once we have our tools in place, the next section of this recipe creates one of the simplest blocks possible, which only displays a short block of HTML code. This is done in src/index.js by first importing the RegisterBlockType function from the block development libraries, and then calling it with a number of parameters. These parameters respectively define the name of the new block, the name of the Dashicons font element to use as an icon for the block, the block editor category that the block should be assigned to, and finally, the code used when rendering the block in the editor (edit) and on visitor-facing web pages (save). As you can see, we use the same code in both cases in this recipe, and that code is essentially the same that we used in the Creating a new simple shortcode recipe in Chapter 2, Plugin Framework Basics.

Once all code has been placed in the src/index.js file, running the npm run build command calls the wp-scripts tool to compile our code and places the resulting output in build/index.js, overwriting any previous version of the file in the process.

The last few steps of this recipe are closer to the plugin development work that we did in previous chapters. More specifically, we write PHP code to register a function to be called when WordPress performs its initialization routine, and then provide an implementation for this callback function. Our callback first checks for the existence of the register_block_type WordPress function and exits immediately if the function does not exist. Its absence either indicates a version of WordPress older than 5.0, or a ClassicPress installation, where the block editor does not exist. In either case, trying to execute further code will only result in a fatal error on the site. If the function does exist, our code loads a small PHP file that was created during the compilation process called index.asset.php and uses variables found in this file in the following call to wp_register_script. Once the script has been included, our function calls the register_block_type function. In this function, the first parameter should match the block name defined when calling the RegisterBlockType function in our JavaScript code, and the second argument is an array of configuration parameters. For this first example, the array contains a single item specifying the script to be loaded to create the custom block.

Now, a block such as this specific one is perhaps not quite as useful as the shortcode that we created before, since it cannot be placed in the middle of a sentence to display a link to a Twitter feed. That being said, it shows us how to write and compile a very basic example of a block and can still be useful to create reusable HTML blocks for custom projects.

There's more...

With all of the files that were created in this recipe, let's take a look at the ones that should be placed under version control and distributed with your plugin.

Version control for custom blocks

If placing your plugin source files under version control, the package-lock.json file and node_modules directory do not need to be stored in your code repository. They can easily be recreated by running the npm install and npm run build commands.

Files required for plugin distribution

If you are planning on distributing your plugin, the only files that need to be included are the ch6-block-template.php file and the entire build directory. All of the other files (the .json files, the src folder, and the node_modules folder) are not used when running the code. If you plan to distribute your work as open source software, you should also include the package.json file and all files in the src directory. You should never include the node_modules directory, as it is quite large and can be recreated following the steps in this recipe.

How it works...

This second block creation recipe adds a few concepts to the simple static block that we created in the Setting up a block development environment and creating a simple block recipe. If we first look at src/index.js, we can see that we are importing a second element from the WordPress block development libraries, namely the RichText component.

Our main block code then proceeds to call the RegisterBlockType function but with a few differences from our first example. It first uses a block of SVG code to define the icon parameter and thus make our block stand out from other default blocks in the WordPress editor with a custom icon. It then proceeds to define attributes for the block. In this case, there is a single one called content, defined as an array capable of holding one or more HTML paragraphs.

The edit section of the RegisterBlockType function is also different from what we've seen before. It receives an argument called props. The props argument contains the block's data, which is assigned to the attributes structure that was previously created. The edit section also creates a function called onChangeContent that will be called when the user edits the blockquote's content. Finally, the edit section renders an element of RichText type and assigns a callback function to its onChange property. It also initializes its value to the text received from the block's data and assigns any stored CSS class name to it.

The save section of the RegisterBlockType function is much simpler but still uses the RichText element to render onscreen text based on the content attribute saved in the block's data.

The main plugin PHP file is almost exactly the same as the one created in this chapter's first recipe. More specifically, our code registers an init action hook callback. This callback proceeds to verify whether the register_block_type function exists. If it does, it follows up with calls to register the block's main JavaScript compiled file, along with creating a reference to a style sheet file. Finally, it calls the register_block_type function with an additional array member in its second argument to load the registered CSS style sheet.

The content of the CSS style sheet file that we created is used both in the block editor and in visitor-facing pages to style our new blockquote block.

Creating a new WordPress REST endpoint

The REST API is an interface that allows application developers to exchange data with the core of a WordPress site. This API can be used for anything, from developing a mobile application that displays WordPress pages or custom post types to creating a complete replacement interface for content creation.

The new WordPress block editor was built using the REST API to interact with the rest of WordPress. As such, plugins occasionally need to extend the REST API to be able to implement new endpoints. This allows custom block JavaScript code to get access to data that is not part of the default WordPress REST API.

Getting ready

You should have already followed the Managing multiple sets of user settings from a single admin page recipe in Chapter 3, User Settings and Administration Pages, to have a starting point for this recipe. The resulting plugin should still be active on your development site. Alternatively, you can get the resulting code (ch3/ch2-twitter-embed/ch2-twitter-embed-v2.php) from the book's GitHub page and rename the file as ch2-twitter-embed.php.

How to do it...

Follow these steps to create a new endpoint used to retrieve a list of plugin options created in a previous recipe.

  1. Navigate to the ch2-twitter-embed folder of the WordPress plugins directory of your development installation.
  2. Open the ch2-twitter-embed.php file in a text editor.
  3. Add the following line of code at the end of the file to assign a callback function to be called when WordPress initializes its REST API components:

    add_action( 'rest_api_init', 'ch2te_rest_api_init' );

  4. Continue the plugin's code file by inserting the following code to provide an implementation for the ch2te_rest_api_init function:

    function ch2te_rest_api_init() {

        register_rest_route( 'twitter-embed/v1',

            '/optionlist',

            array(

                'methods' => 'GET',

                'callback' => 'ch2te_rest_option_list',

                'permission_callback' => '__return_true'

        ) );

    }

  5. Add the following block of code to the plugin file to provide an implementation for the ch2te_rest_option_list function that was mentioned in the previous step:

    function ch2te_rest_option_list(

            WP_REST_Request $request ) {

        $option_array = array();

        for ( $counter = 1; $counter <= 5; $counter++ ) {

            $temp_options = ch2te_get_options( $counter );

            $option_array[$counter] =

            $temp_options['setting_name'];

        }        

        $response = new WP_REST_Response( $option_array );

        return $response;

    }

  6. Save and close the plugin file.
  7. Enter the following address in your browser: http://plugin-development-site.local/wp-json/twitter-embed/v1/optionlist, replacing http://plugin-development-site.local with your development site's address. You should see the following output appear in your browser:

    {"1":"First Setting","2":"Default", "3":"Default","4":"Default","5":"Default"}

As you can see, visiting this address returns a complete list of configuration names, as defined in our plugin's administration page. Note that the first part of the address will vary depending on the web server that you're using to test your development work.

How it works...

Our new code first takes care of registering a function to be called when WordPress initializes the REST API system. This function contains a single call to the register_rest_route function, where the first two parameters are used to specify the URL of the new REST API endpoint. They are followed by an array of additional parameters that specify the methods that will be used to query this data (GET and/or POST), the callback function that should be called when the new endpoint is queried, and finally, an optional permission_callback function that could be called to validate whether requests to this endpoint have proper permissions.

The remainder of this recipe's code implements the function that gets called when the endpoint is accessed. By using a simple for loop, this function's code retrieves the names of all configurations for the plugin and puts them in a new array. This is placed in a WP_REST_Response object and sent out to answer the request.

Creating a server-side rendering block that leverages an existing shortcode

As mentioned at the start of this chapter, block creation uses a different programming pipeline by leaning more heavily on JavaScript. This means that providing a simple block to complement an existing simple shortcode, as we've done in this chapter's first recipe, results in code duplication in our plugin. It's also not always easy for developers who are more accustomed to PHP and HTML to create complex blocks using pure JavaScript code. To alleviate these issues, WordPress offers a method by which plugins can use a server-side PHP function to render a block's content. This allows developers to offer plugins with shortcodes and blocks that share the same code base.

Getting ready

You should have already followed the Creating a new WordPress REST endpoint recipe to have a starting point for this recipe. The resulting plugin should still be active on your development site. Alternatively, you can get the resulting code (ch6/ch2-twitter-embed/ch2-twitter-embed-v3.php) from the book's GitHub page and rename the file as ch2-twitter-embed.php.

Alternatively, you can perform steps 1 to 8 of the Setting up a block development environment and creating a simple block recipe when asked to copy files to the new folder you'll be creating.

How it works...

The first thing to note about this recipe is that while we've broken out our block JavaScript code into two separate files, both are combined together automatically in a single index.js file in the build directory when we compile our code. This allows developers to organize their development code in smaller files while maintaining good performance when running their custom blocks.

If we first look within src/index.js, we can see that we are calling the registerBlockType function as before but, this time, declaring two attributes for our block, user_name and option_id. We can also see that the save parameter of the function does not return anything, since block rendering is actually handled by a PHP function in our main plugin file. Finally, the edit parameter is just assigned a value of edit, a variable imported at the top of the script.

Moving on to the src/edit.js file, our code first imports a number of new components: ServerSideRender, SelectControl, PanelBody, TextControl, and InspectorControls. These will be used to build the configuration panel for our new block and to implement server-side rendering. These lines are followed by a section of code that uses the REST endpoint that we created in the previous recipe and stores the list of options it receives in an array called optionIdOptions.

The edit variable itself starts with the reception of the block's data and storing it locally. It then registers two callbacks to be called when the Twitter username value is changed or when a new option is selected from the block's configuration drop-down list.

In its next section, our code defines the block's configuration panel using the various elements that were imported at the top of the file using a syntax similar to HTML. We also use the optionIdOptions array to initialize the SelectControl component and show a drop-down list of options.

The last part of the edit section contains a user warning written in standard HTML, along with an instance of the ServerSideRender component and the configuration panel defined previously. When the block is added to the editor, the warning text shown in Figure 6.4 appears, along with a small block of text.

The reason we are not seeing actual tweets is that the block editor is a dynamic environment where content is loaded as soon as blocks are created. When using server-side rendering, this does not always allow dynamic content triggers to run properly. In this case, our plugin output partly renders on screen, but the JavaScript code it loads from the Twitter website does not get triggered as it normally would. Thankfully, we are able to define different output when our block is rendered in the editor and on web pages. This allows us to display a warning to content creators to explain the situation.

We could rework our custom block code to display the tweets in the block editor by using ESNext and JSX, but that would defeat the purpose of using server-side PHP rendering and working off a single code base. Direct HTML output would render without a hitch using server-side rendering, but it would not teach us this lesson.

Moving on to the plugin's main PHP file, ch2-twitter-embed.php, its code is very similar to what we used for our blockquote block, with the addition of two items in the array of parameters sent to the register_block_type function. These items are the render_callback, which is the PHP function to be called to display the block's contents, and an array of attributes that should exactly match what was defined in src/index.js. While we used attributes before with our blockquote block, our PHP code did not need to be aware of them until now, since all rendering in the previous recipe was done within the JavaScript code.

It's interesting to note that the render_callback function that is assigned in our call to register_block_type is identical to the code we had previously defined to render our shortcode content. By making our attributes match the names of our previous shortcode arguments, we have complete code reusability between our existing shortcode implementation and our new block.
