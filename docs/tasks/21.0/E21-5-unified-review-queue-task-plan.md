## Objective

Replace the 4-queue `SuggestionReviewPanel` stack with a **card-at-a-time review queue** driven by the existing `nextAction` selector, with kind-derived filter chips, per-item accept/reject with a brief **announced** undo window that gates the queue advance on a durable backend write (no optimistic "saved" state), and **person-commit** (creatable roster combobox) as the primary naming action on the review card. Finalize one-primary-CTA-per-state in the media footer. This is the demo's central interaction — it converts "a pile of stacked panels" into a legible one-item-at-a-time pipeline.

## Problem Statement

The scan→review→confirm loop is the demo's story, but today it renders as four vertically stacked queues (`SuggestionReviewPanel`, 369 lines) — assignment, merge, suggested-names, top-unlabeled-clusters — plus a bulk-accept block, all mounted at once and competing with a 10–100-row media table for attention (WBUX-1 §2.1 "everything renders at once"). The `nextAction` driver already computes the single highest-priority item but is used only to scroll to those queues or open a labeling panel — it is a scroll helper, not a queue driver. Primary naming routes through a **label-only** path (`updateClusterLabel` → cluster `label` string) rather than committing a real roster person, so a first-time visitor's "name this person" produces a label, not a person. Accept/reject has no user-facing undo (only a silent optimistic rollback on network error). The media footer shows two enabled CTAs (`MediaAnalyzeCta` accent + `BulkDescribeCta` WP-secondary) whose priority is expressed only by CSS class, with no state machine choosing one primary per screen state.

## Constraints

- **Frontend-only. Zero backend contract changes** — all needed endpoints already exist (accept/reject/merge/name/bulk-accept, roster `.../commit`, cluster `PATCH label`). No REST, PHP, or schema edits. If a design pressure suggests a new endpoint (e.g. a server-side batch or an "un-accept"), it is **out of scope** — file as an E16/service follow-on (rg-002).
- **rg-002 (preserve atomic write paths)**: every accept/reject/commit is a **single atomic backend call**. Do not split one backend operation into multiple frontend mutations. Card-at-a-time makes each action single-item, so the existing non-atomic **group** fan-out (`Promise.all(mutateAsync…)` in `SuggestionReviewPanel.tsx:67-112`) is eliminated, not reproduced. Undo is rg-002-safe by construction (see Proposed Solution — immediate-commit + gated advance; exactly one POST or none; no inverse endpoint invented).
- **rg-003 (zero-state reachability)**: the queue's primary controls (and the media footer's Analyze CTA) must be reachable and legible from a zero/empty state — disabled-with-reason, never hidden.
- **sr-004 (design tokens)**: all new styles consume `--acx-*` tokens landed by E21-4 (`--acx-color-*`, `--acx-text-*`, `--acx-shadow-*`, `--acx-radius-*`, `--acx-font-weight-*`, `--acx-space-*`). Zero raw hex/scale literals; the tokenization test (`workbench-tokenization.test.ts`) must stay green over every touched `components/*.scss`.
- **sr-007 (centralized status enums)**: projection categories and queue-item kinds import from a single canonical definition (extend the existing `NEXT_ACTION_KIND` / `queue_memberships` union) — no scattered magic strings.
- **No new god-context coupling**: consume existing `WorkbenchContext` / `useWorkbenchFindings` / `useSuggestionReview*` surfaces; do **not** widen `WorkbenchContextValue`. The provider decomposition is E21-11 (P5-A) and is out of scope here — but do not add fields that make it harder.
- **Banned vocabulary**: all user-visible copy passes `banned-vocabulary.test.tsx` (`topology`, `replay`, `projection`, `dead-letter`, `curation acknowledgement`, `Source version`, `projected instances`, `Curriculum`, raw UUIDs). Filter chips must use plain human labels (working copy: "Close matches", "Possible duplicates"), never raw `queue_memberships` strings or E15-13 terms of art ("Singletons" fails this bar).

## Design-direction preamble (composition of the new surface)

E21-4 owns the token direction; this preamble owns the **composition** of the new surface — a genuinely new composed card cannot inherit its layout direction from a tokens task [LAY-10: every default that survives must be a choice]. Direction (mirrors the E21-4 preamble's role, scoped to layout):

1. **One focal point, three sense-groups [LAY-01][LAY-04].** The card regroups its ~9 elements into exactly three units so the structure is absorbable without counting:
   - **G1 — subject (dominant)**: face crop + the identity question ("Is this \<name\>?" / "Who is this?"). Largest mass, first in reading order and DOM order.
   - **G2 — action zone (support)**: person-commit combobox + Accept/Reject (+ tertiary "just label"). Adjacent to G1, visually subordinate to it.
   - **G3 — queue chrome (subordinate, recessed)**: filter chips, "N of M" position, prev/next. Smallest type, lowest value contrast, spatially separated from G1/G2 by the largest interval on the card [LAY-03].
   Hierarchy is carried by size/weight/position, not by nested boxes or rules [LAY-06].
2. **Type-scale steps are assigned, not emergent [TYPE-05].** Card title / identity question: `--acx-text-lg` + `--acx-font-weight-semibold`; body/meta and combobox text: `--acx-text-sm`; chip labels and the N-of-M position indicator: `--acx-text-xs`; nothing on the card takes a step not named here. Leading rebalances where a step moves [TYPE-02]. Tokenization-green proves no raw literals; **this assignment** is what proves the hierarchy is chosen — the visual re-baseline review checks it.
3. **Accent thrift — at most one accent-carrying primary in the viewport per state [COL-03][COL-09].** Token roles: **primary** = `--acx-color-accent` background + `--acx-color-accent-contrast` text + `--acx-font-weight-semibold`; **secondary/tertiary** = neutral/ghost (grey ramp, no accent). The state selector (§7) resolves primacy across the **whole rendered Workbench viewport**, not the footer alone: when the review card is on screen its G2 primary carries the accent and both footer CTAs render secondary; when no card is mounted the footer's state-selected CTA is the single accent carrier. Selection/focus tints use `--acx-color-accent-soft` and do not count as a second primary; chips use neutral styling with a value-contrast active state [COL-04], never accent fill.
4. **Target sizes are a floor, not a hope.** Every new interactive control (chips, prev/next, accept/reject, combobox trigger, undo) gets `min-width`/`min-height` `var(--acx-space-24)` (1.5rem = 24px) — the WCAG 2.5.8 floor — asserted by bounding-box in the e2e spec (A11Y-14 is owned **here** for these controls, not deferred to E21-9's drag seam).
5. **No dead chrome.** Nothing interactive-looking on the card leads nowhere (see §6 — the hard-examples chip is omitted until its contract lands) [LAY-10].

LAY/COL/TYPE IDs above verified against `docs/strategy/design-aesthetics-heuristics.md` (LAY-01–09, COL-03/04/09, TYPE-02/05) and the heuristics-canon lexicon (LAY-10).

## Workflow Principles

- **Relocate/rebuild-behind-behavior, don't redesign data flow.** The queue is a new presentation over existing queries and mutations. Every backend interaction already exists and stays byte-for-byte.
- **Risk-first slicing.** Slices 1a/1b land the structural core under orchestrator ownership — 1a the driver contract (zero UI diff), 1b the shell swap — kept separate so the highest-structural-risk step never mixes a contract change with a surface migration; Slices 2–4 layer behavior onto the shell and are parallelizable across **Claude Agent-tool subagents on disjoint file sets** (grok offload is on security hold). Each slice merges independently through the pre-merge gate.
- **A11y is acceptance, not audit.** Every async surface (card transition, pending/undo announce, commit result) ships a live-region assertion; the core loop passes a keyboard-walk. Axe alone gates nothing (A11Y-23).
- **Read the landed dependency plans before Slice 1** — E21-1 (`E21-1-sync-status-view-model-task-plan.md`) and E21-4 — to consume whatever status view-model and tokens actually landed rather than what this plan assumes.

## Terminology

- **Review queue**: the new card-at-a-time surface replacing the `SuggestionReviewPanel` stack.
- **Queue driver**: the `selectNextAction` priority selector (`useWorkbenchFindings.ts:112-144`), promoted from scroll-helper to the thing that chooses which single card is shown.
- **Person-commit**: creating or assigning a real roster person via `commitClusterToRosterEntry` (`POST .../roster/clusters/{id}/commit`). Distinct from **label-only rename** (`updateClusterLabel` → `PATCH .../clusters/{id}`, a `label` string with no roster person).
- **Filter chip**: a chip over the review queue, **derived from the queue-item `KIND`** (not from roster `queue_memberships` — see below), rendered as **plain human copy**: assignment→**"Close matches"**, merge→**"Possible duplicates"** (working copy — final strings must pass banned-vocabulary and contain no term of art; "Singletons" is E15-13 projection jargon and is not used). **No "Hard examples (coming soon)" chip is rendered** — dead UI is omitted until its contract lands (see §6). Pending suggestions have no roster entry yet, so the roster-side `queue_memberships` field does not apply to this pre-commit queue (resolves PA-01).
- **Immediate-commit undo (gated advance)**: no optimistic "saved" state — a brief window holds the item as *Saving…*; when it closes the single backend call fires and the queue advances **only on success** (failure re-surfaces via a persistent inline `role=alert`). "Undo" cancels before the call fires — 0 calls if undone, exactly 1 on commit (no inverse endpoint needed). The window's countdown **pauses while focus or pointer is on the held card's undo affordance** (A11Y-16 — a fixed 5s window is illusory reversibility for AT users).

## Target Outcome

A first-time visitor, after scanning, sees **one review card at a time** — the highest-priority item the `nextAction` driver selects — with filter chips to scope by category. They accept or reject with a single click; an **inline announced hold** ("Saving… — Undo") offers **Undo** before the write fires. When they name a person, they **commit a real roster person** (creatable combobox), and a "View in roster →" affordance points at the roster. Bulk accept is one disclosure, not a stacked block. The media footer shows exactly **one primary CTA per screen state**. Every state (loading/empty/error/offline) manages focus and announces; the whole loop passes the automated keyboard-walk/live-region specs **and the manual VoiceOver protocol** (Verification Strategy — the harness cannot run an AT; a human does). No sync-internal jargon reaches the UI.

## Proposed Solution

**1. Queue driver (promote `nextAction`).** Extend `selectNextAction` from "top item" to an ordered, filterable **queue view** over the same sources: expose the ordered list (not just `[0]`) and a `filter` by chip category, keeping the existing priority for the default (unfiltered) order. Keep `NEXT_ACTION_KIND` as the canonical kind enum (sr-007) with a `KIND`→chip-label map. No new queries — derive from the data `useWorkbenchFindings` already holds.

**Group handling (resolves the no-group-endpoint gap).** Same-cluster assignment groups (`type: 'group'` from `buildSuggestionReviewItems`) are **flattened to one queue item per suggestion**: the queue enumerates suggestions, N-of-M counts suggestions, and each accept/reject is the existing single atomic `POST` — rg-002 holds for every card with zero exceptions. Grouped "accept all" (today's `Promise.all` fan-out) is **dropped, not reproduced**: its ergonomic replacement is the bulk-accept disclosure (§4), which is a genuine single atomic endpoint. Consecutive same-cluster cards keep the cluster label visible ("3 more for \<name\>") so the flattening reads as a run, not repetition. A true server-side group-accept endpoint is out of scope — file as the E16/service follow-on the Constraints already anticipate. `GroupedSuggestionCard` is retired with the stack.

**2. Card-at-a-time shell (`ReviewQueue`).** New `pages/workbench/identity-clusters/ReviewQueue.tsx` **retires the 4-queue stack body**: it replaces `SuggestionReviewPanel` as the **else-branch** inside the anchor div (`ScanTabContent.tsx:92`, `className="acx-findings-detail-anchor"` + `findingsDetailRef` — a className/ref, **not** an id selector); the old `SuggestionReviewPanel` is deleted, its header + bulk-accept disclosure folded into `ReviewQueue` (PA-04 — no "thin host" hedge). Renders exactly one card (the current queue head) + a **filter-chip row** + a "N of M" position indicator + prev/next. Each card is the existing per-kind card (`SuggestionCard` / `MergeSuggestionCard` / name card) reused, not re-implemented.

**Coexistence with the `clusterPanel` reducer.** The reducer's `label`/`review` modes still swap the whole anchor surface (`ScanTabContent.tsx:93-111`, post-merge; the panel state now arrives via the `useClusterPanel()` context) and remain unchanged: `open_review` (→ `ClusterReviewPanel`) keeps its current triggers, and `open_label` (→ `ClusterLabelingPanel`) remains the destination of the **tertiary "just label"** affordance only. What changes is the primary route: queue cards no longer dispatch `open_label` for naming — person-commit is inline on the card (§5) — so the panel swap becomes the exception (explicit tertiary action), not the naming path. Returning from either panel (`close`) re-mounts `ReviewQueue` at the same queue position — possible only because the swap **unmounts `ReviewQueue` wholesale**, so the index cannot live in `ReviewQueue` state: it is lifted to `ScanTabContent` and mirrored in the `queue=` URL param (see Queue state ownership below).

**Queue state ownership (no context widening).** The **current index is lifted to `ScanTabContent` state**, beside the existing `findingsDetailRef` plumbing (`ScanTabContent.tsx:41`) — the `clusterPanel` swap unmounts `ReviewQueue` wholesale (`:93-111`), so queue-local index state would reset on every label/review round-trip; `ReviewQueue` consumes it as a controlled `index`/`onIndexChange` prop pair. The index is additionally **mirrored in the `queue=` URL param** through `useWorkbenchFilters` (`hooks/useWorkbenchFilters.ts`) — the same shim-compatible param surface already specified for the chip filter (Contract table), carrying filter + position — so the queue position also survives reload/deep-link, not just panel swaps. The active chip filter rides that same `queue=` param; the **pending-undo hold stays local to `ReviewQueue`** (it flushes on unmount — §3 policy — so it must never outlive the mount). `ReviewQueue` exposes a small imperative handle (`focusCurrentCard()`) via a ref held by `ScanTabContent` — mirroring the existing `findingsDetailRef` pattern — and `ScanTabContent` extends `handleTargetFindings` (`:56-64`) so `WorkbenchFindingsPanel`'s "Review next" (`:159`, routed via the existing `onTargetFindings` prop) drives the mounted queue instead of scroll-to. `WorkbenchContextValue` gains **zero** fields.

**Focus placement on advance (the happy path, specified).** On accept/reject advance (card unmounts, next card mounts): focus moves **programmatically to the next card's primary action** (the element that owns the same role the user just activated — Accept on an accept-flow, the combobox on a NAME/CLUSTER card). On draining the queue (last card resolved): focus moves to the **empty-state region** (the anchor div, `tabIndex={-1}`, whose empty-state copy is announced). Without this, DOM default drops focus to `<body>` and the keyboard loop restarts from page top on every accept. Card transition announces via live region (A11Y-21); the focus move is asserted with a bare `toBeFocused()` immediately after the action keypress — **never** via `tabUntilFocused`, which re-tabs from `<body>` and is structurally blind to this regression (see Current State).

**Per-kind action matrix** (grounded in `WorkbenchNextAction`, `useWorkbenchFindings.ts:33-43`) — resolves PA-02:

| --- | --- | --- | --- |
| `ASSIGNMENT` | nullable | Accept / Reject; **person-commit only when `clusterId != null`** | `suggested_cluster_id` present on the suggestion; null → commit affordance hidden, accept/reject only |
| `MERGE` | absent | Accept / Reject (merge) | no `clusterId` → **not** a person-commit card |
| `NAME` | required | **Person-commit** (primary) | `clusterId` always present |
| `CLUSTER` | required | **Person-commit** (primary) | unlabeled cluster; `clusterId` always present |

Every review item resolves a `suggested_cluster_id` (`suggestionReviewItems.ts` groups by it), so the commit endpoint's `clusterId` requirement is satisfied for every kind that offers commit. `ASSIGNMENT` rows are per-suggestion (groups flattened — see §1); there is no "group" kind in the queue.

**3. Immediate-commit accept/reject + announced undo (gated advance — no optimistic "saved").** On accept/reject the card enters a brief **pre-commit hold** announced as *Saving… — Undo* (an inline `role="status"` live region, **not** a false "Accepted"); the queue does **not** advance yet. When the ~4–5s window closes without undo — or the user takes the next action, or navigates away — the single atomic POST fires **immediately** and the card advances **only on the backend's success**. **Undo** cancels before the POST fires (rg-002-safe: exactly one backend call, or none). **AT-viable reversibility (A11Y-16)**: the window's countdown **pauses while keyboard focus or pointer hover is on the held card's hold region** (Undo stays available until the user leaves it or acts); the Undo button is in the normal tab order immediately after the actioned control — no Radix F6 viewport-hop, no fixed unreachable deadline. The UI never reports success before the write is durable ([RLSE-05]); failure keeps/re-surfaces the item and announces via a **persistent** inline `role="alert"` (never auto-dismissing; see policy below). **Announce mechanism**: inline in-card live regions only — `ToastContext` is unusable and untouched here (no action slot, no politeness knob, assertive foreground default, hardcoded 5s — see Current State); failure follows the existing inline-alert precedent (`ClusterLabelingPanel.tsx:311`). **Mutation-layer scope (honest sizing)**: this is a **rewrite of the mutation choreography, not a reuse** — the optimistic cache-removal moves out of `onMutate` (the POST is deferred, so cache changes ride the hold state), and the merge/name mutations get pending/error handling **built from zero** (today they have no `onMutate`/`onError` at all — Current State). Slice 2 owns this explicitly. **Rejected alternatives**: (a) optimistic advance + deferred commit — shows "saved" before the durable write, and a React unmount cleanup cannot `await` the flushed async POST, re-introducing the silent-data-loss defect ([RLSE-05]); (b) fire immediately + inverse endpoint on undo — no such endpoint exists and it doubles backend calls; (c) durable pending-queue replayed on remount — an at-least-once replay of a non-idempotent POST double-applies without an idempotency key ([API-02]/[RES-01]) and is speculative machinery for a demo ([REF-12]).

**Undo failure + concurrency policy** (resolves PA-03):
- **Single in-flight window.** At most one commit is in flight at a time. Taking the next action (accept/reject/commit on the next card) **flushes** the prior held commit immediately (fires its POST now, gating that card's advance on the result) before opening the new window — so commits never overlap and never reorder.
- **Failure recovery.** If the fired POST rejects, the gated advance never happened, so the item **stays at the queue head**; announce the failure via `role="alert"` (`aria-live=assertive`) with a retry affordance — the A11Y-24 error state. The failure must never be silent (today's `console.warn`-only path is the defect being removed).
- **Unmount/navigation.** Leaving the Workbench (route change) or unmounting `ReviewQueue` fires any held commit synchronously. Because the advance was gated on success, an unmount-time rejection leaves the item **un-accepted (honest, re-appears next mount)** rather than a shown-saved loss — the [RLSE-05] hole is closed by construction, not by trying to `await` in cleanup.
- **Each invariant above has a named unit test** (they are check-then-act races on a shared pending ref — the likeliest real bugs): (1) *rapid double-action* — accept card A then immediately accept card B: A's POST flushes and resolves before B's window opens, exactly 2 POSTs, order preserved; (2) *unmount-during-window* — unmount with a held commit: exactly 1 POST fires, no state update after unmount; (3) *post-window failure re-surface* — flushed POST rejects: item back at queue head, persistent `role=alert` rendered, retry re-fires exactly 1 POST. These live in `useSuggestionReviewMutations.test.tsx` (new) and are Slice 2 exit criteria alongside the trivial 0-or-1-call assert.
