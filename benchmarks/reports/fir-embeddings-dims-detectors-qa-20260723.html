0a · Objective function — what this program is optimising UNDECLARED

The deepest reason this document does not guide decomposition: nineteen sections each optimise a different quantity — embedding dims optimise open-set margin, §19 optimises corpus licence-cleanliness, §18 optimises GPU dollars, §1 optimises recall against a contaminated GT — and no single criterion ranks them. [EXP-03] names this failure directly: an experiment that decides ship-or-kill, listing many metrics and naming no primary, invites the wrong launch. Every scheduling argument in §§1–18 was therefore arguable, and it was argued, five rounds running.

Proposed OEC — operator-reserved, not adopted. Stated so it can be rejected on the record rather than left absent:

Identity-correct description rate at fixed abstention: the fraction of deployment-corpus images whose published description names every present enrolled person correctly and names no one incorrectly, measured at a fixed abstention rate, on a sealed test split.

It makes the detector question subordinate rather than primary, which is what [RSCH-08] (component-optimum trap) and [EVAL-16] (upstream failure counts against the end-to-end metric) both demand: a detector improvement that does not move this number is not an improvement.

What it costs to measure v7 correction — v6 claimed it was "computable on the same 646-image pass that everything else consumes." That was false. The OEC needs three labels no scheduled task emits: an enrolled roster, the set of present enrolled persons per image, and the name mentions in each published description. T-03 emits detections and descriptions; T-04 emits face boxes. Neither is identity GT. Adopting and instrumenting the OEC is a task (T-12), not a free rider.

"At a fixed abstention rate" is not yet scoreable [EXP-04] [RSCH-07]. A system free to choose which units it abstains on maximises the numerator by abstaining on exactly the hard images the product exists to handle. The adopted form must fix the selection rule, not only the rate: abstain on a% of images under a rule R declared before scoring; abstentions score as neither success nor identity error; coverage 1−a is a separate guardrail.

The structural change, corrected. v7 — v6 got the direction right and the economics wrong

FIRTRAIN-01 as scoped was "adjudicate the Golden-150 detection GT" — have humans check the boxes buffalo already produced. Because truth ascertainment then depends on the detector's own score, that design yields precision and leaves recall — which is what D1 measures — unidentified [AUDIT-04]. That much stands.

What v6 got wrong is that exhaustive annotation is the only remedy. [AUDIT-04] names two branches, and v6 adopted only the second: sample negatives and apply a MAR adjustment (Begg–Greenes / inverse-probability weighting), or treat the parameters as non-identified under extreme positive-only verification. There is also a partial-identification path v6 missed entirely. Ordered by cost, the identification menu is:

  1. Union adjudication (T-14, ~1–2 days). Verify the union of buffalo and candidate boxes. The recall gap is then bounded above by (TPb−TPc)/U. If that bound is below 0.05, D-01 is dead and nothing further is funded. This can only kill, never fire.
  2. Person-box or roster ceiling on joint misses. An external upper bound on faces-per-image truncates the unobserved miss mass and can convert the bound into a partial fire.
  3. Stratified negative sampling + IPW — [AUDIT-04]'s own first branch.
  4. Exhaustive pixel annotation (T-04, 88–147 person-h) — sufficient, and required only if D1 must fire.

And D-03 is not free. v6 claimed the same sample "delivers D-03 for free" via [AUDIT-01]'s inversion. The calculation, stated so it can be checked. D1 is a paired (McNemar-type) comparison of two detectors over the same faces, so the binding term is the discordant rate. For a one-sided 95% lower bound above the funding threshold t = 0.05, with 80% power at a true gap δ:

SE(d̂) = sqrt( (p_disc − δ²) / n_eff )       required:  δ − t  ≥  (z.95 + z.80) · SE  =  2.487 · SE
⇒  n_eff  ≥  (p_disc − δ²) · ( 2.487 / (δ − t) )²      α = 0.05 one-sided,  1−β = 0.80,  planning p_disc = 0.15

p_disc = 0.15 is a planning assumption, not a measurement — the discordant rate between buffalo and the candidate is unknown until T-14 runs, and neff scales roughly linearly in it. Under that assumption:

  • δ = 0.12 — requires neff ≥ 171 faces. Within reach across the whole ICC grid.
  • δ = 0.10 — requires neff ≥ 346. On the image proxy this is the boundary case: reachable at ICC ≤ 0.10 on the split column (353), not on the naive column (295).
  • δ = 0.08 — requires neff ≥ 987. Not reachable from 646 images at any ICC on the proxy grid; may be reachable at the face level if the face-level deff is mild — unknown until T-02.
  • δ = 0.06 — requires neff ≥ 9,055. Out of reach by an order of magnitude.

They assume a discordant rate nobody has measured, a single-level design effect on the wrong unit, and a resampling scheme that the cluster structure does not support. The one conclusion that survives all three caveats is the qualitative one, and it is the reason the section exists: a true detector gap of 0.05–0.08 is not resolvable from this corpus, so a decision rule with a 0.05 boundary cannot be powered here at any sample size. The precise MDE is T-02's output.

Therefore the design error v6 shipped: it used 0.05 as both the funding threshold (CI_LB > 0.05) and the "minimum effect worth detecting". Power at a true effect exactly equal to the decision boundary is 2.5% by construction, not 80% — the study would be designed to fail. The minimum detectable effect must be set strictly above the threshold. Given the frame, set it at 0.10–0.12 and state plainly that a true detector deficit between 0.05 and 0.10 is outside this corpus's resolution. That is an honest limit, and it is decision-relevant: if the deficit is that small, it is not worth a GPU campaign anyway.

Q: What is the path to replacing InsightFace with an in-house FIR for the WP plugin?

Unchanged in shape, corrected in order. What changes is which one goes first, and what has to be true before either is funded:

This is exactly D-02, still open at prior 0.50, and T-01 — ~1 spike-day, $0 — is the only thing that separates them. It is now the first thing to run.

A replacement cannot be declared better than InsightFace against criteria that do not exist.   4. And nothing ships on a pre-OpenCV-5 baseline. v8 CVUP-1 invalidates every SFace-derived number in this document, M-11 included. It is step 0, not a parallel lane.

1 · Can the FIR pipeline's embedding dims be increased? (128 → 512)

Short answer: not on the current model — dims are baked into the trained embedder's final layer, and up-projecting 128→512 adds zero information. But as part of the FIR-7 GPU retrain, yes, trivially: output dimension is a free architecture choice. Recommend 512D for the own-weights retrain.
  • Evidence on dims: FaceNet's controlled same-backbone ablation (CVPR 2015, Table 5): 64/128/256/512D → 128D best (87.9%), 512D worst (85.6%), differences statistically insignificant. ArcFace/MagFace/AdaFace standardize on 512D by convention without a 128-vs-512 accuracy table. The principled reason for 512 is class-packing headroom (CosFace bound: separability degrades when identity count ≫ feature dim).
  • Our measurement v5: withdrawn as evidence of a detector deficit — the buffalo head-to-head appeared to localize the occlusion collapse to re-detection misses (R 0.504 vs 0.995). That comparison scored both detectors against a Golden-150 whose detection GT is 98.4% buffalo_l's own output, so it measures agreement with buffalo, not recall against truth, and the contamination runs in a known direction: buffalo's 0.995 is close to tautological and YuNet's 0.504 is inflated as a miss rate. FIRTRAIN-05's independent margin of +0.012 [−0.034, +0.057] is consistent with a much smaller or absent gap. 8 · If 512D helps, is 768D or 1024D worth it? No

Premise check first: 512D does not increase accuracy — §1's evidence (FaceNet Table 5) shows 128D ≥ 512D within noise at the same backbone; 512 buys identity-packing headroom. The question "if 512 helps, why not 1024" therefore starts from a false premise, and the answer past 512 is actively negative:
  • Distance concentration / retrieval instability (bruch-vector-retrieval distilled, Beyer et al.): as ambient dimension grows, pairwise distances concentrate — "every point becomes an ε-nearest-neighbor" — and ANN recall/latency degrade. What governs searchability is intrinsic dimensionality of the face manifold, which does not grow because the FC head got wider; extra coordinates are redundancy the index must fight.
  • Dimensionality curse (zezula-similarity-search distilled, pp.7–8): coordinate index structures "either become slower than naive linear scan or use too much space" in high d. pgvector HNSW RAM/latency scale ~linearly in d — 1024D doubles the 512D bill for zero measured benefit.
  • Packing math: CosFace's bound bites when identity count ≫ dim. Our roster is O(10²)–O(10³); even a 1M-identity training set is comfortably served by 512. FR literature has no 768/1024 win to point at; industry teacher models (buffalo w600k_r50) are 512.
  • If more capacity is ever wanted, spend it on backbone depth, training data quality (MLDATA-10 degradation matching), and loss design (AdaFace) — not head width. Ceiling: 512D.

14 · Can InsightFace inference guide/steer in-house training? Eval-side only — keep it out of the training loop

19 · What replaces WIDER FACE as a detector training corpus? v5 — first-party measurement, 2026-07-28

Headline: Among the candidates evaluated (table in §19a), Open Images V6/V7 is the largest face-box corpus whose annotations carry no NC or ND term — CC BY 4.0, attribution to Google LLC required — and the only one with exhaustively-annotated splits that make its own mismatch measurable. Its images are a separate licence surface: CC BY 2.0 per-image, per-photographer attribution, and Google explicitly disclaims warranty of per-image status. Acquired and measured 2026-07-28: 1,037,710 train face boxes over 331,627 images (non-exhaustive protocol, 3.13 faces/image), plus 22,602 boxes on the exhaustive val+test splits (1.79–1.83 faces/image). The measurement produced a corrective finding that governs how it may be consumed: train's IsOccluded and val/test's IsOccluded are not interchangeable — established; why — not established (§19c). Unlike §§1–18 this section is our own measurement over the actual files, not a research summary; see the caveat on what "first-party" does and does not mean in the evidence inventory.

19a · Why Open Images, and what was rejected

  • Distribution fit ([MLDATA-10]: match training degradation to measured target statistics). WIDER FACE sits at 12.2 faces/image (human-annotated GT); Open Images val/test sit at 1.79–1.83 (human-annotated GT); train sits at 3.13 under its non-exhaustive protocol. The ACX deployment figure of 2.73 is not the same kind of number: it is YuNet-apparent faces/image at threshold t=0.30 v7 — the manifest records detector.score_threshold = 0.3; every earlier statement of "t=0.030" in this program was a transcription error, uncorrected for sensitivity and specificity (benchmarks/manifests/detections-yunet-t030.json, 646 images / 1,763 detector boxes). Per [AUDIT-01/02] a detector's positive fraction is not prevalence, so it may not be compared directly against annotation GT without a measurement model. The honest form of this argument is weaker still than v5's and v6's. v7 correction The WIDER gap is 4.5× (12.2/2.73), not "a full order of magnitude" — and 4.5× is inside the range a threshold change on YuNet can manufacture, so it does not survive any plausible error rate. Neither the coarse gap nor the finer 1.79-vs-2.73-vs-3.13 ranking survives, and no [MLDATA-10] degradation-matching claim can be made until the deployment corpus is human-counted on a sample. That count is a task, not a footnote.
  • Licence — annotations. WIDER FACE is CC BY-NC-ND, banned by FIR-7's own policy (§7). Open Images annotations are CC BY 4.0: no NC, no ND, but attribution is a live obligation — credit Google LLC, link the licence, and state that changes were made, on any derivative annotation set or model card. ~90% of V7 boxes are human-drawn.
  • Licence — images, which is the harder surface. Images are listed as CC BY 2.0 per image, requiring per-photographer attribution, and Google states it makes no representations or warranties regarding the licence status of each image and that the consumer must verify each one. So the corpus is not "commercially clean" as acquired — it is clean at the annotation layer and conditionally clean at the pixel layer. gate A per-image licence verification pass plus an attribution manifest is a binding pre-ingest requirement before any pixel is trained on or redistributed. Annotation-only analysis (everything in §19b/§19c) does not trip this; training does.
  • Rejected ACI-Institute/faces4coco — boxes are yoloface (YOLOv3 trained on WIDER FACE) output over COCO, cut at conf ≥ 0.7. Last commit 2019-11-27. Grounds, in order of strength: (1) [MLDATA-08] — detector-harvested boxes need a post-hoc stratum audit nobody has run; (2) the harvest bias is directional and known: a conf ≥ 0.7 cut on a WIDER-trained detector preferentially deletes the occluded/tiny/profile regime this program exists to improve, which is the [MLDATA-09] failure mode — though we have not measured the deletion rate against a lower cut, so "verbatim" was too strong and is withdrawn; (3) circularity, as below. v5 correction An earlier draft asserted that MIT on the release files "does not launder the upstream NC/ND terms," i.e. that NC/ND reaches through a WIDER-trained detector into numerical boxes over COCO pixels. That is stated more confidently than §14 states the same legal question for buffalo distillation ("no settled case law on NC licences reaching outputs, but the licence text controls"). Holding both is motivated reasoning. The reach-through question is unsettled; conservative exclusion of WIDER-trained teachers is our policy, and should be argued as policy.
  • Rejected HapKoM/coco-faces — same detector-harvested defect, same three grounds. Last push 2019-06-13.
  • Both would re-import the Golden-150 circularity (369/375 = 98.4% of its "ground truth" is buffalo_l's own output) at 59k-image scale — the same [EVAL-15] contamination §14 refuses for the embedder, arriving through the corpus instead of the loss.
  • The search frame, named. v5 The v5 first draft claimed Open Images was "the only" corpus of its kind on the strength of two GitHub rejections. That is a universe claim with no stated universe — [AUDIT-07] — and is withdrawn. The candidates actually evaluated are: WIDER FACE (CC BY-NC-ND — excluded by policy), faces4coco and coco-faces (detector-harvested, above), COCO keypoints 2017 (retained as a complement, §19d), and Open Images V6/V7. The defensible claim is "largest clean-annotation candidate among those evaluated", and completing that table is open work.
  • Note canon names no detector corpus and has no dataset-licensing rule family. It supplies the selection procedure ([MLDATA-01] name the sampling frame, [MLDATA-06/07] stratum reporting, [MLDATA-08] detector-harvested sets need a post-hoc stratum audit, [MLDATA-09], [MLDATA-10]) — not the answer. 19c · Corrective finding: train's IsOccluded is not interchangeable with val/test's binding constraint mechanism unidentified

What is measured. Validation and test differ on occlusion by Δ = 0.64pp against SE(Δ) ≈ 0.71pp — sampling-compatible, i.e. no detectable difference, which is weaker than the "agree to within 0.6pp" an earlier draft claimed and weaker than treating 0.6pp as a calibrated agreement bound. Both differ from train by ~18pp overall and ~21pp composition-matched. Three checks were run. They do not do equal work, and an earlier draft claimed they "rule out the benign explanations" — withdrawn. What each actually establishes:

  • decisive Composition is excluded. Occlusion rate is flat across crowd size in every split, so train's higher faces/image cannot account for the gap. On single-face images — identical composition by construction — train reads 53.91% [53.66, 54.17] against val 32.61% [30.60, 34.63] and test 32.04% [30.88, 33.21]. Train's per-bucket range is 48.5–53.9%; the exhaustive splits' is 20.2–34.8%, trending mildly downward with crowd size. This check is clean and it kills one specific rival: the crowd-composition account of the rate gap.
  • descriptive Train's size signal is attenuated ~4.3×. On single-face images, both exhaustive splits show occluded faces markedly smaller than unoccluded ones (ratio 0.685 [0.607, 0.773] and 0.683 [0.636, 0.733]), which is physically sensible since distant faces are more often partly hidden. Train reads 0.927 [0.914, 0.940]. Attenuation is ×4.31 [3.80, 4.57] against validation and ×4.33 [4.24, 4.46] against test — both intervals exclude ×1 by a wide margin, so the magnitude is real and not an artifact of three point estimates. But this is a single confounded proxy: areas are normalized (a function of framing, FOV and aspect, none stratified), and train's size support is compressed relative to val/test (single-face mean 0.107 vs 0.163), which can flatten coupling mechanically. It measures that something differs. It does not identify a label-threshold mapping.
  • provenance, not a check The gap is concentrated in one annotation flow — and one sub-slice matches. 99.14% of train face boxes carry Source=xclick (50.40% occluded, ratio 1.06). The remaining 0.86% (activemil, n=8,901) reads 31.32% — which is validation's 31.05% and test's 31.69%, near-exactly. v5 correction An earlier draft reported this slice at 26.2% (a denominator error, §19b) and concluded "neither reproduces the val/test signature, so there is no clean sub-slice to fall back to." On the rate, that is wrong: activemil reproduces it. It does not reproduce the size-discrimination signature (ratio 0.97 vs 0.683–0.685). So the corrected reading is narrower and more useful: the rate excess is an xclick-flow phenomenon, which is real evidence about annotation process — but this is provenance, not a test of whether the underlying latent is shared, and n=8,901 at 0.86% of train is a lead for audit, not a supervision set.

Corroborating direction: train also reports lower truncation (5.1% vs 6.8/7.4%) and 6× lower group_of (0.4% vs 2.7%), plus the -1 unannotated level that val/test lack entirely — consistent with a different attribute rubric plus crowds individuated into many boxes rather than collapsed into group boxes.

Mechanism: unidentified. v5 — this is a downgrade from the v5 first draft That draft concluded train's flag was "not a different quantity so much as a differently calibrated one" — same latent, shifted operating point — and dismissed the population rival on the grounds that "harder images should sharpen the size/occlusion coupling, not flatten it." That rebuttal is withdrawn. It assumes hardness means small or distant faces. Scale-independent object occlusion — hands, phones, masks — raises occlusion prevalence at every size and flattens the size coupling, which is precisely the observed pattern, and it is also the regime this program actually cares about (cf. pewter_hollow_271.jpg). At least four mechanisms predict what we see, and nothing measured here distinguishes them:
  1. Calibration — one latent, a lower firing threshold in the xclick flow.
  2. Different image populations — train is not exhaustively annotated and is not a random sample of the val/test distribution; if it carries more scale-independent object occlusion, both the rate excess and the flattening follow with no annotation difference at all.
  3. Proposal-stage selection on box size, compressing train's size support and flattening coupling mechanically.
  4. Rubric difference — self-occlusion and pose scored differently from object occlusion.
What settles it: exhaustively re-annotate a few hundred train images under the val/test rubric and compare against their shipped labels — a dual-label sample identifies the mapping directly. It is the cheapest decisive experiment in this section and it is unfunded.

Why the program does not need the mechanism. The operational rule below follows from the measured rate gap and the documented protocol difference alone, under any of the four mechanisms. Non-interchangeability is established; the explanation is not. This section is deliberately left as a strong constraint with an open cause rather than a closed story.

Two consequences, both binding:
  1. Train is not exhaustively annotated, so its unlabelled regions are not background. Standard detector training treats every unmatched anchor as a negative, which injects false negatives precisely in the small/occluded regime — [MLDATA-09] by another route. Training on it requires positives-only supervision with ignore-regions, which is a training-loop engineering cost, not a data cost.
  2. You cannot supervise on train's occlusion flag and evaluate on val/test's. Occlusion-stratified training against train labels would optimise a quantity the benchmark does not report — which quantity is unknown (§19c), and that uncertainty is itself the reason not to do it. Three options, in ascending cost: (i) use train boxes as geometry only — no occlusion stratification; (ii) stratify on a physically-derived proxy computed from the boxes themselves (box area, IoU overlap with neighbouring face boxes) so both sides use one definition; (iii) hand-annotate an occlusion stratum on a val/test-sized sample. This is the [MLDATA-08] post-hoc stratum audit falling due, and it lands on a corpus we did not harvest.

Secondary mismatch worth carrying: matched on single-face images, train's mean face box is ~1.6× smaller in area than val/test's (0.107 vs 0.163 pooled). Train still skews small relative to its own eval splits — an [MLDATA-06/07] stratum-reporting obligation on any result trained from it — but far less than the unmatched aggregate (3×) suggested.

19d · Harmonising with the full-body COCO standard

  • COCO complements rather than competes. person_keypoints_train2017.json keypoints 0–4 (nose, eyes, ears) are facial and human-annotated, so face regions derived from them do not carry the detector-harvested circularity that disqualifies faces4coco.
  • Body prior as search-space reduction. Keypoints 5/6 (shoulders) + 11/12 (hips) bound a torso, constraining face search to the region above it — this is the §11 person→face cascade with labelled supervision instead of an off-shelf person detector, and it is the mechanism that makes a case like pewter_hollow_271.jpg (all but part of one eye occluded by a phone) tractable.
  • Candidate hard-occlusion positives v5 — downgraded from "free". An instance with labelled shoulders/hips but all facial keypoints v=0 is a plausible person present, face not visible case, with human provenance and a definition more stable across corpora than IsOccluded. But v=0 means "not labelled", not "occluded" — the causes include occlusion, out-of-frame, annotator skip, and protocol not requiring the point. Treating the whole set as occlusion GT repeats the §19c error one corpus over. Required before use: draw a sample, audit the actual cause distribution, and report the fraction that are genuinely face-invisible. If that fraction is high this is the most promising route around §19c(ii); until it is measured, it is a hypothesis.
  • COCO is per-image licence-tagged, therefore filterable — unlike WIDER's all-or-nothing. But the "clean" pool is not homogeneous and an earlier draft collapsed it: license ∈ {4,5,7,8} is id 4 = CC BY 2.0, id 5 = CC BY-SA 2.0, id 7 = no known copyright restrictions, id 8 = US Government Work. SA Id 5 carries ShareAlike, which propagates to adapted material and is a materially different commercial risk from plain BY — it must be split out and either disclosed or excluded by policy, not silently banked as "clean". Ids 6 (BY-ND) and 1–3 (NC variants) are out. Reported split: 69.0% NC, 5.1% BY-ND, 26.1% in {4,5,7,8} = 30,836 images, 16,513 with a person, 33,193 head-bearing instances ("head-bearing" = person instance with ≥1 labelled keypoint among 0–4). Class mapping: COCO person → /m/01g317. unreplicated Unlike §19b, these COCO counts are not backed by persisted tooling — no script, no pinned annotation-JSON revision, no per-id breakdown. They are provisional until re-derived the way §19b was.
  • Same caveat, different route: only 127,517 of 262,465 COCO person instances (48.6%) carry any labelled facial keypoint. Keypoint-derived faces are not exhaustive face ground truth either, so the ignore-region requirement from §19c(1) applies to COCO too.
