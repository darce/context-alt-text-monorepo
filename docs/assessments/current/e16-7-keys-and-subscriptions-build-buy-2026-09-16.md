# E16-7: API keys and subscription self-service — build/buy assessment

> **Current APP-1 recommendation (2026-09-19):** [launch decision and source-book grounding](app-portal-launch-recommendation-2026-09-19.md) recommends Clerk identity, retained local API-key management and Polar Starter. It supersedes open-ended vendor selection and keys-only/later-billing scope for APP-1. The analysis below is retained as dated prior art; it is not evidence of implementation.

Date: 2026-09-16  
Status: planning decision; E16-7 is still a draft, and billing is a later scope

## Decision and boundary

Keep recognition API-key storage, issuance, validation, and revocation in the existing Python service. Buy customer identity (Clerk, subject to the E16-7 verification spike) and subscription management (Polar, subject to the later billing plan). Build a small tenant portal to join these systems. The WordPress plugin continues to hold an installation's key; a portal cannot silently update a key provided by `wp-config.php` or a filter.

The differentiating operation is tenant-scoped recognition. Delegating each request's key verification to a gateway would add a vendor dependency and a migration while the existing store already hashes random keys, records expiration and revocation, and supports multiple keys per tenant. This is a conditional decision, not an assertion that in-house code is free. Measure operator time, incidents, and required features against vendor cost before renewing it. Zuplo or Unkey becomes worth reconsidering if credential support and recovery exceed the cost of their integration and exit path.

Clerk authenticates a person; it does not select a tenant from an untrusted request. Polar handles checkout, payment methods, invoices, cancellation, and plan changes. The service owns the tenant-to-identity and tenant-to-billing mappings and decides entitlement locally. The hosted [Polar customer portal](https://polar.sh/docs/features/customer-portal/introduction) already supplies the subscription UI; `app.altcontext.com` should link to it rather than duplicate payment forms. Polar provides [customer state](https://polar.sh/docs/integrate/customer-state) and [webhook validation and redelivery](https://polar.sh/docs/integrate/webhooks/delivery) for synchronization. Vendor capabilities and prices must be verified again when that later slice starts.

## Evidence and limits

- The existing `api_keys` repository can find active hashes, classify expired/revoked keys, list by tenant, create, revoke, and track last use. `api_key_admin_service.mint_api_key` creates a 43-character random token, hashes it, and leaves commit to its caller. See `apps/prototype-description-service/recognition/infrastructure/repositories/api_key_repository.py` and `recognition/application/services/api_key_admin_service.py`.
- `docs/scopes/e16-7-tenant-selfserve-key-panel-scope.md` and `docs/tasks/16.0/E16-7-tenant-selfserve-key-panel-task-plan.md` cover operator-provisioned customers and keys. The existing scope accepted immediate revocation and downtime; this assessment changes routine rotation to bounded overlap.
- `docs/epics/v0.3.1/saas-foundation-epic.md` still describes a new business database as owner of tenant and key records. E16-7 explicitly deviates toward the live recognition database. Reconcile this before implementing billing or moving the key authority; never run two writable sources of truth.
- The prior demo key incident exposed operational fragility after a database reset. It does not by itself prove that outsourcing verification would fix restoration or WordPress configuration.

## E16-7 acceptance and resilience requirements

1. **Durable authority.** Back up tenants, key hashes, identity links, rotation records, and audit evidence off the service host. Test point-in-time recovery through the latest revocation using retained WAL, or replay an independently stored append-only revocation journal before accepting traffic. A plain older snapshot can re-enable a revoked credential and is insufficient by itself. Separate recognition-data reset privileges from customer credential authority. Record the recovery owner and measured recovery time.
2. **Stable identity.** Use a verified primary-contact email once to claim an operator-provisioned tenant, then persist a unique `(issuer, subject) → tenant_id` binding. Subsequent sessions resolve by that binding. Email changes or account replacement use an audited operator recovery path; an email claim alone must not silently transfer control. Check ownership before every key read and mutation. `/admin*` remains inaccessible on public vhosts.
3. **Routine rotation with overlap.** Lock and authorize the named active key. Reserve the idempotency key and old-key rotation in the database, mint the replacement, and shorten the old key's remaining validity to at most seven days, without extending an earlier expiry. Preserve its revocation field until the explicit revoke action. Show the new raw key once and show the old key's cutoff time. A replacement gets a fresh lifetime based on the old key's original lifetime policy; an unexpiring old key yields an unexpiring replacement. A retry replays metadata, never the secret. A customer who loses the one-time response can rotate the new active key again; the UI must say this plainly. Direct emergency revoke takes effect immediately. Test an old WordPress installation during overlap and after cutoff.
4. **Atomic evidence.** Commit rotation, old-key cutoff, and audit evidence together. A failed audit insert rolls back the mutation. Make distinct concurrent requests against the same old key result in one winner and a clear conflict. Alert on repeated invalid credentials and failed portal actions without logging raw keys.
5. **Customer handoff.** For a WordPress option, paste the replacement and run Test Connection before the old key's cutoff. For `wp-config.php` or filter provisioned installs, show deployment instructions and the deadline; the setting is correctly read-only. Warn before a direct revoke that would leave the tenant without a working key.

## Separate subscription slice

E16-7 must remain a bounded key-panel task. A later task must define checkout, billing identity, entitlements, usage/quota enforcement, and account recovery. Key authentication should identify the tenant; a locally stored entitlement should decide plan and access, so subscription changes do not force key replacement. Define cancellation at period end, failed-payment grace, suspension, and reactivation as explicit state transitions. Suspended customers must retain billing recovery access.

Verify webhook signatures, persist and deduplicate events before acknowledging them, tolerate out-of-order delivery, and reconcile periodically with the billing provider. A checkout redirect alone cannot grant access. Keep provider calls off the recognition request path and specify bounded stale-state behavior. Keep customer contact and mappings exportable so a provider change has an executable exit.

## Decision tests and reconsideration

Before E16-7 release: restore customer identity/key state from backup in a drill; prove a revoked key does not become valid; exercise overlap, concurrent rotation, lost one-time response, WordPress option and constant installs, and a Clerk outage without stopping valid recognition calls. Before billing release: replay duplicate and out-of-order webhooks, then reconcile a missed event and verify cancellation and failed-payment recovery. Track median operator minutes per onboarding/rotation, credential incidents, restoration time, and key-management spend. Revisit the build decision if these stay materially worse than a vendor migration plus operation.
