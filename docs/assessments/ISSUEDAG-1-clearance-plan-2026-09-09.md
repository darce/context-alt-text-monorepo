## Method (heuristics canon, graph lexicon)

1. **Components before paths (GRPH-06, GRPH-16).** Findings are grouped into fix units by the file prefixes a fix must touch; the cut is placed at seams no other unit needs to cross (for example `appError.ts`/`http.ts` versus their hook consumers, or `recognition-service.sh` versus `sync-demo.sh`). Units are the DAG nodes.
2. **Colour the conflict graph (GRPH-09).** Two units conflict iff they own a common path. Each conflict was resolved either by re-cutting ownership or by turning it into a precedence edge (same file, sequenced). The build asserts the residual conflict graph is edgeless, so the chromatic number is 1: any two ready nodes may run at the same time. The only binding resource is the remote worker count W.
3. **Edges only where data moves (GRPH-32, GRPH-33, GRPH-34).** 13 precedence edges, each with a stated reason (a landing SHA, an API contract, a shared file). Parallel nodes that share a type or contract carry an explicit contract clause in the lane brief instead of an edge. Formatting a file two lanes need is edge work folded into the owning lane, not a node.
4. **Critical path and width (GRPH-01, GRPH-31, Pinedo CP rule).** Topological order, ASAP levelling (width = max antichain = 17), longest remaining chain per node, then a list schedule with W workers that always starts the ready node with the longest remaining chain. Two documented tie-breaks: `GATES-HARNESS` first (its remote-agent orphan fix raises W for every later wave) and in-flight `GUIDESEED-1` stages next (WIP-first).

## Per-lane protocol

1. Implementation on the remote OCI runner: `grok-remote` / `grok-4.6` / `high` (first-turn exit → one retry at another effort, then `codex-remote` `gpt-5.6-luna` `max` on the same brief). One writer per worktree; lane test command green on the runner.
2. Review: `codex-remote` `gpt-5.6-luna` effort `max` (no `speed`), read-only, FINDINGS JSON under `ISSUEDAG-1-<NODE>-R-nn`. Fix high and medium (grok lane); defer low and lint findings to the next wave.
3. Harmonize: `gpt-6-astra` `medium`, integration lenses only. Only high findings block the merge; medium/low go to the fast-follow queue.
4. Gate: `handoff_close_check(enforce=True)` on the lane branch, then a serialized merge queue into `main` in topological order (`merge_order` in `config/lane-orchestration/ISSUEDAG-1.json`), coordinated with PEER-CODEX. No push.
5. Closure of the original rows: after a lane lands on `main`, each cleared finding is updated on its source task (`fixed`, `verified_commit_sha` = landing SHA, evidence = lane report line); `NOT-A-DEFECT` lines become `wontfix` with the evidence; `DEFERRED`/`BLOCKED` lines stay `deferred` with the lane id in the notes. New lane findings are recorded under `ISSUEDAG-1`.
