## Problem

- A production DB reset leaves operators manually ferrying raw keys back to the WordPress site, the failure mode recorded in decision 6437.
- Tenants have no bounded self-serve path to see, rotate, or revoke their own recognition keys; the operator console is the wrong trust boundary for that workflow.
- A portal must not broaden the existing operator `/admin` surface or trust a client-supplied tenant identifier.
- Routine key rotation should allow a WordPress installation to switch keys before the old key stops working; lost one-time key display and customer-data restoration need explicit recovery paths.

## MVP scope

- Buy identity only: use Clerk; verify the Clerk session JWT server-side in FastAPI and require a verified primary email claim on every session. Lowercase + trim it before the first lookup via a new `SqlAlchemyTenantRepository.find_by_primary_contact_email(email)` method; `tenants.primary_contact_email` is nullable with a unique index. Atomically bind the verified `(issuer, subject)` to the operator-provisioned tenant. Resolve subsequent requests through that binding, never by a fresh email lookup or client-supplied tenant id; a changed verified email does not change the binding. A replacement Clerk account requires an audited operator recovery procedure; the spike confirms the exact verified-email claim. [SEC-01][WEB-08][CARD-10]
- Browser sign-in happens on Clerk's hosted sign-in page (Clerk Account Portal) configured for `app.altcontext.com`; Clerk sets its standard `__session` cookie (the Clerk session JWT) on the app domain. Every portal request reads the JWT from `__session` (browser) or `Authorization: Bearer <jwt>` (API clients), using the same verifier, checking the cookie first and the bearer second, and never accepting both. An unauthenticated browser `GET /portal/` redirects with 302 to the Clerk sign-in URL with `redirect_url` back to `/portal/`; an unauthenticated API request returns 401 `invalid_session` JSON. No Clerk JS runs on the panel page itself; only the Clerk-hosted sign-in page runs Clerk's script. [SEC-01][WEB-16]
- Require an operator-provisioned tenant with a non-NULL primary contact email before the first portal claim. Provision from inside the prod API container on the VM (`python -m scripts.provision_customer --env prod ...`) or through a tested remote wrapper; the laptop-side `make provision-customer ... ENV=prod` cannot reach the prod DB. No signup, billing, or tenant creation in this MVP. [CARD-10]
- If no tenant matches the normalized email at first claim, if the tenant email is NULL, or if the tenant is already bound to another subject, return `403 tenant_not_eligible`, create no tenant, and write one row to the new pre-tenant `portal_auth_events` table: `id uuid pk`, `clerk_sub text not null`, `email_hash text nullable` (sha256 of the normalized email), `outcome text not null` in {`tenant_not_eligible`, `email_unverified`, `claim_missing`}, and `created_at timestamptz`. `email_hash` is NULL exactly for `claim_missing`. The table is pre-tenant and RLS-exempt. A separate `portal_identity_links` table stores unique `(issuer, subject)` and unique `tenant_id` bindings with a link timestamp; it is RLS-exempt for pre-tenant lookup and writable only through the portal claim/recovery service. [SEC-01][DATA-13][WEB-08]
- A missing email claim returns `403 claim_missing`, and an unverified email claim returns `403 email_unverified`; each writes one `portal_auth_events` row with the corresponding outcome.
- The verifier accepts only `RS256` (rejecting `alg=none` and `HS*`), requires `iss` equal to the configured Clerk frontend API issuer, requires `azp`/`aud` in the configured allow-list (`https://app.altcontext.com`), rejects passed `exp` and future `nbf`, and validates the signature against cached JWKS refreshed on an unknown `kid`. A failed token check returns 401 `invalid_session`, writes no `portal_auth_events` row because unverified claims are untrusted, and emits only a structured log. [SEC-01]
- Each `403` `tenant_not_eligible`, `email_unverified`, or `claim_missing` event is written through a separate short-lived `get_portal_auth_event_session` with no tenant context against the RLS-exempt table and committed before the 403 is raised; the request session is never used. If that write fails, the request still returns 403 and the failure is logged at ERROR. [DATA-13]
- Ship the keys panel only: authenticated tenants can see their own key metadata (`id`, `created_at`, `last_used_at`, `expires_at`, `revoked_at`), rotate, and revoke. [PG-02][ARCH-13]
- Keep the existing hashed `api_keys` store and `api_key_admin_service`; `api_keys` and `tenants` are intentionally outside `TENANT_TABLES` because recognition auth must look up a key before a tenant is known. Use existing `SqlAlchemyApiKeyRepository.list_for_tenant` for portal reads, and a tenant-predicated, row-locked key lookup for every mutation. The portal never uses a tenant id supplied by the client. [ARCH-13][WEB-08]
- Make routine rotation atomic with bounded overlap. Under an old-key row lock, authorize an active named key, INSERT the `portal_rotations` reservation FIRST, mint one `secrets.token_urlsafe(32)` replacement, and set the old key's `expires_at` to `min(existing expires_at, now + 7 days)` (or `now + 7 days` if no earlier expiry). Leave `revoked_at` NULL until explicit revoke. Derive the new key's fresh `expires_in_days` from the old key's original `created_at` to `expires_at` lifetime before shortening it; if the old key did not expire, neither does its replacement. Preserve `rate_limit_tier`. Commit mint, cutoff, reservation, and audit together; show the replacement once and the exact old-key cutoff. Enforce both `UNIQUE (tenant_id, idempotency_key)` and `UNIQUE (tenant_id, old_key_id)` so concurrent distinct requests cannot rotate the same old key twice. On the idempotency unique violation, roll back, open a NEW transaction, re-apply tenant context and safety timeouts, then re-read the committed winner: equal fingerprint replays metadata with `raw_key: null, replayed: true`; different fingerprint returns 422. An old-key conflict with a different idempotency key returns 409. Catch only these named constraint violations. Foreign keys return 404; revoked, expired, or already rotated keys return 409. A lost one-time response is recovered by rotating the new active key shown in metadata with a fresh idempotency key; no raw key is replayed. Multiple active keys remain allowed. [API-02][DATA-13][WEB-08][WEB-16]
- Make revoke irreversible (`revoked_at = now()`), check that the addressed key belongs to the resolved tenant before the write, and record an audit event with the Clerk subject and email. `audit_events.actor` is `varchar(100)`: for portal actions store `clerk:<sub>` (Clerk `sub` is ≤ 64 chars; truncate-with-hash if longer) and put `{ "clerk_sub": ..., "email": ..., "sid": ... }` in the existing `payload` JSONB; never widen the column. Dual control is judged excessive for self-serve; the audit trail is the compensating evidence. [WEB-08][SECD-04]
- Preserve the existing SHA-256 hash behavior for the 43-character random token as a known, accepted risk; changing the hashing scheme is out of scope. [PHP-09]
- Separate the portal router from the Tailscale-only operator router and its shared `X-Admin-Token`; the portal uses the same DB role with repository-level isolation and never reuses the admin dependency or token. [SECD-02][CARD-10]
- Treat identity as a generic subdomain to buy (Clerk) and key issuance as supporting/core functionality to build (the thin tenant-scoped router). [DOM-01]
- Read the recognition DB directly instead of the planned business DB from E16-1. This is an explicit greenfield deviation: there are no production users, so the existing hashed key store is the narrowest source of truth for this MVP. [DOM-01][SECD-02]
- On Clerk JWKS failure, fail the portal loudly with a distinct 503 while keeping the recognition API path independent of Clerk; use bounded JWKS timeouts and cached verification keys. [CARD-07][RES-13]

## Architecture sketch

- Add a FastAPI `portal` router under `/portal`. It MUST NOT depend on `get_session`/`get_optional_session` or take a request tenant id. A new `deps/portal_session.py` verifies the Clerk JWT, requires the verified email claim for first claim, and resolves `(iss, sub)` through `portal_identity_links` thereafter. A missing binding may claim only one unbound tenant matched by normalized verified primary-contact email; use a transaction and unique constraints to stop concurrent or competing claims. A changed email does not remap an existing binding. Set `app.current_tenant` to the resolved tenant id before tenant-scoped writes; no request header or body can override it.
- Browser sign-in is the Clerk-hosted Clerk Account Portal configured for `app.altcontext.com`; Clerk sets the standard `__session` session JWT cookie on that app domain. The shared verifier reads `__session` first for browser requests or `Authorization: Bearer <jwt>` second for API clients and never accepts both. Unauthenticated browser `GET /portal/` returns 302 to the Clerk sign-in URL with `redirect_url` back to `/portal/`; unauthenticated API requests return 401 `invalid_session` JSON. The panel page contains no Clerk JS; only the hosted sign-in page runs Clerk's script. [SEC-01][WEB-16]
- Cookie-authenticated `rotate` and `revoke` mutations require BOTH a per-session CSRF token (HMAC of the verified Clerk `sid` claim with a server secret, rendered as a hidden form field or sent as `X-CSRF-Token`) and `Origin`/`Referer` matching `https://app.altcontext.com`. Bearer-authenticated requests skip CSRF because bearer credentials are not ambient. Any service-set cookie uses `Secure; HttpOnly; SameSite=Lax`. [WEB-08][SEC-01]
- Endpoints:

  | Endpoint | Behavior |
  | --- | --- |
  | `GET /portal/` | Render the authenticated keys panel; without browser auth, redirect 302 to Clerk sign-in with `redirect_url` back to `/portal/`. |
  | `GET /portal/me` | Return the verified Clerk subject/email and resolved tenant summary. |
  | `GET /portal/keys` | Return only the resolved tenant's key metadata: `id`, `created_at`, `last_used_at`, `expires_at`, and `revoked_at`; an unauthenticated API request returns 401 `invalid_session` JSON. |
  | `POST /portal/keys/{id}/rotate` | Require `Idempotency-Key`; authorize an active named key for the resolved tenant (404 foreign; 409 revoked, expired, or already rotated), mint a fresh-lifetime replacement, shorten only the old key's expiry to at most seven days, and return the raw value only once plus the old cutoff. Cookie auth also requires CSRF and same origin; bearer auth skips CSRF. |
  | `POST /portal/keys/{id}/revoke` | Authorize the key's `tenant_id` before the irreversible revoke and audit write. Cookie auth requires the CSRF token and matching `Origin`/`Referer`; bearer auth skips CSRF. |

- `api_key_admin_service.mint_api_key` only mints, hashes, and persists (it does not commit or audit). `revoke_key_atomic`, `RevokeOutcome`, `UnknownKeyError`, and the `audit_events` writes currently live in `recognition/interface_adapters/http/routers/admin.py` (`revoke_key_atomic` at ~L267); Slice 0 moves them into `api_key_admin_service.py` behind transactional `rotate_api_key(session, *, key_id, tenant_id, actor)` and `revoke_api_key(session, *, key_id, tenant_id, actor)` functions that write the `audit_events` row in the same transaction and roll back the key mutation if the audit insert fails. For portal rotate/revoke actions, `audit_events.actor` is `varchar(100)`, so store `clerk:<sub>` (Clerk `sub` is ≤ 64 chars; truncate-with-hash if longer) and put `{ "clerk_sub": ..., "email": ..., "sid": ... }` in the existing `payload` JSONB; never widen the column. Successful portal actions write `audit_events` with the resolved `tenant_id`; pre-tenant auth failures write `portal_auth_events` because `audit_events.tenant_id` is non-null. Reuse `SqlAlchemyApiKeyRepository.list_for_tenant` and the existing auth outcome vocabulary (`invalid_key`, `expired`, `revoked`, `tenant_mismatch`) where the recognition API validates keys. The portal's Clerk dependency is separate from `_require_auth_impl`, and the portal router never imports the admin router module [SECD-02].
- Use `SqlAlchemyApiKeyRepository.list_for_tenant` for portal reads and a tenant-predicated ownership lookup under row lock for mutations. All `portal_rotations` access goes through new `TenantScopedRotationRepository(tenant_id)` methods with tenant predicates built in. `api_keys`, `tenants`, and pre-tenant `portal_identity_links` remain outside `TENANT_TABLES` (RLS-exempt); portal authorization must therefore enforce tenant ownership structurally before every read or write. [ARCH-13][WEB-08]
- Add durable `portal_rotations` in `001_identity_schema.py`: `id`, `tenant_id`, `idempotency_key`, request fingerprint, old/new key IDs, and `created_at`, with unique `(tenant_id, idempotency_key)` and `(tenant_id, old_key_id)`. The reservation INSERT precedes mint and expiry shortening. `new_key_id` is nullable only until the same transaction records the minted key; committed rows must have it. Give rotations FORCE RLS. On an idempotency conflict, roll back and reapply tenant context in a new transaction before replay; metadata includes `old_expires_at`, never a raw key or `revoked_at` for routine rotation. Reuse the existing idempotency normalization pattern. [API-02][DATA-13]
- Add `portal_auth_events` directly in `001_identity_schema.py` with `id uuid pk`, `clerk_sub text not null`, `email_hash text nullable` (sha256 of the normalized email, never the raw email), `outcome text not null` in {`tenant_not_eligible`, `email_unverified`, `claim_missing`}, and `created_at timestamptz`; enforce `CHECK ((outcome = 'claim_missing') = (email_hash IS NULL))`. It is pre-tenant, not tenant-scoped, and RLS-exempt like `api_keys`; register it in `EXPECTED_SCHEMA_TABLES` and keep rows indefinitely because volume is negligible. Write it through separate short-lived `get_portal_auth_event_session` without tenant context and commit before each 403; if the write fails, still return 403 and log at ERROR. [DATA-13]
- Add `portal_identity_links` as a third raw-SQL table with `tenant_id uuid fk tenants UNIQUE NOT NULL`, `issuer text NOT NULL`, `subject text NOT NULL`, `linked_at timestamptz NOT NULL`, and `UNIQUE (issuer, subject)`. Register all three new tables in `RAW_SQL_TABLES` and `EXPECTED_SCHEMA_TABLES`, only `portal_rotations` in `TENANT_TABLES`; create constraints, heal and downgrade behavior, and extend the four schema-truth surfaces. [DATA-13][WEB-08]
- The implementation lane must update `docs/workbay/contracts/security.md` in the same slice with portal cookie + bearer auth transport, the CSRF rule, `/portal/*` request/response schemas including the replay envelope (`raw_key: null, replayed: true`), error codes and 404/409/422 semantics (404 for a foreign key, 409 for an already-revoked key, 422 for an idempotency-fingerprint conflict; `invalid_session`, `csrf_failed`, `tenant_not_eligible`, `email_unverified`, `claim_missing`), and `Idempotency-Key`/`X-CSRF-Token` headers. [DATA-13][SEC-01][WEB-08]
- Serve a minimal server-rendered HTML page that reuses the escaped f-string pattern of `admin_console.py::render_console` — extract the shared HTML-escaping helpers into `recognition/interface_adapters/http/html_render.py` (Slice 0 refactor item) and build `portal_console.py::render_portal(...)` on them. No Jinja2, no StaticFiles, no htmx, no npm build; the existing `test_admin_mount.py` module ban stays in force and a twin assertion is added for the portal mount. The new page is served on the new `app.altcontext.com` Caddy vhost. The vhost needs an operator-created DNS A record, proxies portal requests to the service, and keeps `respond 404` for every `/admin*` path. Existing API vhosts retain their `/admin*` 404 behavior. [WEB-16][CARD-10]
- Keep operator admin mutations Tailscale-only with the single shared `X-Admin-Token`; a portal principal can touch only its own tenant's keys. [SECD-02][CARD-10]
- Clerk commitment is gated on a spike proving the JWT verification path, organization/email claim shape, and outage behavior before durable purchase or deployment evidence is accepted. [CARD-06]
- Eval registration is not included here: `packages/workbay-system/config/evals/` does not exist in this checkout, so the eval spec lives beside this scope note; registration in the eval runner is a follow-up owned by another lane.

## Non-functional intake

- Latency: propose p95 ≤ 500 ms for `GET /portal/keys` and `POST /portal/keys/{id}/rotate`; this is an assumption for plan-draft validation.
- Idempotency: `POST /portal/keys/{id}/rotate` requires `Idempotency-Key`; a retry must not double-execute and must replay the prior rotation result. [API-02][DATA-13]
- Clerk outage: use a timeout and cached JWKS; return a distinct 503 from portal auth when verification cannot proceed, while `/analyze` with a valid API key does not call Clerk and remains available. [CARD-07][RES-13]
- Staleness: none expected for reads-after-writes; portal reads and writes use the same recognition DB.
- Scale: target tens of tenants; no capacity claim is made for 10× growth in this MVP.

## Success criteria

The RED lane adds a `require_postgres` fixture that FAILS (not skips) when `ACX_PORTAL_TESTS_REQUIRE_PG=1` and PostgreSQL is unreachable, applied to every DB-backed portal test. The eval gate fails on any skipped case.

1. **SC-1** — Cross-tenant key access through the portal returns 404 or 403 and never exposes the other tenant's key.
2. **SC-2** — An authenticated tenant sees its own key metadata—`id`, `created_at`, `last_used_at`, `expires_at`, and `revoked_at`—and a client-supplied tenant id cannot change the server-resolved tenant.
3. **SC-3** — Equal idempotency key and fingerprint mint exactly one replacement with the old rate tier and a fresh lifetime based on its original lifetime; replay returns metadata with no secret, and a different fingerprint returns 422.
4. **SC-4** — Rotation authorizes only an active key owned by the resolved tenant (404 foreign; 409 revoked, expired, or already rotated), keeps the old key valid only until `min(original expiry, now + 7 days)`, and does not set `revoked_at`; recognition accepts the old key before that cutoff and classifies it `expired` afterward.
5. **SC-5** — The raw key is shown exactly once in the first successful rotate response, is not re-shown on an idempotent replay, and never appears in application logs, audit rows, or URLs.
6. **SC-6** — Every `/admin*` request on the `app.altcontext.com` vhost returns 404.
7. **SC-7** — When Clerk JWKS is unreachable, the portal returns a distinct 503 while `/analyze` with a valid key still succeeds.
8. **SC-8** — Two concurrent rotate requests with the same Idempotency-Key and fingerprint produce exactly one new key and one old-key expiry shortening; the loser receives replay under re-applied tenant context. Distinct idempotency keys against the same old key yield one winner and a 409 loser. [API-02][RES-13]
9. **SC-9** — Cross-tenant test: tenant B cannot read or replay tenant A's `portal_rotations` row, at both repository and RLS level. [ARCH-13][SECD-04]
10. **SC-10** — A portal request carrying `X-Tenant-ID` for another tenant is served strictly as the Clerk-resolved tenant; the header is ignored (test asserts no cross-tenant rows returned). [SECD-02][WEB-08]
11. **SC-11** — Direct `POST /portal/keys/{id}/revoke` (200 → `revoked_at` set + `audit_events` row; 404 for a foreign key id; 409 if already revoked).
12. **SC-12** — `GET /portal/me` returns `{tenant_id, email, key_count}` for an eligible user and 403 `tenant_not_eligible` for an unmatched one, with a `portal_auth_events` row.
13. **SC-13** — Missing `email` claim → 403 `claim_missing` with a `portal_auth_events` row whose `email_hash IS NULL`; `email_verified=false` → 403 `email_unverified` with a hashed email in its row.
14. **SC-14** — The server-rendered page (`GET /portal/`) returns 200 HTML listing the tenant's keys with no `jinja2` in `sys.modules`.
15. **SC-15** — If the `audit_events` insert fails inside rotate, the key mutation rolls back and no `portal_rotations` row survives.
16. **SC-16** — Unauthenticated `GET /portal/` redirects (302) to Clerk sign-in; unauthenticated `GET /portal/keys` returns 401 `invalid_session`; a valid `__session` cookie and a valid bearer token each authenticate identically. [SEC-01][WEB-16]
17. **SC-17** — A cross-site form POST to rotate/revoke with a valid `__session` cookie but missing/mismatched CSRF token or foreign Origin is rejected 403 `csrf_failed` and no key changes. [WEB-08][SEC-01]
18. **SC-18** — Tokens with bad signature, wrong `iss`, wrong `azp`, disallowed `alg`, expired `exp`, or future `nbf` each return 401 `invalid_session` and write no `portal_auth_events` row. [SEC-01]
19. **SC-19** — Each 403 (`tenant_not_eligible`, `email_unverified`, `claim_missing`) leaves exactly one committed `portal_auth_events` row observable from a fresh connection after the response. [DATA-13]
20. **SC-20** — With `ACX_PORTAL_TESTS_REQUIRE_PG=1` and PostgreSQL stopped, the portal DB tests FAIL (not skip).
21. **SC-21** — A verified contact claims an unbound tenant once; subsequent sessions resolve by unique `(issuer, subject)` even after email changes, while a different subject claiming the same tenant receives 403. Concurrent claims cannot create two bindings.
22. **SC-22** — A lost first rotation response cannot reveal the secret through replay; the tenant can rotate the new active key with a new idempotency key, and a constant-provisioned install sees deployment guidance and the old-key cutoff.
23. **SC-23** — A customer-record restore drill confirms tenant/key/link/audit restoration and prevents a formerly revoked key from becoming valid; this is an operator release gate, not a unit-test-only claim.

SC-1 through SC-22 map to named tests in the adjacent eval spec. SC-23 requires a recorded restore drill before production exposure.

## Canon gaps

- no rule for shown-once/unrecoverable secret display semantics; no rule for JWT-to-internal-identity re-derivation beyond SEC-01.
