# APP-1: recommended launch path after the build/buy review

Date: 2026-09-19. Status: recommendation for planning review, not an accepted implementation baseline. This conclusion supersedes the open-ended vendor-selection sequence in the [earlier reassessment](app-portal-build-buy-reassessment-2026-09-19.md). Its commercial comparison remains evidence. Execution contract: [Plan 0001](../../plans/0001-app-altcontext-beta-clerk-polar-task-plan.md).

## Decision

**Proceed with a controlled free self-service beta, Clerk for human identity, the existing local API-key authority, and Polar Starter for paid conversion.** Build one complete customer journey and one payment adapter. Stop broad vendor comparison; reopen a specific choice only when the failure conditions below occur. Confidence is moderate: the code and public contracts support this direction, but account approval, actual integration effort and customer behavior have not been measured.

The working bottleneck is getting a qualified WordPress user from signup to an accepted caption and repeat use without founder provisioning. That is a diagnosis to test, not a measured funnel result. The product roadmap sells workflow, trustworthy records and support; hosted processing is an allowance/cost component. A more elaborate account platform or a cheaper card transaction does not by itself improve that outcome.

Buy login/recovery and financial subscription infrastructure. Extend the credential machinery already on the service's request path. Own the thin connection between them: tenant identity, authorization, beta grants, admission/usage accounting, and the customer journey. Human login and API-key verification are different responsibilities; retaining an existing random-token/hash verifier is not a proposal to build a password, OAuth or session system.

## Why this stack, and what would change it

| Decision | Evidence and incremental work | Counter-case / reopen condition |
| --- | --- | --- |
| **Polar Starter** | Hosted checkout/portal, sandbox, customer-state API and a no-monthly-fee entry tier fit one monthly offer. Existing GTM contracts already describe the required lifecycle. This is design reuse, not a claim that integration is shipped or fastest | Seller/product/payout approval fails, required lifecycle cannot be made correct in the bounded proof, or an existing approved competitor account demonstrably removes substantial work. Do not reopen for a small fee difference alone |
| **Clerk identity; start Hobby if required features fit** | Removes login/session/recovery plumbing. Stable issuer/subject maps to our tenant UUID. The browser SDK spike must prove the real session flow | Required security features exceed Hobby: price the necessary plan explicitly. A failed supported browser flow is an integration blocker, not a reason to invent auth |
| **Local tenant API keys** | Existing mint/hash/lookup/expiry/revoke path and plugin contract are reusable. New work is tenant-bound authorization, a small panel, atomic rotation and recovery. One DB transaction can coordinate cutoff/replacement/audit | Reopen Clerk managed keys if characterization invalidates reuse or the remaining credential work/support burden materially exceeds a proved managed alternative under the same accepted policies |
| **One existing customer-state authority** | Avoids migrating keys and introducing the unbuilt second Business API/database before learning. Restricted reset roles and tested backups are mandatory | Shared database cannot enforce reset containment or measured contention blocks the service: isolate the authority before beta. Colocation does not provide independent failure domains |
| **One monthly paid offer with an allowance** | Limits catalog, checkout and support states while retaining real paid conversion. No charge during beta | Repeated qualified demand demonstrates another required pricing unit; actual paid behavior, not feature requests, gates expansion |

Polar's [current pricing](https://polar.sh/resources/pricing) is not the old universally available 4% rate. Use Starter until actual volume justifies a paid plan. [Customer state](https://polar.sh/docs/integrate/customer-state) supports reconciliation; financial state remains Polar's truth and local access remains our policy. [Stripe Managed Payments](https://stripe.com/managed-payments) is a credible MoR alternative, not excluded as an old preview. Paddle remains a credible alternative, particularly where account fit or international economics are stronger. Dodo and Lemon Squeezy remain documented alternatives rather than additional integrations.

Clerk managed keys are inexpensive enough for a small beta; fees are not the reason to retain local keys. Its documented [verification API](https://clerk.com/docs/reference/backend/api-keys/verify) adds a request dependency, and create/update-based rotation leaves coordination work. Even a simpler two-key workflow still needs local tenant authorization, usage enforcement and installation guidance. Migrating authority now introduces work without demonstrated reduction in the next bottleneck. Conversely, a greenfield API without this installed credential path would make buying keys more attractive. The earlier guide/getSecret contradiction stays an unresolved vendor custody question; this recommendation does not claim to have tested it.

**Fallback procedure:** first identify the failed requirement, then select one matching alternative. Prefer Stripe Managed Payments when an eligible existing Stripe setup or required capability is the advantage; prefer Paddle when approval, coverage or international economics is the advantage. Compare only those candidates affected by the trigger. Keep one active billing adapter. Do not silently switch keys or relax revocation/isolation to meet a deadline.

## Execution recommendation

1. **S0 - settle the small contract.** Use this stack as the review recommendation. Record actual seller/payout eligibility, single-owner tenant mapping, one offer, cost ceiling, exact rotation policy and E16-7/E20-7 ownership. Repair the known worktree lifecycle setup before implementation. Numeric defaults in Plan 0001 remain proposals, not spending authorization.
2. **S1 - prove the chosen integrations.** Proposed two engineer-day discovery timebox for Clerk browser/JWT and Polar sandbox checkout -> verified inbox -> authoritative customer state -> cancellation/recovery, plus characterization of the existing key path. Record outcomes and remaining work. This is a feasibility checkpoint, not a promise to finish production billing in two days. A blocker triggers a targeted alternative test; otherwise stop vendor evaluation.
3. **S2/S3 - deliver a thin end-to-end path.** Durable tenant-bound keys and a self-service account/installation flow. Retain existing WordPress keys, local verification, named-key overlap rotation and separate emergency revoke. Prefer a tested standard PostgreSQL backup/WAL mechanism over a bespoke security journal when available; do not implement both merely for completeness. Unknown restore tails remain closed/remint as specified.
4. **S4/S5 - bound costs and complete paid conversion.** Enforce job allowances and worst-case compute reservations, then finish one Polar lifecycle and hosted portal. Billing code is sandbox-complete before the beta; production checkout stays disabled. Never create a paid subscription as a side effect of beta signup.
5. **S6 - run the learning cohort.** Recruit a proposed 10 users first, with capacity up to 20 after fixes; no card. Observe five sessions and record unassisted/assisted outcomes, first accepted caption, repeat use and support minutes. Repair the dominant failure before enlarging the cohort.
6. **S7 - opt-in paid release.** After readiness and approved price/allowance, offer explicit checkout to eligible users; no automatic charge or beta arrears. Record offers, purchases, cancellations, compute cost and support burden separately. Sandbox success proves plumbing; live opt-in purchases establish paid-demand evidence.

Keep original APP-SC-01..20. Proposed learning gates remain 8/10 unassisted first-caption activations and 5 repeat-day users in 14 days, with exact denominators. Also report accepted-caption outcomes separately: a successful API response is not proof of useful text. Numeric gates guide iteration, not statistically certain market validation. Choose a paid-conversion hypothesis and observation window before S7 offers; do not invent a universal conversion benchmark.

## Stop, simplify and reconsider

- Stop admission immediately for cross-tenant access, exposed secrets, unintended charges, revived revoked keys or failed compute-budget enforcement.
- If users stall at copy/paste/connection, fix that flow before buying a different credential store. If users cannot produce useful captions, focus on the publishing workflow and quality before adding portal features.
- Review actual support time after each cohort and monthly after paid release. Reopen key outsourcing when credential operations remain a material recurring burden after the largest UX defect is corrected; compare observed work, migration and outage/custody costs.
- Reprice payment vendors at the first paid-cohort review and meaningful volume/geography changes. Retain exportable mappings and a documented customer reauthorization path; a code adapter does not move payment credentials by itself.
- Defer multi-admin organizations, custom billing forms, per-seat/annual/overage catalogs, multiple payment adapters, generic API gateways, complex usage charts and new analytics infrastructure until a specific observed need justifies them.
