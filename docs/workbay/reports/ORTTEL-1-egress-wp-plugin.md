# ORTTEL-1 egress audit: WordPress plugin

The plugin has no automatic analytics, crash-reporting, license, or custom update-check client in the inspected source. Its main outbound traffic is authenticated requests to the configured recognition/description service, which is first-party when pointed at AltContext; the URL can also be configured to another HTTPS host. These requests carry image files and WordPress/site context when an operator or visitor starts recognition/description work, and service credentials accompany proxy requests. Package installation and explicit clicks on external links cause separate, conditional egress. Plugin assets and fonts are bundled locally; no runtime CDN or remote font host was found. `Telemetry::log_line()` writes to PHP's local error log and is not network telemetry.

## Recommended switches

- To stop plugin-to-service traffic, clear both the configured service URL and key, including deploy-time constants or filters. The settings URL option is `acx_recognition_url`; the API key option is `acx_recognition_api_key`. The saved URL can be blanked in Settings. Removing only the API key also makes authenticated proxy calls fail before transport, but clearing both avoids stale routing configuration.
- To disable face-identification analysis, set `acx_recognition_enabled` false in Settings. This gate defaults off. It does not disable image-description requests, which still upload images when invoked.
- To disable the anonymous public demo, leave `acx_public_demo_enabled` false (its code default) or set it false in WordPress options. This does not disable authenticated admin/CLI description calls.
- For development asset egress, unset `ACX_VITE_DEV_SERVER`; normal built assets are served from the plugin/WordPress site.
- For build and CI egress, use cached installs or approved npm/Composer mirrors. Package downloads are separate from runtime requests; Composer notification behavior remains unverified.
- For a strict no-egress deployment, apply network policy at the WordPress host for WordPress core update checks and any operator-configured remote service. The plugin has no global switch that blocks every host-level WordPress request.

## Gaps

- `node_modules` and Composer `vendor` were absent, and network access was unavailable. I could not inspect locked installed-package source for telemetry behavior. The manifests/locks contain no named analytics, crash-reporting, or Scarf SDK; `package-lock.json` lists optional `@opentelemetry/api` as a Vitest peer, which alone does not establish an active exporter. Package-manager telemetry and Composer's recorded Packagist notifications are therefore unverified.
- WordPress core updater traffic and payload were not audited because core source/configuration is outside the plugin tree. No plugin-specific update or license request was found.
- Any LLM/model-provider egress performed after requests reach the first-party recognition/description services is outside this plugin's code path and needs the service-side audit.
- Static code search cannot enumerate site-specific WordPress HTTP hooks, proxy rules, security plugins, or custom filters that may add or redirect traffic.
