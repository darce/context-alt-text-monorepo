## Specific answers

1. **Shared OCIR tag before production health:** Yes. `promote_gate` smoke-tests a digest-pinned image in a throwaway container, then `_ship_selected_env` moves the shared environment tag (`prod` is `:latest`) before `do_restart` and public `do_verify`. Thus the candidate has passed boot smoke, but the deployed canonical/public runtime has not yet passed health verification. If verification fails, `restore_env_tag_to_rollback` restores the captured digest of the image that was actually serving before this transaction, after checking that the current registry mapping is still this candidate or already the rollback digest. If restoration fails, the handler reports unknown state and exits; status 75 refuses to overwrite a newer mapping, while other failures do not proceed with runtime compensation.

2. **`ACX_TRAFFIC_FLIPPED` and edge exits:** It becomes `1` only after `flip_edge_alias next` returns successfully. After that, failures in candidate enablement, public health, canonical restart, candidate re-health, canonical health, image-ID verification, or the final canonical flip can return with traffic still on `*-api-next`. The public-health failure plus a failed canonical flip can knowingly leave an unhealthy candidate selected; later health/digest failures leave the candidate selected for recovery. The transaction wrapper attempts rollback, and interrupt cleanup consults the inflight marker. Separately, a nonzero result from `flip_edge_alias next` is ambiguous: the route may have changed before SSH failed, while the immediate error branch calls `abort_cutover_candidate` without first restoring/verifying the canonical route (N3).

3. **Rollback target ordering and overwrite:** `preserve_rollback_tag` reads the currently serving image ID/reference/digest and verifies a rollback tag before candidate build, SHA push, environment-tag promotion, sticky `.env` write, or restart. A later deploy with a different prior digest normally uses a different digest-derived rollback tag; if it sees the same prior digest, it republishes the same content. The short 12-hex rollback tag prefix is a theoretical collision surface, but the ordinary same-environment race is more dangerous through the mutable env tag/runtime/cutover state (N2). `assert_rollback_fence` refuses a stale rollback when the registry tag or runtime generation no longer matches this transaction.

4. **Second deploy to the same environment:** No stage provides a deployment-wide exclusion. The remote BuildKit lock covers only the build phase; the shared-tag lock covers individual promote/restore operations; `image_repo_resource claim` can replace the current owner ID. If a second deploy reaches restart while the first has `cutover-inflight`, it treats that marker as recoverable interruption and may restore canonical routing/drain the first candidate. Forward restart also stages its own digest under the VM-local mutable env tag without first requiring that OCIR's env tag still maps to that digest. See N2.

5. **Success inferred from silence:** The main artifact/health gates do not accept empty output as success: they check process status plus explicit digest, image-ID, route, or HTTP results. Some file-copy commands in `converge_runtime` are status-only (`ssh cat/cp` then return); they do not read back and hash-check the deployed compose/unit bytes. This is a limited positive-readback gap, but not a separate finding here because the copy command itself is exit-status checked and the later candidate probes exercise the runtime path.

## N2 — CONFIRMED — HIGH

- **Evidence:** `scripts/deploy/recognition-service.sh:1033-36`: `flock additionally serializes builder setup, bootstrap, prune, and the resource-heavy BuildKit phase`; `scripts/deploy/recognition-service.sh:1344`: `with_shared_tag_lock "${tag}" do_push_tag --locked "${tag}" "${source_digest}"`; `scripts/deploy/recognition-service.sh:1626-28`: `if action in ("claim", "clear"):` followed by `owner = uuid.uuid4().hex` and replacing `state`; `scripts/deploy/recognition-service.sh:3048-50`: `Found persisted inflight cutover for ${env}; recovering before a new candidate` and `recover_interrupted_cutover`; `scripts/deploy/recognition-service.sh:3298-300`: `remote_docker_with_config tag "${expected_digest}" "${expected_repo}:${env_tag}"`.
- **Mechanism:** Locks serialize only builder work, an individual mutable-tag operation, or one `.env` state write; none owns the full environment transaction through verify/rollback. A second claim replaces the first sticky-repo owner, and a second restart treats any inflight marker as interrupted without checking whether its transaction is still active. The forward restart also does not fence the env-tag mapping against another deploy.
- **Failure scenario:** Deploy A promotes digest A, then deploy B promotes digest B under the short tag lock. A can subsequently restart using digest A and report A healthy while OCIR `:latest` maps to B; B can also observe A's live inflight marker and restore canonical routing/drain A's candidate while A's process is still active. Final registry label and serving image can disagree.
- **Canon:** RES-10 applies: a stale transaction can still mutate shared state unless the target rejects it with a transaction-wide fencing token. CARD-15 also applies because interleaved rollback and cutover operations are not one reversible commitment.
- **Fix design:** Add an environment-scoped lock acquired by `_ship_selected_env` before `preserve_rollback_tag` and held through verification or completed rollback, using a persistent VM lock path such as `${ACX_DEPLOY_BACKUP_ROOT}/locks/deploy-${env}.lock` and transaction ID ownership. Make `image_repo_resource claim` refuse an unexpired owner, and make `recover_persisted_cutover` verify that the owning transaction is abandoned before draining it. Before `do_restart`, check the registry env tag still maps to `ACX_CANDIDATE_DIGEST_REF`.
- **Regression test:** `scripts/deploy/tests/test_recognition_deploy.py`; run two fake deploy processes against one env and assert the second blocks/fails before rollback capture or promotion, recovery never drains a live owner's candidate, and the final OCIR env digest equals the running canonical image digest.

## N3 — CONFIRMED — HIGH

- **Evidence:** `scripts/deploy/recognition-service.sh:3113-20`: `printf 'env=${env}\\ndigest=${digest}\\ntimestamp=%s\\ntransaction=${ACX_DEPLOY_TRANSACTION_ID}\\nnext_unit=${next_unit}\\nstatus=traffic_on_next\\n' "$(date +%s)" | sudo tee "$backup_root/${env}/cutover-inflight" >/dev/null` precedes `sudo mv -f -- "$tmp" Caddyfile`; `scripts/deploy/recognition-service.sh:3334-41`: `if ! flip_edge_alias "$env" next; then`, `if ! abort_cutover_candidate "$env"; then`, and `ACX_TRAFFIC_FLIPPED=1`; `scripts/deploy/recognition-service.sh:2894`: `if sudo systemctl stop $(remote_quote "${next_unit}"); then`.
- **Mechanism:** A lost SSH response makes the result of the edge mutation unknown. The persistent inflight marker records that the flip may have happened, but the direct error branch does not consult it or restore Caddy before stopping/removing the candidate. The later transaction rollback may restore the route, but there is a window with Caddy still targeting a stopped candidate; if that restore also fails, 502s persist until recovery succeeds.
- **Failure scenario:** Candidate is healthy; Caddy reloads the `*-api-next` route; the SSH connection drops before returning status. The caller sees flip failure, a new SSH attempt successfully stops the candidate, and edge restoration then fails. Public traffic points to the stopped candidate.

- **Regression test:** `scripts/deploy/tests/test_recognition_deploy.py`; fake the remote flip as “apply next route, then exit 255” and assert the candidate remains running until canonical route restoration is verified, including when the first restore attempt fails.

## N4 — CONFIRMED — MEDIUM

- **Evidence:** `scripts/deploy/recognition-service.sh:1037`: `build_dir="${REMOTE_BUILD_DIR%/}-${sha:0:12}-$(date +%s)-${BASHPID:-$$}-${RANDOM}"`; `scripts/deploy/recognition-service.sh:1053-55`: remote generation directory creation; `scripts/deploy/recognition-service.sh:1124`: `remote_build_cleanup_generation "${build_dir}" "${command_timeout}"`; `scripts/deploy/recognition-service.sh:299-300`: the interrupt handler only recovers cutover and purges OCIR credentials.
- **Mechanism:** The remote build context is local to `do_build_remote`, and the EXIT/signal trap does not know its path. Ctrl-C, terminal loss, or SSH interruption after mkdir/rsync bypasses the normal cleanup call and leaves the generation tree under the VM's `/tmp` build prefix.
- **Failure scenario:** Repeatedly cancel remote builds after context sync. Stale full build contexts accumulate until the VM's free-space floor rejects later pulls/builds; enough residue can also pressure the production-serving host's root filesystem.
- **Canon:** CARD-15 applies because the temporary remote filesystem mutation has a normal-path undo but no interruption undo.
- **Fix design:** Record the active path in `ACX_REMOTE_BUILD_GENERATION_DIR` before remote mkdir. Have `deploy_interrupt_cleanup` attempt bounded cleanup for that path, then clear the variable; add a remote TTL reaper for generations left by workstation/SSH loss where no trap can complete.
- **Regression test:** `scripts/deploy/tests/test_bounded_remote_build.py`; simulate interruption after mkdir and after rsync, and assert the cleanup path is attempted and the generation directory is absent (or eligible for the TTL reaper).
