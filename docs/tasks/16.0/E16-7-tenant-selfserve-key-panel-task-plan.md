## Objective

Give an operator-provisioned tenant a bounded, server-rendered portal at `/portal` where an eligible Clerk-authenticated contact can inspect its own recognition-key metadata, rotate an active key with at most seven days of overlap and exactly once per idempotency key, and revoke a key immediately when needed. Persist a stable verified identity binding and give a lost-secret recovery path. Preserve the Tailscale-only `/admin` boundary and recognition API behavior while adding tenant isolation, pre-tenant auth-event evidence, and a runbook for provisioning, restoration, and Clerk configuration.

## Problem Statement

After a production database reset, operators must ferry raw recognition keys back to WordPress manually. Tenants have no self-serve way to inspect, rotate, or revoke their own keys, while the existing operator console is Tailscale-only and must not become the tenant trust boundary. A client-supplied tenant identifier or an unverified Clerk claim must never select a tenant, and pre-tenant rejection evidence needs a separate RLS-exempt audit surface.

## Workflow Principles

- Authenticate and validate claims before deriving tenant context; authorization is based on the resolved tenant, never on request input.
- Keep untrusted-token failures (401), trusted-but-ineligible contacts (403), CSRF failures (403), and verifier outages (503) distinct and observable without leaking tenant existence [SEC-01][DATA-13].
- Reserve rotation idempotency and old-key ownership first, then commit mint, old-key expiry shortening, and audit in one transaction. Replay metadata never includes the raw secret; direct revoke is separate [API-02][DATA-13].
- Keep each slice independently reviewable as behavior plus proof. RED names the portal tests for SC-1 through SC-22 and SC-24, SC-25, SC-26, SC-29, SC-30, and SC-31. Slice 0 names SC-27 and SC-28. The ops lane records SC-23.
- Preserve the existing `/admin` response mapping and auth contract while putting tenant behavior in a separate portal router; do not import the admin router into portal code [SECD-02].
- Prefer narrow repository methods with structural tenant predicates over caller-provided tenant arguments [ARCH-13][WEB-08]. Portal key access binds the resolved tenant at construction (`TenantBoundApiKeyRepository`); it does not pass a caller-supplied tenant id into `SqlAlchemyApiKeyRepository.list_for_tenant`.

## Terminology

- **Resolved tenant**: the tenant selected from an existing `(issuer, subject)` link, or atomically claimed once from the normalized, verified Clerk email; it is the only tenant identity accepted by portal handlers.
- **Portal auth event**: a committed pre-tenant row for `tenant_not_eligible`, `email_unverified`, or `claim_missing`; invalid JWTs do not create one [DATA-13].
- **Rotation reservation**: a `portal_rotations` row inserted before mint and cutoff update; unique `(tenant_id, idempotency_key)` and `(tenant_id, old_key_id)` constrain retries and competing rotations.
- **Rotation cutoff**: the old key remains active until the earlier of its original expiry and seven days after rotation; `revoked_at` stays NULL unless explicitly revoked.
- **Replay envelope**: a successful retry response containing prior rotation metadata with `raw_key: null` and `replayed: true`.
- **Ambient cookie**: the Clerk `__session` credential sent by a browser; unlike a bearer token, it requires CSRF and same-origin checks for mutations.
- **Portal mutation context**: frozen dataclass `PortalMutationContext(tenant_id: UUID, idempotency_key: str, request_fingerprint: str, clerk_sub: str, email: str, sid: str)`. Service APIs take this plus `key_id: UUID`; handlers only build it.

## Target Outcome

An eligible Clerk contact reaches a minimal HTML key panel at `GET /portal/` through the Clerk-hosted sign-in flow. The server verifies `__session` first or `Authorization: Bearer <jwt>` second, rejects a request carrying both with `401 invalid_session` before any token is verified (no `portal_auth_events` row), and resolves the tenant from a stable `(issuer, subject)` link. Only the first claim may use normalized verified email to bind an unbound provisioned tenant. The portal exposes only that tenant's key metadata (full history, including revoked rows), runs no Clerk JS, and never trusts a tenant id from a header, query, or body [SEC-01][WEB-08][WEB-16].

The API surface is:

- `GET /portal/`: authenticated HTML panel; unauthenticated browser requests return 302 to Clerk sign-in with `redirect_url=/portal/`.
- `GET /portal/me`: exactly `{tenant_id, email, key_count}` for an eligible user. The Clerk subject is not returned.
- `GET /portal/keys`: only `id`, `created_at`, `last_used_at`, `expires_at`, and `revoked_at` for the resolved tenant, including revoked rows (`TenantBoundApiKeyRepository.list(include_revoked=True)`).
- `POST /portal/keys/{id}/rotate`: requires `Idempotency-Key`; 404 for a foreign key, 409 for revoked, expired, or already rotated key, and 422 for a fingerprint conflict. The first success returns one raw key and the old-key cutoff; an equal-fingerprint replay returns metadata with `raw_key: null, replayed: true` [API-02][WEB-08]. Handlers build `PortalMutationContext`; the service owns the transaction.
- `POST /portal/keys/{id}/revoke`: one conditional `UPDATE ... RETURNING` bound to the resolved tenant; 404 for a foreign or missing key, 409 when already revoked, and a same-transaction audit event only when a row was returned.

Invalid or missing verification returns API JSON 401 `invalid_session`; missing or unverified email on any session, unmatched verified email on first claim, or a competing subject claiming a bound tenant returns 403 with `claim_missing`, `email_unverified`, or `tenant_not_eligible` and commits exactly one corresponding `portal_auth_events` row (bulkheaded short-lived session; insert failure still returns that 403 and logs ERROR without email/token material). A JWKS outage returns 503 and leaves valid-key `/recognition/analyze` independent [DATA-13][CARD-07][RES-13]. Cookie mutations additionally require HMAC CSRF and same-origin evidence; bearer mutations do not.

## Proposed Solution

Implement a separate `/portal` router and dependency stack around a server-side Clerk JWT verifier. The verifier is `PyJWT[crypto]` (`jwt.PyJWKClient` + `jwt.decode`): cookie-first/bearer-second transport, reject both credentials before verify, and validate RS256, issuer, authorized parties, `exp`, `nbf`, and cached JWKS. `apps/prototype-description-service/api/main.py::create_app` mounts the portal router and calls `apps/prototype-description-service/recognition/interface_adapters/http/deps/clerk_jwt.py::validate_portal_settings (new)` so missing `ACX_CLERK_ISSUER`, `ACX_CLERK_JWKS_URL`, `ACX_CLERK_AUTHORIZED_PARTIES`, or `ACX_PORTAL_CSRF_SECRET` fails at boot. `apps/prototype-description-service/recognition/interface_adapters/http/deps/portal_session.py::get_portal_session (new)` resolves an existing `(issuer, subject)` identity link first. For an unlinked subject only, it verifies and normalizes the email, finds an unbound tenant through `SqlAlchemyTenantRepository.find_by_primary_contact_email (new)`, and inserts the link in one transaction under unique constraints. An existing link remains authoritative across email changes; a competing subject cannot claim it. `get_portal_auth_event_session (new)` writes trusted-claim rejection outcomes on a short-lived session that is never the request session. An operator recovery procedure owns account replacement and audits any link change.

Keep key access structurally bound: portal handlers construct `TenantBoundApiKeyRepository` with the server-resolved `tenant_id`. The wrapper exposes no method that accepts a caller-supplied tenant id. Reads use `list(include_revoked=True)` so `/portal/keys` returns full history including revoked rows with `revoked_at` set. `TenantScopedRotationRepository (new)` owns tenant-predicated rotation operations. Add raw-SQL `portal_rotations`, `portal_auth_events`, `portal_identity_links`, and RLS-exempt `portal_revocation_journal` in `001_identity_schema.py`; give only rotations FORCE RLS; add the outcome CHECK on `portal_auth_events`. Move transactional revoke/audit behavior into `api_key_admin_service.py` as a tenant-aware service extracted from `admin.py::revoke_key_atomic`, using frozen `PortalMutationContext` for portal callers; each successful revoke/rotate inserts a `portal_revocation_journal` outbox row in the same transaction. Extract escaped f-string helpers for dependency-light `portal_console.py::render_portal (new)`.

Rotation locks and authorizes the active old key, inserts the reservation before mint, gives the replacement a fresh lifetime derived from the old key's original `created_at` to `expires_at` interval (or no expiry if the old key had none), and shortens only the old key's expiry to `min(original expiry, now + 7 days)`. It leaves `revoked_at` NULL, preserves `rate_limit_tier`, records `new_key_id` and audit evidence `{clerk_sub, email, sid}`, and commits them together. A failed audit insert rolls back all changes. An idempotency constraint violation rolls back; a new transaction reapplies tenant context and either replays metadata without the raw secret or returns 422 for a different fingerprint. A different idempotency key for the same old key returns 409 through a distinct old-key unique constraint.

Direct revoke is one conditional `UPDATE api_keys SET revoked_at=now() WHERE id=:id AND tenant_id=:tenant AND revoked_at IS NULL RETURNING id`. Zero rows → re-read → 404 (foreign/missing) or 409 (already revoked). Audit row inserted only when a row was returned, in the same transaction. `/admin` maps `already_revoked` to 200 with no second audit row; `/portal` maps it to 409. A lost first rotate response can be recovered by rotating the replacement key listed in metadata with a new idempotency key [API-02][DATA-13][WEB-08][SECD-04].

The rotation table is raw SQL with `id uuid` primary key, non-null tenant/old-key foreign keys, `idempotency_key`, SHA-256 `request_fingerprint`, nullable `new_key_id`, `created_at`, `UNIQUE (tenant_id, idempotency_key)`, and `UNIQUE (tenant_id, old_key_id)`. The auth-event table retains `id`, `clerk_sub`, nullable SHA-256 `email_hash`, constrained rejection outcome (`CHECK (outcome IN ('tenant_not_eligible','email_unverified','claim_missing'))` plus the existing `claim_missing`/NULL hash check), and `created_at`; never store a raw email. The identity-link table has `tenant_id uuid fk tenants UNIQUE NOT NULL`, `issuer text NOT NULL`, `subject text NOT NULL`, `linked_at timestamptz NOT NULL`, and `UNIQUE (issuer, subject)`. It is RLS-exempt for pre-tenant lookup. Recovery changes to it require an audited operator action [DATA-13][WEB-08]. The revocation journal is RLS-exempt raw SQL with `id uuid` primary key, `tenant_id`, `key_id`, `action` CHECK `IN ('revoke','rotate')`, `created_at`, and nullable `shipped_at`; host-side shipping credentials create-only JSONL objects in OCI Object Storage (no overwrite/delete), and read credentials live only with the operator. No WAL archiving exists; this independent copy is the MVP durability path (DDIA).
