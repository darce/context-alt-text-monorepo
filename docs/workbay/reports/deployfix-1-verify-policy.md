## D4 — CONFIRMED — HIGH

- **Evidence:** `scripts/deploy/recognition-service.sh:4528` — `expected_sha="$(git -C "${REPO_ROOT}" rev-parse "${GIT_REF}")"`; `:4572` — `actual_sha="$(printf '%s' "$body" | python3 -c 'import json,sys;d=json.load(sys.stdin);print(d.get("commit_sha") or d.get("git_commit_sha") or d.get("version") or "")' 2>/dev/null || true)"`. `read_remote_image_repo` reads `.env`'s `ACX_IMAGE_REPO` (`:4214-4218`); `verify_running_image_matches_deployed` accepts any tag/digest in that repository (`:4292` — `"${expected_repo}:"*|"${expected_repo}"@*)`). Standalone dispatch is `verify)       do_verify "${1:-dev}" ;;` (`:4930`).
- **Mechanism:** `do_verify` resolves `GIT_REF` from the local checkout at verification time and compares its 8-character prefix with the public `/health` payload. The standalone path has no VM release SHA/digest receipt or immutable expected image identity; remote `.env` supplies only the image repository. The environment tag appears in a diagnostic reference, not as a recorded deployed SHA.
- **Failure scenario:** A deploy starts at `c580e4da`, then local `HEAD` advances to `6ddc5863` before verification while prod still serves the healthy, smoke-fenced `c580e4da` image. `do_verify` expects the new local HEAD and rejects the actual deployed release. The same mismatch makes standalone `deploy-verify-prod` report failure whenever its checkout is not the release that the VM is serving.
- **Canon:** `OBS-12` and `CARD-11` — verification must observe the actual deployed release state; a local checkout that can move during a deploy is a proxy, not evidence of the VM's release.
- **Fix design:** Capture `ACX_CANDIDATE_SHA` once from the selected build ref before building, and use that SHA/digest pair throughout deploy verification. Add `write_deployed_release_receipt` to atomically write `/opt/acx-backend/<env>/deployed-release.json` on the VM with `sha`, digest-pinned image reference, and UTC commit time. Call it after `do_restart` has completed its candidate and canonical probes but before post-deploy verification; snapshot the old receipt with the topology backups and restore it on rollback. Every runtime image mutation writes the receipt: automatic rollback (`restore_runtime_and_edge`) and manual `do_rollback <env> <rollback-id>` (recognition-service.sh:3778) write the restored SHA and digest only after the restored runtime passes its health and image-ID checks. Standalone `do_verify` should read that receipt, require it to be fresh and valid, compare `/health` SHA and `read_running_api_image_id` against its SHA/digest, and fail loudly when the receipt is missing. This makes the VM record the source for `deploy-verify-prod`.
- **Regression test:** Add `test_do_verify_uses_vm_release_receipt_when_local_head_differs` to `scripts/deploy/tests/test_recognition_deploy.py`. Give the mocked checkout a different HEAD from the mocked receipt and assert standalone verify passes only when both the public SHA and running image ID match the receipt; assert a missing receipt fails closed.

## D5 — CONFIRMED — HIGH

- **Evidence:** Deploy gates rollback on any nonzero verification result: `scripts/deploy/recognition-service.sh:4073` — `if ! ACX_VERIFY_EXPECT_LOCAL=1 do_verify "$env"; then`; `:4074` — `handle_failed_verification "$env" "Deploy"`. The candidate digest is retained at `:3277` — `ACX_CANDIDATE_DIGEST_REF="${expected_digest}"`; `verify_running_image_digest` compares the running image ID with the ID resolved from the expected digest (`:2609-2615`). In `do_verify`, image checking is inside the SHA-match branch: `:4580` — `if [[ "${actual_sha:0:8}" == "${expected_sha:0:8}" ]]; then`; `:4621` — `if ! verify_running_image_matches_deployed "$env"; then`. The handler unconditionally requests rollback at `:3969` — `if restore_env_tag_to_rollback "$env" 1; then`. Rollback ordering is `systemctl restart` at `:3651-3654`, then `restore_edge_backups` at `:3657`, then candidate drain at `:3669`, then public rollback verification at `:3674`.
- **Mechanism:** The SKEW branch in `do_verify` runs before `verify_running_image_matches_deployed`, so a healthy HTTP 200 response with a mismatched SHA never compares the running container ID against `ACX_CANDIDATE_DIGEST_REF`. After retries, `do_verify` returns failure and `handle_failed_verification` restores the previous image without distinguishing an incorrect expectation from an incorrect running artifact. During that restoration, the canonical unit is restarted before edge recovery and before the next unit is drained; prod traffic can therefore reach a stopped or starting canonical API.
- **Failure scenario:** The incident's candidate digest is still the digest that passed smoke and the API returns HTTP 200, but the local expected SHA advances after restart. The verifier reports SKEW, the handler restores the previous image, and requests to the canonical route receive 502 while `acx-prod` stops and starts. The incident log's two rollback verification 502s align with this route gap; the code does not stage and health-check a rollback candidate before disrupting the canonical service.
- **Canon:** `CARD-07` — a healthy candidate with a bad expectation must produce a clear expectation error, while a bad artifact or unhealthy service must produce a visible rollback path; collapsing both into “verification failed” confuses the success and failure channels.
- **Fix design:** Have `do_verify` return structured failure classes using `actual_sha`, `http_code`, `ACX_CANDIDATE_DIGEST_REF`, and the result of `verify_running_image_digest`. Preserve the real status in `do_deploy`, `do_promote`, and scoped producer-preparation callers instead of using `if !` when branching on it; return status `2` from a healthy-candidate expectation error without treating it as success or calling the rollback handler. Use this classification table:

  | Running digest | `/health` | Version | Result |
  | --- | --- | --- | --- |
  | Equals candidate | 2xx healthy | Mismatch | Expectation error; no rollback; distinct exit code `2` and message `VERIFY EXPECTATION ERROR` |
  | Differs from candidate or cannot be established | Any | Any | Roll back; report artifact identity mismatch |
  | Any | Unhealthy after the health retry budget | Any | Roll back; report unhealthy service |
  | Equals candidate | 2xx healthy | Matches expected SHA | Pass |

  Only artifact mismatch and exhausted health failures should call `handle_failed_verification`; the healthy-candidate expectation error should return its distinct status directly. For actual rollbacks, factor the staged cutover sequence from `do_restart` into a reusable digest-pinned helper and use it from `restore_runtime_and_edge`: start and probe the rollback digest in the next unit, flip Caddy to it, restart and probe canonical, flip back only after canonical health and digest pass, then drain the next unit. This keeps a known-good service serving throughout rollback.
- **Regression test:** Add `test_healthy_candidate_with_version_mismatch_does_not_rollback` to `scripts/deploy/tests/test_recognition_deploy.py`. Stub HTTP 200, a different SHA, and a running image ID equal to `ACX_CANDIDATE_DIGEST_REF`; assert exit code `2`, the expectation-error message, and zero calls to `restore_env_tag_to_rollback`. Add a rollback-order assertion that the rollback digest is healthy behind the next route before canonical restart and that the candidate is drained only after canonical health succeeds.

## D7 — CONFIRMED — MEDIUM

- **Evidence:** Each of `verify_restored_runtime`, `probe_cutover_api_health`, `probe_canonical_api_health`, and `do_verify` reads the same defaults: `ACX_VERIFY_ATTEMPTS:-5` and `ACX_VERIFY_SLEEP:-5` (`scripts/deploy/recognition-service.sh:2622-2623`, `:3201-3202`, `:3229-3230`, and `:4532-4533`). `verify_retry_sleep` adds jitter to that shared base (`:4322-4329`). `verify_live_gpu_snapshots` instead has a single `ACX_GPU_SNAPSHOT_GATE_TIMEOUT_SECONDS:-60` deadline (`:4442-4446`), but `do_verify` runs it inside the outer verify loop and sleeps the shared `sleep_s` on failure (`:4632-4635`). The pre-promote boot smoke has its separate `ACX_SMOKE_TIMEOUT` budget (header `:100`, resolver use `:2254`).
- **Mechanism:** One `ACX_VERIFY_ATTEMPTS`/`ACX_VERIFY_SLEEP` setting controls probes with different roles: candidate admission, canonical restart readiness, post-deploy public verification, and rollback verification. The GPU snapshot contract has its own per-call timeout but inherits the public verification loop's retry count and sleep.
- **Failure scenario:** With the incident overrides `ACX_VERIFY_ATTEMPTS=12` and `ACX_VERIFY_SLEEP=10`, a setting intended to lengthen post-deploy observation also lengthens both cutover health gates and rollback verification. A deterministic version skew then consumes all 12 attempts and roughly 2.5 minutes of retries before the rollback path starts.
- **Canon:** `CARD-07` — probes with distinct purposes should have distinct, legible outcomes and budgets; a single shared knob hides which gate consumed the time.
- **Fix design:** Introduce independently validated attempt/sleep pairs: `ACX_CUTOVER_HEALTH_ATTEMPTS`/`ACX_CUTOVER_HEALTH_SLEEP`, `ACX_CANONICAL_HEALTH_ATTEMPTS`/`ACX_CANONICAL_HEALTH_SLEEP`, `ACX_VERIFY_ATTEMPTS`/`ACX_VERIFY_SLEEP`, and `ACX_ROLLBACK_VERIFY_ATTEMPTS`/`ACX_ROLLBACK_VERIFY_SLEEP`. Pass each pair to `verify_retry_sleep`; keep `ACX_GPU_SNAPSHOT_GATE_TIMEOUT_SECONDS` as the checker transport deadline and make its retry behavior explicit rather than inheriting public health settings. Keep `ACX_SMOKE_TIMEOUT` separate for boot smoke. Validate each knob at the entry to its own probe and log the selected attempts and sleep budget.
- **Regression test:** Add `test_health_probe_budgets_are_independent` to `scripts/deploy/tests/test_recognition_deploy.py`. Set distinct attempt counts for cutover, canonical, verify, and rollback; stub the probes and assert each is called only its own configured number of times, while a GPU checker timeout does not change any health-probe count.

## D11 — CONFIRMED — MEDIUM

- **Evidence:** After an HTTP 2xx response, `do_verify` extracts the reported version and directly retries a mismatch: `scripts/deploy/recognition-service.sh:4561` gates on 2xx; `:4572` parses `actual_sha`; `:4644` — `warn "SKEW: ${env} runs ${actual_sha:0:8}, expected ${expected_sha:0:8} (attempt ${attempt}/${max_attempts}; warm-up retry)"`; `:4645` calls `verify_retry_sleep`. Only after the loop does it emit diagnostics and fail (`:4652-4654`).
- **Mechanism:** Any nonempty version mismatch on a healthy response is labeled warm-up and retried without checking whether the running digest is the candidate. The decision is “retry until `max_attempts`” rather than a classification of the observed release. A retry can pass without this script restarting anything only if a later request observes a different backend or version payload that matches; a fixed image cannot change its baked commit SHA through waiting alone.
- **Failure scenario:** Prod repeatedly returns HTTP 200 and the same candidate `c580e4da` while local `HEAD` is `6ddc5863`. Each observation is treated as warm-up; only the final attempt fails, causing the D5 rollback. If a concurrent route change makes a later request hit a backend reporting `6ddc5863`, the current loop can instead pass without a restart by this process, even though its earlier observations came from a different release.
- **Canon:** `OBS-04` — a healthy service with a deterministic version mismatch is a false warm-up alarm; repeating it trains operators to ignore real mismatch reports.
- **Fix design:** In `do_verify`, classify a 2xx response together with the running digest before retrying. If the digest equals the candidate and the version differs, terminate immediately as the D5 expectation error (exit `2`, no rollback). If the digest differs, classify it as an artifact mismatch for rollback. Reserve retries for transient HTTP/health failures, using the dedicated health budget from D7; do not label version skew as warm-up.
- **Regression test:** Add `test_healthy_version_skew_is_terminal_not_warmup` to `scripts/deploy/tests/test_recognition_deploy.py`. Return the same HTTP 200 mismatched SHA on every mocked request with the running digest equal to the candidate; assert one `/health` request, the terminal expectation-error classification, no “warm-up retry” message, and no automatic rollback.
