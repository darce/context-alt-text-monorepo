## Outcome and settled decisions

Deliver a new LocalWP site, suggested name `altcontext-fir-dev`, using an authenticated, isolated remote development service with a **working 512D in-house FIR path**, a matching isolated vector database and real self-hosted remote descriptions. Keep the existing 128D YuNet/SFace stack as a reproducible comparator. Per the 2026-09-21 operator choice, it is an optional integration baseline, not a prerequisite for the AuraFace512 development route; use the current [next-wave DAG](../scopes/next-wave-gpu-ui-fir512-dag.md). The final development milestone is not satisfied by stopping at 128D or merely changing a database setting.

The 512D route starts with exact-artifact qualification of AuraFace-v1 through ONNX, using the in-house runtime/identity pipeline without InsightFace runtime or buffalo weights. A 512D artifact is a development target, not a guarantee of better recognition. If artifact review fails, stop that candidate and record the replacement decision. Never silently substitute a different model. Detector improvement and encoder capacity are separate workstreams; **detection is the first quality experiment**.

Already settled: LocalWP plus isolated remote service/DB; no public WP endpoint; self-hosted VLMs only; reuse FIR-16/VLM-6; paired clustering visualizations; `codex-remote`, `gpt-5.6-luna`, `max` for junior work; codemap discovery and semantic `handoff.db` prior art. Do not ask these questions again. No PG19 prerequisite, production cutover or broad weight-training campaign belongs to this implementation wave.

Functional completion, measured quality and production approval are distinct. A working 512D development route can be delivered and honestly marked unqualified for production when quality evidence is inadequate. It must still pass artifact, isolation and functional correctness checks. Retain an explicit 128D comparison endpoint; never create an automatic cross-model fallback.

## Three technical boundaries that must stay explicit

**Detector versus recognizer.** A missed face never reaches SFace/AuraFace or clustering. Independently annotate whole images; require one-to-one spatial matches, not matching face counts. Current `face_metrics.py::detection_pr` permits a count-only fallback when `matched_faces` is missing; S3a must reject that fallback in new detector comparisons while preserving labeled historical replay. Report clean, mask, sunglasses, hand/object and mixed cells, size/pose controls, FPPI and uncertainty. Reference boxes plus reference landmarks are a combined geometry intervention when both change; do not call the resulting gain pure detector improvement. The withdrawn 0.504/0.995 comparison is not valid independent recall evidence.

**128D versus 512D storage.** Each model space includes exact weights, preprocessing/alignment contract, normalization and distance, not just dimension. Provision a fresh 512D database/store and verify all applicable vector/centroid schema plus API/worker manifests. Re-extract from pixels and reconstruct derived clusters; do not import SFace vectors, buffalo vectors or stale cluster IDs. Suggested resource names such as `acx-dev-fir-512` are proposals subject to collision checks. Keep 128D resources separate and explicitly selectable for comparison. Reuse the installed PostgreSQL/pgvector version after compatibility checks; PG19 cannot repair representation or detection quality.

**Diagnosis versus acceptance.** Legacy data supports diagnosis. Candidate operating points are selected on calibration and frozen before evaluation. Detector adoption requires an agreed recall gain, clean-face floor, FPPI and latency policy; recognizer adoption requires correct identification at a fixed false-identification budget and gallery protocol. Null budgets, missing labels and insufficient independent evidence mean unqualified. Cluster projections are diagnostic; compute scores in the original space. Description evaluation separates supported facts, coverage, identity/position errors, usefulness, latency and actual versus estimated cost.
