## Goal

Turn the single-column Workbench into a **two-pane operator surface** — LEFT a control surface (recognition run · cluster map · name & curate), RIGHT the media library table gaining alt-text and long-description columns — with cluster selection **coordinating** both panes over one shared selection. Ship a **people-first Roster v1** where clusters are a drawer, not a tab. The recognition target is InsightFace on `:10010` (interim, until FIR stabilizes), surfaced **read-only** because it is server-resolved.

## Scope departure — needs operator sign-off

The E21 "Public MVP UX/UI Polish" epic is constrained to **no backend contract changes**. This direction **requires four new backend surfaces** (DEP-1 long-description field, DEP-2 2D cluster-map layout endpoint, DEP-3 media-list `cluster_id` filter param, DEP-4 persisted pre-reveal judgments + multilevel undo — see Data Dependencies). WBUX-5 is therefore a **v0.5.0-candidate direction, not an E21 polish task**, even though it is filed alongside the WBUX series. Two things need an operator decision before backend slices are funded: (1) confirm the backend-change scope (all four deps), and (2) reconcile ownership with in-flight E21 roster/shell tasks (see Ownership Reconciliation).

## Grounding — verified code reality

The redesign is drawn against the current implementation, not an imagined one. Three findings reshape the plan:

- **Long descriptions have no FE field yet; storage is pinned.** `WorkbenchMediaItem` (`api/generated/workbench-media-item.ts`) exposes only `altText` — no `description` / `caption` / `longDescription` on the generated media type or detail model. Long-description **storage** maps to the WP attachment **description** (`post_content`), written by the existing plugin path `DescribeMediaService::maybe_write_long_description` (`src/api/services/class-describe-media-service.php`, `wp_update_post`→`post_content`, gated by `acx_alt_style=alt_plus_description`) — not `post_excerpt` (caption) and not new post meta. DEP-1 still must expose that value on the workbench media REST read/write surface and regenerate `WorkbenchMediaItem` with a bindable field (see Data dependencies).
- **The cluster map has no data.** There is no UMAP / 2D-coordinate / scatter data in the frontend; `ClusterSummary` carries counts and sample identities but no `x/y`. The only spatial data is per-face `bbox` (image pixels) and 3D head pose (`debug_metrics.pose`, pitch/yaw/roll). User copy avoids both `embeddings` and `projection`; `projection` is in `BANNED_STRINGS` (substring-checked), `embeddings` is asserted separately in the same test (`banned-vocabulary.test.tsx`) — user copy says "cluster map".
- **The endpoint is server-resolved.** `src/api/class-recognition-endpoint-resolver.php` resolves the URL by precedence (`ACX_RECOGNITION_URL` constant → `acx_recognition_base_url` filter → `acx_recognition_url` option → empty); local dev default is `:8000`, not `:10010`. There is **no UI toggle** (RECOG-1 retired the option-writing UI). Selecting InsightFace `:10010` is a constant/filter, not an operator control.

What is already healthy: the `--acx-*` design-token surface is complete across all six families the redesign needs (color/gray/text/shadow/radius/font-weight), asserted by `design-tokens.test.ts` (only `--acx-gray-800` is absent from the ramp).

## Decisions

- **Clusters live in the Workbench left pane; retired from Roster.** Cluster building/naming is an operator loop, not a people-directory concern. Roster becomes people-first; cluster review there is a drawer (`?cluster=`). Consistent with the golden fixture's retired clusters-tab and with E21-9's direction.
- **Recognition endpoint is read-only status, not a switcher.** Topbar and left-pane `z-endpoint` show the resolved target + health only (RECOG-1). The "change endpoint" affordance links to Settings (`act-view-endpoint-settings`), which documents the constant/filter — it does not write an option. Health includes an explicit **unreachable / degraded** state: disable the recognition-run control, surface retry + last-checked, and preserve last-good clusters/list (and later map) so an interim target such as InsightFace `:10010` failing is operable under `[INT-10]`/`[HAI-04]`, not a silent empty success. Invalidation-on-endpoint-switch remains a separate DEP-2 concern; this state is endpoint-down, not endpoint-switched.
- **Naming uses commit-before-reveal (enforced two-phase machine).** The name & curate form is a reveal-gate state machine, not a soft guideline: `judgment_pending` (operator enters/commits their independent name; model top candidate and confidence are **not mounted**) → `revealed` (top candidate + confidence shown for reconcile) `[HAI-15]`. A confirm-only screen that shows the model first logs agreement, not verification. Candidate shortlist is **bounded** with the count recorded `[HAI-16]`, every cluster/match links to its source frames `[HAI-01]`, and the reference set spans captures rather than one image `[HAI-17]`.
- **The cluster map ships list-first, scatter as a dependency-gated fast-follow.** Day-one left pane is a **cluster list** with URL-synced selection (`?cluster=` via the Slice-3 owner) and name/curate focus — **no new backend**. The **right-pane cluster-wide media filter** waits on DEP-3; **persisted pre-reveal judgments + multilevel undo** wait on DEP-4; the 2D scatter waits on DEP-2. This de-risks layout and selection ownership from the surfaces that need new contracts, without claiming full dual-effect coordination is backend-free.
- **AI output is a proposal, never the answer.** Alt-text / long-description suggestions ship the accept / edit / regenerate triad `[HAI-12]`/`[INT-11]`, disclose synthetic authorship `[HAI-14]`, and the operator remains the last error detector on the caption at risk `[HAI-13]`. AI-generated captions must themselves meet WCAG / ATAG `[A11Y-34]`.

**DEP-2 contract sketch (must be fixed before Slice 4 starts):**

- **Request (cache key).** Recognition run id + endpoint dimensionality. Switching endpoint (`:10010` InsightFace 512d ↔ FIR/SFace 128d) or re-running recognition **invalidates** the layout. Layout is computed **once per recognition-run id** and cached for reads; a new run id or an endpoint-dimensionality change invalidates and recomputes — **no** intra-run incremental caching.
- **Response shape.** `{ clusterMapVersion: string, truncated: boolean, total_clusters: number, points: Array<{ cluster_id: string, x: number, y: number, member_count: number }> }`. **Aggregation:** one **representative point per cluster** (centroid of its members' layout coords) carrying a `member_count` badge. **Cap:** the endpoint returns the **top ≤200 clusters by descending `member_count`** in a single response — **no pagination in WBUX-5**. If a run exceeds 200 clusters the response sets `truncated: true` and `total_clusters: <N>` so the client shows "top 200 of N"; multi-page fetch is an explicit out-of-scope follow-up. `[VIZ-09]` caps *colours* (~6–12), not *points* — an uncapped face set is an unbounded-result render (rg-007 spirit).
- **WP REST proxy.** New recognition-read route **`GET /acx/v1/recognition/cluster-map-layout?run_id=<id>`** on the plugin (proxies the recognition service), fetched via a new FE query **`useClusterMapLayout`** in the `api/recognition/` pattern (peer of `useRecognitionClusters`). Generated type lives under `api/recognition/types/` with **generated-type parity** asserted beside the contract fixture.
- **Overplotting / occlusion discipline** (distinct from the point cap). The scatter renders **one mark per cluster (≤200 marks total)**; the discipline addresses **co-located cluster marks**, using `member_count` as weight — **no member-level geometry is requested from the endpoint**. Mitigate layered fusion `[VIZ-12]`: **limit the render to a few (≈2–3) luminance-distinct layers with a lawful luminance order — representative cluster marks sit above a lower-contrast density/hull background, never competing at the same spatial frequency** — plus controlled opacity/alpha, small positional jitter, and/or aggregate-at-zoom (hull or density mark until the operator zooms) so individual marks stay assignable to a layer. Cap answers *how many*; this answers *how they remain separable when co-located*.
- **Consistency on invalidation.** A stale `?cluster=<id>` deep-link (and any coordinated selection over it) must resolve to an explicit empty state — never a silent mis-filter or an empty-looking success.
- **Failure-mode split (do not conflate).** A transport/fetch error is a **retryable degraded** state — keep last-good `clusterMapLayout` when present, offer retry, and do **not** treat the cluster as invalid. **Only** a true `clusterMapVersion` mismatch (run/endpoint invalidation) triggers the "this cluster no longer exists / re-run recognition" empty state. Collapsing fetch failure into that empty state would brick a still-valid Slice-3 list.

**DEP-4 contract sketch (must be fixed before Slice-3 persistence + undo start):**

- **Write ownership (MECE).** name/abstain judgments → the `recognition_judgment` store + `POST /acx/v1/recognition/cluster-judgment`. merge/split corrections → the **existing** `cluster_merged`/`identity_reassigned` ops, stamped with the same correction-provenance (`correction_source=human`, `run_id`, `source_version`). These are the only two write paths; no third.
- **Store.** A `recognition_judgment` record keyed by `(cluster_id, run_id)`: `human_name` (nullable), `abstain` (bool), `candidate_count` (int, the bounded shortlist size `[HAI-16]`), `correction_source='human'`, `source_version`, `decided_at`. This record is the **latest-decision projection** (current decision only — not a history). Merge/split corrections stamp the same provenance onto the existing `cluster_merged`/`identity_reassigned` ops (the second write path).
- **Undo model.** A session→persisted **append-only operation log** (ordered) records BOTH judgment commits AND merge/split ops as discrete **reversible entries** `[INT-09]`. The `recognition_judgment` record keyed `(cluster_id, run_id)` is the **latest-decision projection**; the operation log is the **LIFO undo history**. **`operation_id` is minted server-side and returned on every commit** — both the judgment commit (`POST /acx/v1/recognition/cluster-judgment`) and the merge/split ops return the created `operation_id` in their response body; the FE stores it to drive undo. Each append-only log entry is `{ operation_id, affected_cluster_ids: string[], run_id, op_type: 'judgment' | 'merge' | 'split', payload, correction_source, source_version, created_at, undone: boolean }`, where **`payload` is discriminated by `op_type` and records the reversal before-state**: judgment → `{ cluster_id, decision: 'name' | 'abstain', candidate_id?, before_label }`; merge → `{ source_cluster_ids, result_cluster_id, before_membership_ref }`; split → `{ source_cluster_id, result_cluster_ids, before_membership_ref }`. `affected_cluster_ids` lists the single cluster for a judgment and every source+result cluster for a merge/split. `before_membership_ref` is an **opaque server-stored snapshot id** referencing the pre-op cluster→member map captured at commit time, which the compensating action reloads to restore membership on undo (no client-visible shape beyond the id). There is **no re-application of reversed operations** in WBUX-5, so undo is a single in-place `undone` flag ordered by `created_at`. `POST /acx/v1/recognition/cluster-judgment/undo` takes an explicit request body `{ operation_id }` (the log entry to reverse — not a blind pop) and issues the compensating action: delete/restore the judgment, or reverse the merge/split via its existing reversible op. **Atomic per-affected-cluster LIFO:** an undo `{ operation_id }` is valid only if the target is the **newest non-undone entry for EVERY cluster in its `affected_cluster_ids`** (checked atomically); if any affected cluster has a newer non-undone entry, the server rejects the out-of-order undo (**409**). The compensating action reverses via the op's existing reversible action, **restoring the recorded before-state**, and sets `undone=true` in place; re-issuing an undo for an already-`undone` entry is a no-op success. **Merge/split mint into the shared log:** merge/split corrections append their own entry (`op_type` `merge`/`split`) to the **same** operation log, listing **every affected cluster in `affected_cluster_ids`** so the atomic per-affected-cluster LIFO check spans all clusters the structural op touched; a single undo surface reverses judgments and structural corrections uniformly via each op's existing reversible action. Reads fold into the existing cluster list/detail responses. FE mutation client extends the recognition write path (peer of the cluster-label mutation) with a session→persisted undo stack in the name/curate context.
- **Generated types + parity** asserted beside the DEP-4 fixture (rg-001, rg-005).
- **Replay precedence.** On recompute, re-apply the **latest non-undone** judgment per cluster (precedence over the auto-label). This is the `[HAI-02]` discrimination test's assertion and stays **DEP-4-gated**.
