# Engineering Heuristics Lexicon

## About this document

Decision rules for planning, writing, and reviewing code. Referenced, not read
end to end: this file is the concept vocabulary for agent skills and rule guides,
the way the Fowler smell table serves `refactor`. An activation surface inlines
the cue (trigger plus question) and cites the rule by ID where the decision
happens; this file holds the rationale, and section headings are the deep-link
anchors.

The load-bearing works are Kleppmann's
[*Designing Data-Intensive Applications*](../SOURCES.md#src-designing-data-intensive-applications),
Nygard's [*Release It!*](../SOURCES.md#src-release-it), Farley's
[*Modern Software Engineering*](../SOURCES.md#src-modern-software-engineering),
Fowler and Beck's [*Refactoring*](../SOURCES.md#src-refactoring-fowler-beck), and
the Arpaci-Dusseaus' [*Operating Systems: Three Easy Pieces*](../SOURCES.md#src-operating-systems-three-easy-pieces).
A share of agent-operations and practice rows is unsourced rather than tied to
those texts.

**Reading a row**

| Column | What it holds |
|---|---|
| ID | stable citation key, immutable once assigned; cite it as `[RES-01]` |
| Trigger | observable in a diff, plan, error, or runtime signal |
| Rule | the falsifiable claim: condition, action, consequence |
| Answers | the one question to ask, answerable from the diff and plan |
| T·P | tier and phase, below |
| Src | source slug, resolved in [`SOURCES.md`](../SOURCES.md) |

Tier: **B**locker (correctness, data loss, or security if violated), **S**hould
(strong default, exemptions exist), **J**udgment (weigh in context). Phase:
**p**lan, **w**rite, **r**eview (where the rule primarily fires).

**Example of a row that does not meet B:** [AGT-07](#agt-07) is S: externalizing
a fact prevents re-derivation after context loss, but a missed note alone does not
break correctness, lose data, or create a security flaw.

Repo-derived rules enter at tier J with occurrence provenance and are promoted
by the Short-Rules vote mechanism (`helpful=`/`harmful=`). This file is the
canonical source: consuming repos inline cues by phase tag and cite rules by ID,
never copying row bodies.

## 1. AGT: Agent Craft<a name="fam-agt"></a>

| --- | --- | --- | --- | --- | --- |
| AGT-01<a name="agt-01"></a> | session's first write lands within two turns on a task with prior state | **Orient before acting**: context, plan checklist, recent decisions, branch state: four reads prevent redo and collision (↔ ux [[COG-01]](interaction-ux.md#cog-01) act from externalized state, not incomplete working memory) | Did I check what's done and in flight before editing? | J·w | [bootstrap](../SOURCES.md#src-bootstrap) |
| AGT-02<a name="agt-02"></a> | plan/finding/code relies on a path, symbol, API default, or config fact not looked up this session | **No unresolved anchors**: look it up, don't guess; grep/read the manual, spec, or source before citing; a missing anchor is a finding, not a license to improvise (↔ writ [[WRIT-41]](writing.md#writ-41) a citation that cannot be followed is worse than none; ↔ ml [[PROV-01]](ml-systems.md#prov-01) every output walks back to its evidence; ↔ [[FORE-06]](epistemics.md#fore-06) a point figure with no decomposition has no walkable ancestors; ↔ sec [[SEC-10]](security.md#sec-10) unpinned weights are an unauditable dependency; ↔ a11y [[A11Y-27]](accessibility.md#a11y-27) authority is the primary regulation, not a derived summary) | Did I verify this claim against the source, not memory? | B·w | [Debugging: The 9 Indispensable Rules](../SOURCES.md#src-debugging-9-rules) |
| AGT-04<a name="agt-04"></a> | completion claim without command + decisive output line | **Evidence verbatim**: every done-claim names the evidence that proves it — the file:line, the named test, or the command's decisive output; also satisfies closure guards for free (↔ [[TEST-03]](engineering.md#test-03) the pinned, named test is what a done-claim cites; pin first so there is evidence to name) | What evidence proves this claim? | J·r | [bootstrap](../SOURCES.md#src-bootstrap) |
| AGT-06<a name="agt-06"></a> | checklist, gate, or review item is left unchecked or marked skipped with no written reason or exemption | **Name the skip**: the checklist is institutional memory; skipping an item as "probably fine" hides a gap that a declared skip would keep recoverable (↔ ux [[HAI-05]](interaction-ux.md#hai-05) do not overclaim autonomy beyond the tested envelope) | Which items did I not do, and did I say so? | J·r | [bootstrap](../SOURCES.md#src-bootstrap) |
| AGT-07<a name="agt-07"></a> | same fact re-derived twice in one session | **Externalize at discovery**: notes/decisions written when learned survive compaction; working memory doesn't (↔ [[ARCH-07]](engineering.md#arch-07) the same act at architecture scale: write it when learned, so it survives the author) | Should this be in the log instead of my head? | S·w | [The Programmer's Brain, ch. 11](../SOURCES.md#src-programmers-brain) |
| AGT-08<a name="agt-08"></a> | A caller is about to pass an argument outside a routine's documented precondition. | **Check preconditions at the caller**: when the language checks a precondition before the routine is entered, perform any explicit parameter check at the caller, because the routine will never see parameters that violate its precondition; without that language support, bracket the call with a preamble or postamble that checks the assertion (↔ biz [[CLM-05]](business-marketing.md#clm-05) the hostile reader checks the named contract literally; ↔ a11y [[A11Y-22]](accessibility.md#a11y-22) one failing step falsifies the claim) | Does this language check the precondition before entry, and where is the explicit parameter check? | S·w | [The Pragmatic Programmer, ch. 4](../SOURCES.md#src-pragmatic-programmer) |
| AGT-10<a name="agt-10"></a> | A repair or exception path catches a failure and continues without promptly reporting it or producing strictly clean output | **Degrade loudly**: if repair cannot continue safely, fail noisily and as soon as possible, or pass strictly clean data to the next program; failed repairs that quietly corrupt can surface later (see [[OBS-01]](engineering.md#obs-01)) (↔ [[RLSE-05]](engineering.md#rlse-05) a crash is honest and a silent wrong answer is not; ↔ [[OBS-08]](engineering.md#obs-08) silence is not success, dead instrumentation breaks loudly; ↔ [[AGT-15]](engineering.md#agt-15) the stream split is where failure surfaces without corrupting data; ↔ [[AGT-21]](engineering.md#agt-21) exit status keeps the failure machine-legible) | Can repair continue safely, and will the next program receive only strictly clean data? | S·r | [The Art of UNIX Programming, ch. 1](../SOURCES.md#src-art-of-unix-programming) |
| AGT-11<a name="agt-11"></a> | operator asked a question the repo answers | **Grep before asking — facts, not forks**: config, patterns, and commands are self-serve, so spend a tool call on them rather than a human round-trip (↔ [[AGT-02]](engineering.md#agt-02) look it up, don't guess — a missing anchor is a finding, not a license to improvise); but a tool call cannot return intent, preference, or which side of an irreversible fork the operator wants, and there the round-trip is the cheap side, not the cost to dodge (↔ [[MEAS-11]](epistemics.md#meas-11) force the decision purpose before acting; ↔ [[AGT-16]](engineering.md#agt-16) undo beats asking only when the act is reversible). The round-trip is waste only when the answer was already retrievable | Can a tool call answer this — a fact, or a fork? | J·w | [agent-operations](../SOURCES.md#src-agent-operations) |
| AGT-12<a name="agt-12"></a> | third unproductive attempt at the same obstacle | **Timebox and hand off legibly**: tried/learned/next-imperative makes the handoff nearly free (↔ [[NDM-07]](epistemics.md#ndm-07) intent on the wire so the next executor can act without re-deriving) | Am I generating new information or variations? | J·w | [bootstrap](../SOURCES.md#src-bootstrap) |
| AGT-13<a name="agt-13"></a> | diff or plan contradicts a recorded ADR without amending it | **No silent ADR override**: if a consequential choice changes, update its ADR with context, decision, and consequences before the new choice lands; treat the written ADR as the exit criterion (↔ biz [[OPS-08]](planning.md#ops-08) written authority beats live heroics) | Does a recorded decision already answer this, and was it amended if not? | S·w | [Software Architecture: The Hard Parts, ch. 1](../SOURCES.md#src-architecture-hard-parts) |
| AGT-14<a name="agt-14"></a> | A filter or pipeline command run by a script, CI job, or agent blocks for a human to type required input data or processing parameters, or replaces a file’s data with the output of a producer that can fail, with no check of that producer’s exit status. | **Never prompt in an automation path**: filters must not require feedback or commands from the user in their input stream; where a human choice is needed, keep it in a declared-interactive wrapper, and replace a file’s data from a risky pipeline producer only after checking that producer’s exit status, rather than guarding the replacement with a prompt. (↔ [[RES-02]](engineering.md#res-02): every blocking call needs a bound) (↔ [[OBS-21]](engineering.md#obs-21): automation completion has visible checks and owner notification) | Can this pipeline stage receive its input data and parameters without a person typing them, and is a risky producer’s exit status checked before its output replaces data? | S·r | [The Art of UNIX Programming, ch. 11](../SOURCES.md#src-art-of-unix-programming) + [The UNIX Programming Environment, ch. 5](../SOURCES.md#src-unix-programming-environment) |
| AGT-15<a name="agt-15"></a> | A command whose stdout is piped or parsed writes unrequested status or progress text, or error diagnostics, to stdout. | **stdout is data, stderr is for errors**: keep requested, machine-readable output on stdout; omit unrequested banners, progress, summaries, and status messages there, and send real error diagnostics to stderr so they remain visible when stdout is piped or redirected. (↔ [[FM-04]](ml-systems.md#fm-04) machine-consumed output needs a validated schema) | Would a downstream parser have to recognize and skip this line on the success path? | S·r | [The Art of UNIX Programming, ch. 11](../SOURCES.md#src-art-of-unix-programming) + [The UNIX Programming Environment, ch. 6](../SOURCES.md#src-unix-programming-environment) |
| AGT-16<a name="agt-16"></a> | diff adds a confirmation prompt to a routine, recoverable, or undoable operation | **Confirm only when refusal is plausible**: repeated low-value prompts train reflexive acceptance; prefer an undoable operation when recovery is cheap, and reserve confirmation for actions that can destroy data or resist reversal (↔ [[OBS-04]](engineering.md#obs-04) false alarms train operators to ignore real ones) | Is refusal realistic here, and would undo be cheaper than asking first? | S·r | [The Art of UNIX Programming, ch. 11](../SOURCES.md#src-art-of-unix-programming) |
| AGT-17<a name="agt-17"></a> | diff or plan embeds interface decisions (prompting, formatting, interaction flow) inside the engine/mechanism module | **Separate policy from mechanism**: policy changes much faster than mechanism, so hardwiring them together makes policy rigid and destabilizes the mechanism on every policy change; separated, the engine is independently testable and interaction stays at a replaceable frontend | Can the interface change without touching the engine, and is the engine drivable without the interface? | J·p | [The Art of UNIX Programming, ch. 1](../SOURCES.md#src-art-of-unix-programming) |
| AGT-18<a name="agt-18"></a> | plan introduces a custom binary format or protocol without a measured size or parse-latency requirement | **Textual until measured**: prefer a text format that general tools and humans can inspect; accept binary's debugging cost only when a measured density or parsing budget requires it (↔ [[PERF-06]](engineering.md#perf-06) measure before optimizing) | What measurement forces binary here, and how will a human inspect a sample record? | J·p | [The Art of UNIX Programming, ch. 5](../SOURCES.md#src-art-of-unix-programming) |
| AGT-19<a name="agt-19"></a> | diff adds a config flag for a condition detectable at runtime, an optimization knob for users, or an option a wrapper script could supply | **Don't configure what you can detect**: autodetect or try alternatives until one succeeds; users should not see optimization switches; prefer a wrapper over an internal switch, because each on/off option should double the test matrix and never does, so ten options quietly cut real per-configuration coverage a thousandfold (↔ [[REF-21]](engineering.md#ref-21) pull complexity downward, the implementer decides so users don't) | Could the program decide this itself or a wrapper supply it, and who tests both settings? | S·r | [The Art of UNIX Programming, ch. 10](../SOURCES.md#src-art-of-unix-programming) |
| AGT-20<a name="agt-20"></a> | Conflicting configuration values resolve so a global source overrides a local one, or a setting mechanism does not match the preference's expected lifetime | **Config precedence follows preference lifetime**: when multiple levels supply a value, resolve them in this order: system run-control file, system environment, user dotfile, user environment, command-line switch, so later and more local values override earlier and more global ones; choose each setting's mechanism to match its expected lifetime: per invocation → command-line switch, per user → dotfile, sitewide → system run-control file | Does the most local, shortest-lived setting win, and does each lifetime have a home? | J·w | [The Art of UNIX Programming, ch. 10](../SOURCES.md#src-art-of-unix-programming) |
| AGT-21<a name="agt-21"></a> | outcome of a step signaled only by prose ("done", "failed") or by an accidental last-command status | **Exit status is the outcome contract**: return 0 for success and distinct nonzero codes for the failure reasons, because without an explicit exit the status is unpredictable and every caller must parse prose to branch (↔ [[FM-04]](ml-systems.md#fm-04) callers should branch on a named contract rather than prose) | Can a caller branch on this outcome without parsing message text? | J·w | [The UNIX Programming Environment, ch. 5](../SOURCES.md#src-unix-programming-environment) |

## 2. RES: Resilience & Failure Modes<a name="fam-res"></a>

| ID | Trigger | Rule | Answers | T·P | Src |
| --- | --- | --- | --- | --- | --- |
| RES-01<a name="res-01"></a> | Code retries a network/DB call, hedging, or at-least-once queue | **Retry without idempotency**: retried ops double-apply unless idempotent (see [[DATA-13]](engineering.md#data-13), [[API-02]](engineering.md#api-02)) | Is this write safe to retry? | B·w | [Designing Data-Intensive Applications, ch. 8](../SOURCES.md#src-designing-data-intensive-applications) |
| RES-02<a name="res-02"></a> | Connect/read/pool-checkout/HTTP client with no timeout | **Timeout on every blocking call**: every socket/pool/RPC/`wait()` needs a bounded timeout; defaults block forever. Exempt: in-process/in-memory calls (↔ ml [[FM-08]](ml-systems.md#fm-08) agent loops must be bounded or they starve the system) | What bounds this wait? | B·w | [Release It!, ch. 5](../SOURCES.md#src-release-it) |
| RES-03<a name="res-03"></a> | Sync external call; only the error path handled | **Slow failure worse than fast failure**: a hung downstream ties up caller+callee worse than a refused connection (↔ [[RES-21]](engineering.md#res-21): a timeout bounds waiting but does not prove the remote process is dead) | What happens when this dependency is slow, not down? | S·r | [Release It!, ch. 5](../SOURCES.md#src-release-it) |
| RES-04<a name="res-04"></a> | Downstream waits are occupying caller threads until the caller's resource pool is exhausted | **Resource-pool exhaustion / cascade**: downstream hangs can drain the caller's pool; bound checkout waits so blocked threads eventually unblock. | Can this downstream wait exhaust the caller's pool, and are checkout waits bounded? | B·r | [Release It!, ch. 5](../SOURCES.md#src-release-it) |
| RES-05<a name="res-05"></a> | SELECT without LIMIT, fetch-all, master/detail traversal, collection API | **Unbounded result set**: query/response with no LIMIT can OOM in prod; dev data hides it. Exempt: bounded-by-construction enums/config tables | What if this returns 10M rows? | B·w | [Release It!, ch. 4](../SOURCES.md#src-release-it) |
| RES-06<a name="res-06"></a> | Retry loop that re-attempts immediately without a delay | **Queue-and-retry, answer fast**: immediate retry against a persistent fault usually fails again; queue retries with delay and return a fast answer (HTTP 4xx/5xx retry class is [[API-08]](engineering.md#api-08)). | Does retry wait on a queue, and what fast answer reaches the caller? | S·w | [Release It!, ch. 5](../SOURCES.md#src-release-it) |
| RES-07<a name="res-07"></a> | Plan adds a table/log/session/cache that accumulates | **Steady-state reclaimer**: anything that grows needs same-rate purge, shipped in the same release | What purges this? | S·p | [Release It!, ch. 5](../SOURCES.md#src-release-it) |
| RES-08<a name="res-08"></a> | Plan adds cache/memoization | **Cache bound + invalidation**: unbounded key spaces need a size limit; changing values need an invalidation strategy (special case of [[RES-07]](engineering.md#res-07); see [[PERF-08]](engineering.md#perf-08)). | Is the cache bounded, and how are changing entries invalidated? | S·p | [Release It!, ch. 5](../SOURCES.md#src-release-it) |
| RES-09<a name="res-09"></a> | High-fan-in front tier → smaller back tier | **Unbalanced capacities**: front out-generates back; promo load inverts safe ratios | What throttles the front when the back saturates? | S·p | [Release It!, ch. 4](../SOURCES.md#src-release-it) |
| RES-10<a name="res-10"></a> | Code diff adds distributed locks/leases | **Fencing tokens**: paused/expired lease holder can write with stale state; storage must reject old monotonic tokens (↔ sec [[WEB-30]](security.md#web-30) terminate sessions server-side so expired authority cannot still write) | Can a paused holder still write? | B·p | [Designing Data-Intensive Applications, ch. 8](../SOURCES.md#src-designing-data-intensive-applications) |
| RES-11<a name="res-11"></a> | Plan accesses a table owned elsewhere | **Don't reach into another system's DB**: integration DB breaks encapsulation, couples consumers to internal schema (see [[ARCH-02]](engineering.md#arch-02)) | Does this read another service's DB directly? | S·p | [Release It!, ch. 18](../SOURCES.md#src-release-it) |
| RES-12<a name="res-12"></a> | Loop over remote/per-item RPCs | **Chatty remote interface (N+1)**: remote ≈ 1000× local; batch into coarse calls. Exempt: in-process calls | Is this remote interface chatty? | S·r | [Release It!, ch. 9](../SOURCES.md#src-release-it) |
| RES-13<a name="res-13"></a> | plan or diff adds an integration point without a named timeout, containment boundary, degradation path, or tested failure mode | **Bugs are survived, not eliminated**: assume any external call eventually fails; design crumple zones (see [[DIAG-07]](engineering.md#diag-07)) | Ran the failure questions for every I/O point? | S·r | [Release It!, ch. 3](../SOURCES.md#src-release-it) |
| RES-14<a name="res-14"></a> | A consumer receives messages faster than it can process them, or its admission mode is being chosen | **Choose an intake mode by consumer capacity**: use a Polling Consumer when the receiver needs to request the next message when ready to limit admission; an Event-Driven Consumer can be simpler when idle polling dominates, but provider callbacks may deliver faster than the application can process | Does this receiver need to request work when ready, or can it react to delivery without outpacing processing? | B·r | [Release It!, ch. 5](../SOURCES.md#src-release-it) + [Enterprise Integration Patterns, ch. 10](../SOURCES.md#src-enterprise-integration-patterns) |
| RES-15<a name="res-15"></a> | Circuit-less repeated calls to an external dependency | **Circuit-break integration points**: stop calling what's already failing; expose breaker state to operations (↔ biz [[AIPX-05]](business-marketing.md#aipx-05) fail closed to a safe deterministic path when the primary is known-bad) | If this dependency starts timing out, what stops us hammering it? | S·p | [Release It!, ch. 5](../SOURCES.md#src-release-it) |
| RES-16<a name="res-16"></a> | Design claims HA/failover/graceful-degrade but no test ever kills a dependency | **Exercise the tolerance path**: deliberately inject faults to exercise fault-tolerance machinery, because error-handling paths that never run hide critical bugs (see [[RES-13]](engineering.md#res-13)) | Which injected fault exercises this mechanism’s error-handling path? | S·r | [Designing Data-Intensive Applications, ch. 1](../SOURCES.md#src-designing-data-intensive-applications) |
| RES-17<a name="res-17"></a> | multi-structure durable update (file metadata + data, index + blob, manifest + object) that overwrites in place with no durable intent record before the mutation | **Write-ahead of intent before in-place mutation**: before overwriting persistent structures, write a note in a well-known log describing what you will do (journaling / write-ahead logging); after a crash, replay the note instead of scanning or guessing; this is the local form of crash consistency for any application journal, outbox, or migration log (extends [[DATA-16]](engineering.md#data-16), which owns single-file fsync/rename; here the object is multi-write *intent*) | Where is the durable intent recorded before in-place structures change, and can recovery find it? | B·p | [Operating Systems: Three Easy Pieces, ch. 42](../SOURCES.md#src-operating-systems-three-easy-pieces) |
| RES-18<a name="res-18"></a> | durable protocol that issues a commit/sentinel/pointer write in the same unordered batch as the payload it validates, or writes a reference before the referenced object is on disk | **Order durable writes: payload then commit; pointed-to then pointer**: wait for transaction payload to complete before the commit marker (TxE after journal body); persist each target before making its reference durable so recovery never sees a valid reference to garbage; devices reorder within a batch unless barriers/fsyncs enforce the dashed edges (↔ [[DATA-16]](engineering.md#data-16) for the fsync primitive; this row is the multi-write *order* contract) | After a crash mid-update, can a commit or pointer be durable while its payload or target is not? | B·w | [Operating Systems: Three Easy Pieces, ch. 42](../SOURCES.md#src-operating-systems-three-easy-pieces) |
| RES-19<a name="res-19"></a> | crash-recovery, journal replay, or checkpoint apply path that is not safe to run twice, or that assumes checkpoint completed exactly once | **Recovery redo must be idempotent**: a crash can interrupt a checkpoint after durable intent but before completion, so recovery may reapply committed writes; make each redo a no-op on repetition or converge to the same state. Sibling of [[RES-01]](engineering.md#res-01) / [[FLOW-05]](engineering.md#flow-05) (live retry / at-least-once); this row owns the recovery path after durable commit | If recovery runs twice on the same committed intent, is the store still correct? | B·p | [Operating Systems: Three Easy Pieces, ch. 42](../SOURCES.md#src-operating-systems-three-easy-pieces) |
| RES-20<a name="res-20"></a> | resource (file, connection, lock, temp) opened in one function and closed in another via shared field/handle, especially with early-return paths between | **Finish what you start**: the scope that allocates a resource releases it; prefer block-scoped lifetime so every open has a visible matching close on every path, including early returns (distinct from [[RES-04]](engineering.md#res-04) pool-exhaustion/finally leaks: this row is the allocator-releaser *identity* and split-open/close anti-pattern) | Can I point to one scope that both acquires and releases this resource on every path? | S·w | [The Pragmatic Programmer, ch. 4](../SOURCES.md#src-pragmatic-programmer) |
| RES-21<a name="res-21"></a> | A timeout or missed heartbeat is about to mark a remote process failed or to exclude it from membership | **Keep suspicion provisional**: treat the timeout as a suspicion, not as proof of death, and keep the monitoring score separate from the action taken on it, because in an asynchronous system delay and crash are indistinguishable and a slow peer can still be reachable. | What evidence distinguishes a failed peer from a delayed response? | S·r | [Database Internals, ch. 9](../SOURCES.md#src-database-internals-petrov) |
| RES-22<a name="res-22"></a> | A monitored primary provider fails its probe, a secondary is available, and the secondary differs in route or message format, or the plan switches back without a successful check | **Fail over through a monitored boundary**: send new requests to the backup, translate at that boundary when the format differs, keep probing the primary, and switch back only after a successful check, because an unverified return restores traffic to a provider that may still be failing. Do not assume requests already queued at the failed provider move with the switch; resending them can duplicate work, so name the strategy for that queue and make the receiving endpoints safe under duplicates.
