## WBTRUST-2. One curation surface — exclude mismatches, accept the rest

Frontend paths are relative to `apps/prototype-wp-alt-context/js/admin/pages/workbench/` unless stated.

## Objective

From a group of N faces the operator can select the wrong ones (reversibly), see the running count, and, when a valid exclusion producer is ready, finish with one primary action — without a confirm dialog per face and without leaving the surface. Until that producer is independently verified, K>0 stays in the explained hold below; K=0 retains the existing actions.

## Problem Statement

"Review these faces" (47 Ellyn Heald faces) offers only a × per face. Each × opens a confirm dialog and fires one reassign POST. There is no name, no accept, and no way back to a decision: "there is no path to accept, curate, or manage these matches from this screen. How to accept all after removing mismatches?" The shipped UX map records "remove an incorrect face with confirmation, and return" as the intended job, so this is a design gap, not a regression.

The request is not proof of removal: the current `removeClusterMember` sends a null target, which WordPress rejects with `missing_target_cluster_id`/400 before proxy or local mutation. With K=1 the first ordinary exclusion cannot succeed. This is a source-backed logical counterexample, not an executed HTTP defect; the fourth-context amendment already recognizes the same limit.

## Constraints

- Deep link `panel=review&cluster=<id>` (NAV-11, `ClusterPanelContext.tsx`) must keep working; do not change URL shape.
- Atomic write paths stay atomic. Ordinary K>0 requires the **WBTRUST-2-owned ordinary exclusion producer readiness** prerequisite below; the current null-target helper cannot satisfy it. The proposed fourth context separately requires a WordPress-local guarded, receipted exclusion adapter and one atomic final rebind command as specified below; these are explicit contract extensions, not existing API capabilities. No global or service batch-exclusion endpoint is introduced.
- Name/commit behavior reuses `PersonCommitControl`, `useClusterLabelMutations`, `NameFaceControl`, `useClusterConfirmSuggestion`; no second naming implementation.
- Operator vocabulary: group, person, face. sr-004 tokens; status = colour + icon + text. sr-007 enums for tile state. sr-008 ≤ 8 params.
- Tests on the remote VM lane.

## Workflow Principles

- Excluding is a *selection*, not a mutation, until the primary action runs. No membership effect is sent on toggle; the explicit fourth context may save only its draft under the proposed journal.
- Primary action is one button whose label states the outcome ("Accept 44 faces as Ellyn Heald").
- Constrain before sending: absent/unknown/failed producer readiness holds K>0 without requests. Once ready, stop on first failure; show exactly what was applied (INT-10).

## Terminology

**Excluded** = a face the operator marked to leave out; dimmed with an icon and the word "Excluded". **Accept** = after every required exclusion has a verified successful result, run the existing entry-context action below; a named group without a pending suggestion closes without a server commit. An unavailable, pending or failed exclusion never reaches that final action/close.
