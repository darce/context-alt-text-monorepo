# Curation Sync API

## Scope

This contract defines the v0.2.0 curation replay payload for sovereign sync of local person and cluster-person binding decisions to backend recognition state.

- Route owner: recognition service (`apps/prototype-description-service/roster`)
- Consumer: WordPress plugin outbox drain (`apps/prototype-wp-alt-context/src/sovereign/sync`)
- Delivery mode: push-on-drain with idempotency and conflict detection
- Replay semantics: at-least-once with idempotency key deduplication

## Endpoint

- `POST /roster/curation/sync`

Required headers:

- `X-API-Key` or `Authorization: Bearer <token>` (service deployment dependent)
- `X-Tenant-ID`: canonical tenant identifier
- `Content-Type: application/json`

Timeout expectations:

- Client request timeout: 10 seconds
- Backend target p95 response time: <= 2 seconds
- If timeout is exceeded, plugin preserves outbox operation as `pending` and retries on next drain cycle

## Request Payload

```json
{
  "operation_type": "cluster_person_bound",
  "entity_type": "cluster",
  "entity_key": "d290f1ee-6c54-4b01-90e6-d701748f0851",
  "idempotency_key": "b3d8c2e1-7a9f-4d2b-8e3c-9f1a2b3c4d5e",
  "expected_base_version": 1234567890,
  "local_revision": 5,
  "payload": {
    "cluster_uuid": "d290f1ee-6c54-4b01-90e6-d701748f0851",
    "person_uuid": "a1b2c3d4-5e6f-7g8h-9i0j-k1l2m3n4o5p6",
    "person_name": "Flaxen Yarrow"
  }
}
```

### Field Definitions

- `operation_type` (string, required): One of the supported curation operation types (see below)
- `entity_type` (string, required): Entity type the operation targets (`cluster`, `person`)
- `entity_key` (string, required): UUID of the entity being mutated
- `idempotency_key` (string, required): UUID v4 generated by plugin for deduplication
- `expected_base_version` (int, required, >= 0): Backend version the plugin believes it is building on
- `local_revision` (int, required, >= 0): Local monotonic revision number for the entity
- `payload` (object, required): Operation-specific payload (see operation types below)

### Supported Operation Types

#### Person Operations

**`person_created`**

- Target: newly created person record
- Payload fields:
  - `person_uuid` (string): UUID of the created person
  - `name` (string): person name
- Backend behavior: No-op acknowledgement (person records are local-only in v0.2.0)

**`person_updated`**

- Target: existing person record
- Payload fields:
  - `person_uuid` (string): UUID of the updated person
  - `name` (string): updated person name
- Backend behavior: No-op acknowledgement (person records are local-only in v0.2.0)

**`person_deleted`**

- Target: person record being removed
- Payload fields:
  - `person_uuid` (string): UUID of the deleted person
- Backend behavior: No-op acknowledgement; downstream `cluster_person_unbound` operations handle dissociation

#### Cluster-Person Binding Operations

**`cluster_person_bound`**

- Target: cluster being assigned to a person
- Payload fields:
  - `cluster_uuid` (string): UUID of the cluster
  - `person_uuid` (string): UUID of the person being bound
  - `person_name` (string): Authoritative local person label captured at bind time
- Backend behavior: Sets `identity_clusters.roster_id = person_uuid`, updates the cluster label from `person_name` when present, increments `updated_at`

**`cluster_person_unbound`**

- Target: cluster being dissociated from a person
- Payload fields:
  - `cluster_uuid` (string): UUID of the cluster
  - `person_uuid` (null): Explicit null to signal unbinding
  - `person_name` (null): Explicit null because unbind does not carry a local label target
- Backend behavior: Sets `identity_clusters.roster_id = NULL`, increments `updated_at`, and leaves the replay row at `not_applicable` because no suggestion refresh work is queued

### Idempotency Semantics

- Backend persists replay results in `curation_replay_records` keyed by `(tenant_id, idempotency_key)`
- Repeated delivery of same idempotency key returns the persisted acknowledgement or conflict
- Idempotency survives service restarts and process restarts
- Plugin MUST generate unique idempotency keys per outbox operation
- Plugin MUST NOT retry with a different idempotency key for the same mutation
- Acknowledged cluster mutations also persist durable refresh lifecycle state on the replay row. The canonical `CurationRefreshStatus` set is:
  - `not_applicable`: person-only operations, unbind operations, and conflict responses never enter refresh execution
  - `queued`: cluster operations start here when refresh is required
  - `running`: worker has begun executing the refresh
  - `completed`: refresh executed and produced new candidate suggestions
  - `no_candidates`: refresh executed successfully but produced no candidates (terminal success, distinct from `completed`)
  - `timed_out`: refresh aborted by the bounded timeout guard before producing a result; eligible for retry
  - `failed`: refresh executor returned a non-recoverable error
- If the refresh executor is unavailable when the replay row would advance to `running`, the row stays `queued` so a later worker pass can retry instead of terminally failing the curation event.
- If the refresh executor raises a non-timeout failure before replay-state persistence is available, the bounded refresh loop still aborts after that first failure; this is a control-flow guarantee only and does not add a new `refresh_status` value or alter the existing terminal status contract.

### Version Conflict Detection

Backend compares `expected_base_version` against current cluster state:

- `expected_base_version < current_backend_version`: **conflict** (local operation is stale)
- `expected_base_version >= current_backend_version`: operation may proceed

Version calculation:

```python
backend_version = int(cluster.updated_at.timestamp() * 1_000_000)
```

## Response (200) - Acknowledged

```json
{
  "status": "acknowledged",
  "backend_version": 1234567895,
  "idempotency_key": "b3d8c2e1-7a9f-4d2b-8e3c-9f1a2b3c4d5e"
}
```

### Field Definitions

- `status` (string): Always `"acknowledged"` for 200 responses
- `backend_version` (int): Current backend version after applying the operation
- `idempotency_key` (string): Echo of request idempotency key for correlation

### Plugin Behavior on Acknowledgement

1. Update outbox record: `status = 'acknowledged'`, `acknowledged_version = backend_version`, `acknowledged_at = NOW()`
2. Increment sync state: `sync_state.last_acknowledged_version = backend_version`
3. Do NOT modify local projection state (local curation remains authoritative)

## Response (409) - Conflict

```json
{
  "status": "conflict",
  "conflict_code": "version_conflict",
  "backend_version": 1234567900,
  "machine_payload": {
    "cluster_uuid": "d290f1ee-6c54-4b01-90e6-d701748f0851",
    "current_roster_id": "z9y8x7w6-5v4u-3t2s-1r0q-p9o8n7m6l5k4"
  }
}
```

### Field Definitions

- `status` (string): Always `"conflict"` for 409 responses
- `conflict_code` (string): Machine-readable conflict category
- `backend_version` (int): Current backend version that conflicts with local operation
- `machine_payload` (object): Backend state snapshot for conflict resolution UI

### Conflict Codes

- `version_conflict`: `expected_base_version` is stale relative to current backend state
- `cluster_not_found`: Cluster UUID does not exist in backend tenant scope

### Plugin Behavior on Conflict

1. Update outbox record: `status = 'conflict'`, `last_error_code = conflict_code`
2. Insert conflict record in `wp_acx_sync_conflicts`:
   - `entity_type`, `entity_key`, `outbox_id`, `expected_base_version`, `backend_version`, `conflict_code`
   - `machine_payload` (backend state), `local_payload` (outbox operation payload)
   - `resolution_status = 'open'`
3. Increment sync state: `sync_state.conflict_count += 1`
4. Surface conflict in admin UI (pending operations + conflict indicator)
5. Do NOT auto-retry conflicted operations; require explicit operator resolution

## Response (400) - Validation Error

```json
{
  "detail": "unsupported operation_type: invalid_operation"
}
```

Plugin behavior: Mark outbox record as `failed` with error detail; do not retry without code fix.

## Response (401/403) - Authentication Error

Plugin behavior: Halt drain cycle; surface auth error in sync status; do not retry until credentials are refreshed.

## Response (500/502/503/504) - Transient Error

Plugin behavior: Mark outbox record as `pending`, increment `attempts` counter; retry on next drain cycle with exponential backoff.

## Topology Operation Types

The following operations mutate cluster topology and are dispatched by `OutboxDispatcher` directly to recognition service endpoints (NOT through `POST /roster/curation/sync`):

| Operation Type                 | HTTP                                             | Payload Fields                               |
| ------------------------------ | ------------------------------------------------ | -------------------------------------------- |
| `cluster_merged`               | `POST /recognition/clusters/{id}/merge`          | `target_cluster_id`, optional `target_label` |
| `identity_reassigned`          | `POST /recognition/clusters/reassign`            | `identity_uuid`, `target_cluster_uuid`       |
| `cluster_created_for_identity` | `POST /recognition/clusters/create-for-identity` | `identity_uuid`, `cluster_uuid`              |
| `revert_merge_cluster`         | `POST /recognition/clusters/revert-merge`        | `source_cluster_uuid`, `target_cluster_uuid` |
| `assign_outlier_to_cluster`    | `POST /recognition/clusters/{id}/assign`         | `identity_uuid`                              |
| `cluster_label_updated`        | via curation sync                                | `cluster_uuid`, `label`                      |
| `cluster_dismissed`            | via curation sync                                | `cluster_uuid`                               |
| `cluster_undismissed`          | via curation sync                                | `cluster_uuid`                               |
| `cluster_person_bound`         | via curation sync                                | `cluster_uuid`, `person_uuid`                |
| `cluster_person_unbound`       | via curation sync                                | `cluster_uuid`                               |

### Topology Dispatch

The `OutboxDispatcher` routes topology operations using `TOPOLOGY_ROUTES` constant with `%s` entity_key interpolation. These go directly to recognition service topology endpoints with `X-API-Key` and `X-Tenant-ID` headers.

### Cross-Plane Sequencing

Topology mutations that affect multiple entities (merge, split, reassign) are sequenced by `CrossPlaneSequencer` to prevent race conditions between local and remote state. The sequencer ensures that topology commands complete in order.

## Outbox Lifecycle and Dead-Letter

Outbox operations follow a bounded retry lifecycle:

```
pending -> acknowledged (success)
pending -> conflict (409 from backend)
pending -> failed (max attempts exhausted or non-retryable error)
conflict -> pending (operator dismisses: re-enqueue with updated base)
conflict -> discarded (operator accepts machine state)
failed -> pending (operator retries from dead-letter panel)
failed -> discarded (operator discards from dead-letter panel)
```

Max attempts: 5 (configurable). No backoff delay between drain cycles.

### Dead-Letter Management Endpoints (WP REST)

| Endpoint                                       | Method | Purpose                         |
| ---------------------------------------------- | ------ | ------------------------------- |
| `GET /acx/v1/recognition/outbox/failed`        | GET    | Paginated list of failed ops    |
| `POST /acx/v1/recognition/outbox/{id}/retry`   | POST   | Reset to pending, reschedule    |
| `POST /acx/v1/recognition/outbox/{id}/discard` | POST   | Mark discarded, refresh metrics |

## Conflict Resolution Endpoints (WP REST)

| Endpoint                                          | Method | Purpose                           |
| ------------------------------------------------- | ------ | --------------------------------- |
| `GET /acx/v1/recognition/conflicts`               | GET    | Paginated list with status filter |
| `GET /acx/v1/recognition/conflicts/{id}`          | GET    | Detail with decoded payloads      |
| `POST /acx/v1/recognition/conflicts/{id}/resolve` | POST   | Accept or dismiss conflict        |

### Conflict Resolution Semantics

`ConflictResolutionService::resolve()` dispatches per source and `conflict_code`:

**Outbox conflict accepted** (deterministic single-row operations only):

- Clear curation flags on entity (`is_user_confirmed = 0` / `is_curated = 0`)
- Discard outbox row
- Next sync pull converges entity to machine state

**Outbox conflict dismissed** (all operation types):

- Re-enqueue outbox row with updated `expected_base_version`, reset attempts
- Reschedule drain

**Projection conflict accepted** per `conflict_code`:

- `curated_cluster_deleted`: delete cluster row + all member rows (no FK cascade)
- `curated_member_deleted`: delete member row
- `member_cluster_reassignment`: update member's `cluster_uuid` to machine value, clear `is_curated`

**Projection conflict dismissed**: no entity mutation (curated state preserved)

### `allowed_resolutions` per conflict

| Source     | Operation Category                                       | `allowed_resolutions`       |
| ---------- | -------------------------------------------------------- | --------------------------- |
| Projection | any                                                      | `['accepted', 'dismissed']` |
| Outbox     | deterministic single-row (`cluster_label_updated`, etc.) | `['accepted', 'dismissed']` |
| Outbox     | person CRUD + compound topology (`cluster_merged`, etc.) | `['dismissed']`             |

## Data Flow Invariants

### Local Write Atomicity

Plugin MUST execute local mutation + outbox insertion within a single database transaction:

```php
$wpdb->query('START TRANSACTION');
try {
    // 1. Update local projection (cluster, person, etc.)
    // 2. Increment local_revision
    // 3. Insert outbox operation
    $wpdb->query('COMMIT');
} catch (Throwable $e) {
    $wpdb->query('ROLLBACK');
    throw $e;
}
```

If transaction fails, neither local state nor outbox state must be modified.

### Curation Authority

- Local curation decisions (person assignment, dissociation) are authoritative ground truth
- Backend acknowledgement updates sync metadata but MUST NOT overwrite local projection
- Conflicts surface divergence but do not force local state changes
- Operator resolves conflicts by choosing local state (re-push), backend state (fetch + overwrite), or manual merge

### Dissociation Preservation

When a cluster is unbound from a person:

- Outbox operation: `cluster_person_unbound` with `person_uuid: null`
- Backend sets: `identity_clusters.roster_id = NULL`
- Local projection preserves: `is_user_confirmed = 1`, `curation_state = 'confirmed'`
- Future snapshot replays MUST NOT re-assign the cluster unless local curation is explicitly updated

### Expected Base Version Semantics

- Plugin captures backend snapshot version when fetching clusters
- Plugin includes snapshot version as `expected_base_version` in outbox operations
- If backend state changes between fetch and replay, conflict is detected
- This prevents lost-update scenarios where plugin overwrites concurrent backend changes

## Error Recovery Patterns

### Transient Network Failure

- Symptom: Timeout or 5xx error
- Recovery: Plugin retries on next drain cycle (e.g., every 5 minutes via cron)
- Bound: After N failed attempts (default: 10), mark operation as `failed` and require manual review

### Idempotent Replay After Network Interruption

- Symptom: Request sent but response not received
- Recovery: Plugin retries with same idempotency key
- Backend returns cached acknowledgement if operation was previously applied

### Conflict Detected

- Symptom: 409 response with `version_conflict` or entity-not-found
- Recovery: Store conflict record; surface in admin UI; await operator resolution
- Options:
  1. Re-fetch backend snapshot and accept machine state (discard local curation)
  2. Re-push with updated `expected_base_version` (force local curation)
  3. Manual merge (operator reviews divergence and chooses resolution)
