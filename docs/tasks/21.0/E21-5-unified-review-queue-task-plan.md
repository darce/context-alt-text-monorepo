## Objective

Replace the 4-queue `SuggestionReviewPanel` stack with a **card-at-a-time review queue** driven by the existing `nextAction` selector, with kind-derived filter chips, per-item accept/reject with a brief **announced** undo window that gates the queue advance on a durable backend write (no optimistic "saved" state), and **person-commit** (creatable roster combobox) as the primary naming action on the review card. Finalize one-primary-CTA-per-state in the media footer. **The r5 wave fold adds**: ≥48px click-to-original face crops (②), show-all members with the PA-10 paging leg (③), explicit multi-select bulk with exact-id matrix M1 replacing the confidence-threshold model (①), preset band filters over the landed UXP-3 projection contract + the FBT-1 criterion-2 three-consumer harness + matrix M2 (④), and the open-target lifecycle invariant (⑤/B1, PA-06: built here). This is the demo's central interaction — it converts "a pile of stacked panels" into a legible one-item-at-a-time pipeline.

## Problem Statement

The scan→review→confirm loop is the demo's story, but today it renders as four vertically stacked queues (`SuggestionReviewPanel`, 364 lines) — assignment, merge, suggested-names, top-unlabeled-clusters — plus a bulk-accept block, all mounted at once and competing with a 10–100-row media table for attention (WBUX-1 §2.1 "everything renders at once"). The `nextAction` driver already computes the single highest-priority item but is used only to scroll to those queues or open a labeling panel — it is a scroll helper, not a queue driver. Primary naming routes through a **label-only** path (`updateClusterLabel` → cluster `label` string) rather than committing a real roster person, so a first-time visitor's "name this person" produces a label, not a person. Accept/reject has no user-facing undo (only a silent optimistic rollback on network error). The media footer shows two enabled CTAs (`MediaAnalyzeCta` accent + `BulkDescribeCta` WP-secondary) whose priority is expressed only by CSS class, with no state machine choosing one primary per screen state.

## Constraints

- **Zero backend contract changes, one scoped carve-out (PA-10)** — all needed endpoints already exist (accept/reject/merge/name, roster `.../commit`, cluster `PATCH label`). The single permitted server change is ③'s members-route paging (`limit`/`offset` on the cluster-members route, envelope already `{members, limit, total, truncated}`) — FBT-1 scope L60: "the members route may gain paging params (affordance plumbing), nothing else". Everything else (a server-side batch-by-ids, an "un-accept") is **out of scope** — the wave **stops and escalates** (FBT-1 L59) rather than inventing endpoints. The legacy `POST .../bulk-accept` (`{suggestion_type, min_confidence}`) is **no longer called by the UI** (§4) but is not removed — service untouched.
- **rg-002 (preserve atomic write paths)**: every accept/reject/commit is a **single atomic backend call per suggestion**. Do not split one backend operation into multiple frontend mutations. Card-at-a-time makes each action single-item, and the existing unbounded **group** fan-out (`Promise.all(mutateAsync…)` in `SuggestionReviewPanel.tsx:67-112`) is eliminated. Multi-select bulk (§4) is **not** an rg-002 violation: it commits N *independent* single-suggestion atomic ops **sequentially** with per-id outcome gating — no single backend op is split, no `Promise.all`, and matrix M1 asserts the exact mutated id set. Undo is rg-002-safe by construction (see Proposed Solution — immediate-commit + gated advance; exactly one POST per committed item or none; no inverse endpoint invented) [CON-05: the sequential single-in-flight rule is the lost-update guard].
- **rg-003 (zero-state reachability)**: the queue's primary controls (and the media footer's Analyze CTA) must be reachable and legible from a zero/empty state — disabled-with-reason, never hidden.
- **sr-004 (design tokens)**: all new styles consume `--acx-*` tokens landed by E21-4 (`--acx-color-*`, `--acx-text-*`, `--acx-shadow-*`, `--acx-radius-*`, `--acx-font-weight-*`, `--acx-space-*`). Zero raw hex/scale literals; the tokenization test (`workbench-tokenization.test.ts`) must stay green over every touched `components/*.scss`.
- **sr-007 (centralized status enums)**: projection categories and queue-item kinds import from a single canonical definition (extend the existing `NEXT_ACTION_KIND` / `queue_memberships` union) — no scattered magic strings.
- **No new god-context coupling**: consume existing `WorkbenchContext` / `useWorkbenchFindings` / `useSuggestionReview*` surfaces; do **not** widen `WorkbenchContextValue`. The provider decomposition is E21-11 (P5-A) and is out of scope here — but do not add fields that make it harder.
- **Banned vocabulary**: all user-visible copy passes `banned-vocabulary.test.tsx` (`topology`, `replay`, `projection`, `dead-letter`, `curation acknowledgement`, `Source version`, `projected instances`, `Curriculum`, raw UUIDs). Filter chips must use plain human labels (working copy: "Close matches", "Possible duplicates"), never raw `queue_memberships` strings or E15-13 terms of art ("Singletons" fails this bar).

## Design-direction preamble (composition of the new surface)

E21-4 owns the token direction; this preamble owns the **composition** of the new surface — a genuinely new composed card cannot inherit its layout direction from a tokens task [LAY-10: every default that survives must be a choice]. Direction (mirrors the E21-4 preamble's role, scoped to layout):

1. **One focal point, three sense-groups [LAY-01][LAY-04].** The card regroups its ~9 elements into exactly three units so the structure is absorbable without counting:
   - **G1 — subject (dominant)**: face crop + the identity question ("Is this \<name\>?" / "Who is this?"). Largest mass, first in reading order and DOM order. **Face crops render ≥48×48 CSS px (FBT-1 ② — twice the 24px control floor; the face is the evidence, not chrome; `FaceThumbnail` `sizeMap.md = 48` already provides the size) and are click-to-original: activating the crop opens the source media with the face's bounding box highlighted.** The crop is a real control (button semantics, in tab order, ≥48px bounding-box asserted). **Target surface (PR-32 — no existing surface does this)**: a new **card-local lightbox** `ReviewCardLightbox.tsx` (identity-clusters) rendering the suggestion's `mediaUrl` full-size with the face's bbox rect drawn from the same crop data `FaceThumbnail` consumes — a dialog with `Esc`/close, no routing, no new endpoint. `WorkbenchMediaDetail` is metadata-only and is **not** the target; UXP-5's row-overlay work is adjacent but not a dependency.
   - **G2 — action zone (support)**: person-commit combobox + Accept/Reject (+ tertiary "just label"). Adjacent to G1, visually subordinate to it.
   - **G3 — queue chrome (subordinate, recessed)**: filter chips, "N of M" position, prev/next. Smallest type, lowest value contrast, spatially separated from G1/G2 by the largest interval on the card [LAY-03].
   Hierarchy is carried by size/weight/position, not by nested boxes or rules [LAY-06].
2. **Type-scale steps are assigned, not emergent [TYPE-05].** Card title / identity question: `--acx-text-lg` + `--acx-font-weight-semibold`; body/meta and combobox text: `--acx-text-sm`; chip labels and the N-of-M position indicator: `--acx-text-xs`; nothing on the card takes a step not named here. Leading rebalances where a step moves [TYPE-02]. Tokenization-green proves no raw literals; **this assignment** is what proves the hierarchy is chosen — the visual re-baseline review checks it.
3. **Accent thrift — at most one accent-carrying primary in the viewport per state [COL-03][COL-09].** Token roles: **primary** = `--acx-color-accent` background + `--acx-color-accent-contrast` text + `--acx-font-weight-semibold`; **secondary/tertiary** = neutral/ghost (grey ramp, no accent). The state selector (§7) resolves primacy across the **whole rendered Workbench viewport**, not the footer alone: when the review card is on screen its G2 primary carries the accent and both footer CTAs render secondary; when no card is mounted the footer's state-selected CTA is the single accent carrier. Selection/focus tints use `--acx-color-accent-soft` and do not count as a second primary; chips use neutral styling with a value-contrast active state [COL-04], never accent fill.
4. **Target sizes are a floor, not a hope.** Every new interactive control (chips, prev/next, accept/reject, combobox trigger, undo) gets `min-width`/`min-height` `var(--acx-space-24)` (1.5rem = 24px) — the WCAG 2.5.8 floor — asserted by bounding-box in the e2e spec (A11Y-14 is owned **here** for these controls, not deferred to E21-9's drag seam).
5. **No dead chrome.** Nothing interactive-looking on the card leads nowhere (see §6 — the hard-examples chip is omitted until its contract lands) [LAY-10].
6. **Model-output disclosure (HAI-05 rider).** Every suggestion surface on the card discloses that the match is model-derived (similarity-based), in plain copy — the disclosure is part of the card composition, passes banned-vocabulary, and never dresses a model guess as a confirmed fact.
7. **Destructive prominence stays on the confirmation step [UI-06].** The multi-select bulk commit control (§4) is never the accent primary while the selection is ambiguous: while any selected group's members are unexpanded it renders disabled-with-reason or routes through an explicit confirm naming **total N + hidden count**; red/destructive weight belongs to that confirm, not the always-visible chrome.

## Workflow Principles

- **Relocate/rebuild-behind-behavior, don't redesign data flow.** The queue is a new presentation over existing queries and mutations. Every backend interaction already exists and stays byte-for-byte.
- **Risk-first slicing.** Slices 1a/1b land the structural core under orchestrator ownership — 1a the driver contract (zero UI diff), 1b the shell swap — kept separate so the highest-structural-risk step never mixes a contract change with a surface migration; later slices layer behavior onto the shell. **Implementation mandate (current)**: remote **grok-4.5 at HIGH effort implements in-worktree** (the offload security hold was lifted 2026-07-14); every slice gets dual adversarial review — grok REFUTE + an independent local subagent — with reviewer claims verified in code by the orchestrator before recording. Ordering constraints: Slice 4 (③) before Slice 5 (bulk enable); Slice 6 (④) consumes the landed UXP-3 contract. Each slice merges independently through the pre-merge gate.
- **A11y is acceptance, not audit.** Every async surface (card transition, pending/undo announce, commit result) ships a live-region assertion; the core loop passes a keyboard-walk. Axe alone gates nothing (A11Y-23).
- **Read the landed dependency plans before Slice 1** — E21-1 (`E21-1-sync-status-view-model-task-plan.md`) and E21-4 — to consume whatever status view-model and tokens actually landed rather than what this plan assumes.

## Terminology

- **Review queue**: the new card-at-a-time surface replacing the `SuggestionReviewPanel` stack.
- **Queue driver**: the `selectNextAction` priority selector (`useWorkbenchFindings.ts:112-144`), promoted from scroll-helper to the thing that chooses which single card is shown.
- **Person-commit**: creating or assigning a real roster person via `commitClusterToRosterEntry` (`POST .../roster/clusters/{id}/commit`). The Workbench label panel (`ClusterLabelingPanel`) uses the same `NameFaceControl` as the queue card and Library pane; a successful label `PATCH` also create/binds a roster person (E21-9 write-through). There is no “label-only / don’t add to roster” path.
- **Filter chip**: a chip over the review queue, **derived from the queue-item `KIND`** (not from roster `queue_memberships` — see below), rendered as **plain human copy**: assignment→**"Close matches"**, merge→**"Possible duplicates"** (working copy — final strings must pass banned-vocabulary and contain no term of art; "Singletons" is E15-13 projection jargon and is not used). **No "Hard examples (coming soon)" chip is rendered** — dead UI is omitted until its contract lands (see §6). Pending suggestions have no roster entry yet, so the roster-side `queue_memberships` field does not apply to this pre-commit queue (resolves PA-01).
- **Band chip (④)**: a second chip row of **preset similarity bands** (e.g. "Strong matches" / "Weaker matches" — final copy passes banned-vocabulary) acting as **filters over the shared suggestion projection** (`suggestionProjection.ts`): the band predicate operates on `ProjectedSuggestion.similarity` **after** `isHumanLabeledTarget` eligibility — never a re-read of raw rows, never a continuous slider, never a numeric threshold control (FBT-1 criterion 3).
- **Multi-select bulk (①)**: the only bulk path — an **explicit multi-select (default empty)**, a commit control labeled **verb + count + person label** ("Accept 4 for Maria"), a **preview set** of exactly the selected items, an undo hold, and per-id sequential atomic commits. While any selected group's members are unexpanded, the control is **disabled or confirmed with total-N + hidden count** (joint B3/B4 AC). No interim yes-all ships that ④ later tears down.
- **"Band chip" vs "band filter"**: the chip is the control, the filter is the predicate it toggles — one mechanism, two words; both defined by the Band-chip entry above.
- **Runtime matrices M1/M2 (FBT-1)**: **M1** = single / review-each / multi-select-bulk paths asserting the **exact mutated id set**; **M2** = band filter × multi-select bulk (the bulk preview/commit set is always the intersection with the active band filter). Both land as named test suites [TEST-08: exact-id assertions are the determinism guarantee].
- **Immediate-commit undo (gated advance)**: no optimistic "saved" state — a brief window holds the item as *Saving…*; when it closes the single backend call fires and the queue advances **only on success** (failure re-surfaces via a persistent inline `role=alert`). "Undo" cancels before the call fires — 0 calls if undone, exactly 1 on commit (no inverse endpoint needed). The window's countdown **pauses while focus or pointer is on the held card's undo affordance** (A11Y-16 — a fixed 5s window is illusory reversibility for AT users).

**Group handling (resolves the no-group-endpoint gap).** Same-cluster assignment groups (`type: 'group'` from `buildSuggestionReviewItems`) are **flattened to one queue item per suggestion**: the queue enumerates suggestions, N-of-M counts suggestions, and each accept/reject is the existing single atomic `POST` — rg-002 holds for every card with zero exceptions. **Focus placement on advance (the happy path, specified).** On accept/reject advance (card unmounts, next card mounts): focus moves **programmatically to the next card's primary action** (the element that owns the same role the user just activated — Accept on an accept-flow, the combobox on a NAME/CLUSTER card). **3. Immediate-commit accept/reject + announced undo (gated advance — no optimistic "saved").** On accept/reject the card enters a brief **pre-commit hold** announced as *Saving… — Undo* (an inline `role="status"` live region, **not** a false "Accepted"); the queue does **not** advance yet. When the window closes without undo (**pinned: `UNDO_HOLD_MS = 5000`** — one constant, consumed by unit/e2e/AT scripts alike) — or the user takes the next action, or navigates away — the single atomic POST fires **immediately** and the card advances **only on the backend's success**. **Undo** cancels before the POST fires (rg-002-safe: exactly one backend call, or none). **AT-viable reversibility (A11Y-16)**: the window's countdown **pauses while keyboard focus or pointer hover is on the held card's hold region** (Undo stays available until the user leaves it or acts); the Undo button is in the normal tab order immediately after the actioned control — no Radix F6 viewport-hop, no fixed unreachable deadline. The UI never reports success before the write is durable ([RLSE-05]); failure keeps/re-surfaces the item and announces via a **persistent** inline `role="alert"` (never auto-dismissing; see policy below). **Announce mechanism**: inline in-card live regions only — `ToastContext` is unusable and untouched here (no action slot, no politeness knob, assertive foreground default, hardcoded 5s — see Current State); failure follows the existing `ClusterLabelingPanel` inline-alert precedent (post-UXP-3 at `:439`/`:598` — locate by `role="alert"`, not line). **Mutation-layer scope (honest sizing)**: this is a **rewrite of the mutation choreography, not a reuse** — the optimistic cache-removal moves out of `onMutate` (the POST is deferred, so cache changes ride the hold state), and the merge/name mutations get pending/error handling **built from zero** (today they have no `onMutate`/`onError` at all — Current State). Slice 2 owns this explicitly. **Rejected alternatives**: (a) optimistic advance + deferred commit — shows "saved" before the durable write, and a React unmount cleanup cannot `await` the flushed async POST, re-introducing the silent-data-loss defect ([RLSE-05]); (b) fire immediately + inverse endpoint on undo — no such endpoint exists and it doubles backend calls; (c) durable pending-queue replayed on remount — an at-least-once replay of a non-idempotent POST double-applies without an idempotency key ([API-02]/[RES-01]) and is speculative machinery for a demo ([REF-12]).

**Undo failure + concurrency policy** (resolves PA-03):
- **Single in-flight window.** At most one commit is in flight at a time. Taking the next action (accept/reject/commit on the next card) **flushes** the prior held commit immediately (fires its POST now, gating that card's advance on the result) before opening the new window — so commits never overlap and never reorder.
- **Failure recovery.** If the fired POST rejects, the gated advance never happened, so the item **stays at the queue head**; announce the failure via `role="alert"` (`aria-live=assertive`) with a retry affordance — the A11Y-24 error state. The failure must never be silent (today's `console.warn`-only path is the defect being removed).
- **Unmount/navigation.** Leaving the Workbench (route change) or unmounting `ReviewQueue` fires any held commit synchronously. Because the advance was gated on success, an unmount-time rejection leaves the item **un-accepted (honest, re-appears next mount)** rather than a shown-saved loss — the [RLSE-05] hole is closed by construction, not by trying to `await` in cleanup.
- **Each invariant above has a named unit test** (they are check-then-act races on a shared pending ref — the likeliest real bugs): (1) *rapid double-action* — accept card A then immediately accept card B: A's POST flushes and resolves before B's window opens, exactly 2 POSTs, order preserved; (2) *unmount-during-window* — unmount with a held commit: exactly 1 POST fires, no state update after unmount; (3) *post-window failure re-surface* — flushed POST rejects: item back at queue head, persistent `role=alert` rendered, retry re-fires exactly 1 POST. These live in `useSuggestionReviewMutations.test.tsx` (new) and are Slice 2 exit criteria alongside the trivial 0-or-1-call assert.

Multi-select bulk (① — replaces the confidence-threshold model; supersedes the earlier disclosure draft).** FBT-1 criterion 3 bans the threshold path outright: "No continuous confidence slider anywhere; bulk commit only from explicit multi-select with preview set + undo" and "No numeric threshold control, hidden or otherwise (operator-decided out)". A `min_confidence` endpoint also cannot guarantee an exact mutated id set, which matrix M1 requires. The prior draft of this section ("bulk accept as a disclosure… reusing `POST .../bulk-accept`") is therefore **withdrawn**; the confidence-threshold block is deleted with the stack and the legacy endpoint goes UI-unused (service untouched — Constraints).

The replacement is the FBT-1 final model, built once, no interim yes-all: **explicit multi-select (default empty)** over queue items; commit control labeled **verb + count + person label**; a **preview set** enumerating exactly the selected items; the same announced undo hold as single actions (§3); commit = **sequential per-suggestion atomic POSTs** with per-id outcome gating — single in-flight rule holds (§3 policy extends: the bulk set is one hold; flush fires the sequence; first failure stops the run, announces via the persistent `role=alert`, and re-surfaces the unfired remainder still-selected) [CON-05][RES-01].

**Selection surface (resolves the one-card tension — PA-14).** Selection accrues via a **per-card "Select" affordance**: the user pages through cards (prev/next) and toggles selection card-by-card; selected ids accumulate in a **selection tray** rendered inside G3's queue chrome (count + "Review selection" control), and the **preview set renders inside the commit confirmation disclosure** (a list of the selected items' face/label rows, not full cards). The **one-card invariant is scoped to review cards**: exactly one *card* renders at a time; the tray and preview list are selection chrome, not cards, and the 1b unit test asserts the invariant against card instances so Slice 5 does not break it. Selection is **id-keyed**, so projection invalidations that reorder or refetch the queue mid-selection cannot corrupt it; a selected id that leaves the projection (resolved elsewhere) is dropped from the tray with an announced count update. **Selection ownership/lifetime (PR-31)**: the id-keyed selection set is **lifted to `ScanTabContent` beside the queue index** (same rationale — the `clusterPanel` swap unmounts `ReviewQueue` wholesale); `useBulkReviewCommit.ts` receives it as a controlled prop pair. A `label`/`review` panel round-trip **preserves** the selection; Slice 5 asserts it.

**Bulk commit label (PR-38).** "Accept N for \<label\>" renders only when every selected item shares one target label; heterogeneous selections (mixed persons/kinds are legal under free multi-select + KIND filters) render **"Accept N selected"**. Named M1 case.

**Partial-failure surface (PA-27).** Committed ids leave the tray/preview as each POST succeeds; on stop-on-failure the persistent `role=alert` names **how many landed and how many remain** ("3 of 5 accepted — 'Accept' failed for Maria; 1 not attempted"); the remainder (failed + unattempted) stays selected for retry.

**Bulk state machine (PR-30 — one machine, pinned):**

| Event | Behavior |
| --- | --- |
| Bulk commit initiated (tray) | **First flushes any held single commit** (full §3 flush, gated); then opens ONE bulk hold announced **"Saving N… — Undo"** (same hold mechanics as single: `UNDO_HOLD_MS`, pause-on-focus/hover) |
| Undo during bulk hold | Cancels the **entire set** — 0 POSTs; selection unchanged |
| Hold window lapses / next action taken | Fires the **full sequence**: sequential per-id POSTs, single-in-flight, stop-on-first-failure (per-id gating above); a following single action waits for the sequence to finish before its own hold opens |
| Unmount with a held/running bulk | Fire **item 1 only** synchronously; **cancel the remainder** — honest: "Saving…" is a pending claim, never "Saved"; unfired items re-appear still-selected/pending on next mount (a multi-POST sequence cannot run in a React cleanup — same [RLSE-05] argument that rejected optimistic advance) |
| Overlap with a held single commit | An id in a held single commit **cannot be selected** into the tray (and vice-versa: selecting is disabled on the in-hold card) — no id can ever be POSTed twice; named M1 case asserts the exclusion |

Named Slice-5 unit tests: bulk-undo = 0 POSTs; single→bulk flush ordering; bulk→single flush ordering; bulk×unmount (item-1 + cancelled remainder); in-hold id selection exclusion. **Joint B3/B4 AC — truncated predicate defined (PR-35)**: queue cards do not load cluster members today, so "unexpanded/truncated" needs a data source: when the selection is non-empty, a thin **`useSelectedClusterTruncation.ts`** hook prefetches `fetchClusterMembers(suggested_cluster_id)` (first page only) for each distinct selected target cluster and reads the envelope's `truncated`/`total`; while any selected item's target cluster is `truncated` and unexpanded, the commit control is disabled-with-reason or confirms with **total-N + hidden count** [UI-06].
